## 6. 数据合理性检查（说明这些数字是真的物理测量）

- 静止放置时合矢量 `|a|` 稳定在 **0.97 ~ 0.99 g**，接近理论重力加速度 1g —— 这是加速度计最直接的物理自洽性证据。
- 板子被斜放/竖放时，`|a|` 会随姿态变化（我们实测过 0.87g、0.93g、0.98g 等不同姿态下的结果），
  三个轴的分量随姿态重新分配，而合矢量始终接近 1g。**这是姿态差异，不是标定或代码问题**（见第 7 节）。
- 相邻 1 秒的采样值互不相同（例如 raw_x 在 -2825 ~ -2868 之间自然抖动），
  这是真实传感器的噪声表现；如果是写死的固定值，读数会一模一样。

## 8. 现场真实遇到的 6 个问题与处理（排错记录）

这部分是本次真实踩坑记录，遇到同类现象时可对照排查。

### 8.1 板子连不上手机热点，`reason=201`（AP 未找到）
板子能扫到 17 个 2.4GHz 热点，但目标 SSID 不在列表里 —— 原因是**手机热点工作在 5GHz**，
而 ESP32-S3 只支持 2.4GHz。固件里加了热点扫描功能，把这件事变成可核对的证据；
后来改用 2.4GHz 路由器 `432` 后正常联网。

### 8.2 HTTPS 报 `No matching trusted root certificate found`
隧道/VPS 的证书由 Google Trust Services 签发，ESP-IDF 内置根证书包里没有对应根。
**没有采用"关掉证书校验"的做法**，而是用 `tools/gen_ca_header.py` 把服务器真实下发的
CA 链抓下来内嵌进固件（`firmware/src/server_ca_pem.h`），HTTPS 依旧是真实校验。

### 8.3 串口抓不到开机日志
ESP32-S3 的 USB-Serial-JTAG 发送缓冲很小，宿主机"事后"再打开串口就看不到开机那几行；
而且打开串口本身会复位芯片、导致 USB 重新枚举、刚打开的句柄立刻失效。
解决：`tools/serial_watch.py` 采用"开两次"策略（第一次触发复位、第二次稳定读取），
并能把复位原因打印到可见位置。

### 8.4 板子约 1 次/秒反复重启（本次最关键的一次排错）
现象：开机计数在 110 秒内从 342 涨到 442；串口输出总是断在 `wifi_init: tcp mss: 1440` 之后，
也就是 **Wi-Fi 射频启动的瞬间**。这是典型的"供电能力不足 → 射频峰值电流把电压拉低 →
brownout 复位"。处理：固件里把 Wi-Fi 最大发射功率降到 8dBm（`APP_WIFI_MAX_TX_POWER_QDBM=32`），
并在自检之后补打一行复位原因。改完后板子稳定运行、连续上传（本文档的所有记录都是修复之后的）。

> 如果换用供电更充足的 USB 口/优质数据线，可以把发射功率调回 78（19.5dBm）以换取更远距离。

### 8.5 三方核对时时间戳差 2ms
同一个数据包，串口打印的 `ts` 和上传 JSON 里的 `ts_local` 之前各自调了一次 `gettimeofday`，
相差 2ms，会被误判成"数据不一致"。已在固件里改成**每包只取一次时间**，两处共用同一个字符串。

### 8.6 主机时钟跳变
本机（虚拟机）在挂起/恢复后系统时钟发生了跳变，导致数据库里 `received_at_utc`（服务器接收时间）
与设备 `ts_local`（设备 SNTP 对时后的本地时间）看起来不在同一时刻。
**设备侧的 `ts_local` 来自真实 SNTP 对时**（`ntp.aliyun.com` 等），是可信的时间来源；
服务器接收时间是"入库时刻"的记账字段，两者用途不同。核对时请以同一数据包的字段为准。

### 8.7 实际上报频率只有 0.23Hz（配置写的是 1 秒一次）
现象：数据库里每分钟只有 11~13 条记录，而不是 60 条。两个原因叠加：

1. 每次上传都新建 HTTPS 连接，**TLS 握手要 3.5 秒左右**（TCP + TLS + 证书校验）；
2. 主循环在每次上传后无条件 `delay(1000ms)`，于是真实周期 = **上传耗时 + 1000ms**。

处理（两处都是通用做法，不是特例补丁）：

- **复用连接**：HTTP 客户端开启 `keep_alive_enable = true` 并保留同一个句柄，
  后续上传不再握手。★ 注意必须按 HTTP/1.1 语义**把响应体读干净**——
  响应缓冲区只有 512 字节而服务器回显更长，留着没读完的字节会让复用连接上的下一次请求错位，
  实测表现为 `服务器返回非 2xx: -1`，一次成功一次失败交替出现；
- **周期校准**：主循环只补足"本周期还差的时间"，让 `APP_UPLOAD_PERIOD_MS` 名副其实。

效果（同一板子、同一网络实测）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 单包上传耗时（DATA→POST） | 约 3.5 秒 | **0.88 秒** |
| 实际上报周期 | 约 4.4 秒（0.23 Hz） | **1.00 秒（0.93 Hz）** |
| 每分钟入库条数 | 11 ~ 13 | 约 56 |

好处不止是"数据更密"：握手次数大幅减少后，射频与 CPU 的峰值电流下降，
对第 8.4 节那个"供电不足导致 brownout"的问题也是正向帮助。

### 8.8 网页看起来一卡一卡（画面不流畅）
现象：曲线像是"每两秒跳一格"，数值也是隔两秒才动一下。
原因（都在前端，与硬件无关）：

1. 曲线只在**每次轮询拿到新数据时**才重绘一次，另外还有一个 5 秒的定时重绘 ——
   于是画布大约每 2 秒才更新一帧；
2. 横轴是按**点的序号**定位（`xAt(i)`），不是按真实时间 —— 所以新点一进来，
   整条曲线会整体平移一大格，而不是连续左移；
3. 轮询间隔 2000ms，比板子 1Hz 的上传节奏还慢，最新数据最多滞后 2 秒才出现。

处理：

- 改用 `requestAnimationFrame` **每帧重绘（约 60FPS）**，并在页面切到后台时停画（不白烧 CPU）；
- 横轴改为**按真实时间定位**：右边缘 = 当前时间 + 少量余量，曲线随真实时间连续左移；
  服务器与本机时钟的偏差用"收到该记录时的本机时间"做一次性校正，
  所以即使两边时钟不一致，采样点也落在正确位置；
- 轮询间隔 2000ms → **800ms**（本地请求，开销可忽略），新数据几乎立刻出现；
- Y 轴范围加了约 120ms 时间常数的缓动，量程切换时不会整屏跳变；
- 数值卡片在新数据到达时轻轻闪一下，方便眼睛捕捉变化。

★ 关键约束：**平滑只发生在画布动画上**。卡片数字、时间戳、原始码值一律原样取自接口，
不做插值、不做滚动动画 —— 页面上永远不会出现"某个从没被测到过的数值"。
自检脚本会断言这一点（跑满 61 帧后数值仍精确等于接口返回值）。

实测（`node tools/test_web_stale.js`，手动喂帧）：

```
frames: 0 -> 61          fps 统计 = 61
1.017 秒内曲线左移 19.25px（60 秒窗口的理论值 19.2px）
渲染 61 帧后 valGX 仍精确等于接口值 -0.692     ✔
切到后台标签页：30 帧内帧数增量为 0（确实停画） ✔
```

### 8.9 "还能不能再高一点？"——帧率上限由显示器决定
`requestAnimationFrame` 是**与显示器垂直同步对齐**的，所以帧率上限 = 显示器刷新率：

| 显示器 | 同一份代码的实测渲染帧率 |
|---|---|
| 60Hz | 61 FPS（中位帧 16.7ms） |
| 120Hz | **120 FPS**（中位帧 8.3ms，自检里用可控时钟喂 8.33ms 帧实测得到） |

所以"再高一点"分两种情况，别混在一起：

1. **画面渲染不够快**：先把页脚的 `显示器 ≈xxHz · 最慢 xx ms` 看一眼。
   FPS 与刷新率一致 → 已经到硬上限，再优化也没有意义；
   FPS 明显更低或"最慢帧"远超中位帧 → 那才是掉帧，可以继续优化（本次已先把
   每帧的 DOM 写入与布局读取全部节流掉：61 帧内 DOM 写入 0 次、读布局 0 次）。
2. **数据本身不够密**（曲线内容 1 秒才变一次）：这才是真正能"再高"的地方 ——
   原来板子是 1Hz 采集上传。**这项改动已经实施并实测通过**，见下面第 8.10 节。

另外两个不用改代码就能"看起来更活"的开关：
`?window=20`（时间窗口 60s→20s，曲线左移速度变成 3 倍）、`?poll=250`（最新点更早出现）。

### 8.10 把数据密度从 1Hz 提到 10Hz（本轮改动，已实测）

需求是"曲线内容要一直在变，而不是一秒才跳一次"。做法不是把请求频率提到 10Hz
（那会把连接数打满，而且隧道单次请求要 0.88 秒，根本发不过来），而是：

**① 板端：100ms 采一个点，攒 10 个点（1 秒）发一次包**

| 配置 | 值 | 作用 |
|---|---|---|
| `APP_SAMPLE_PERIOD_MS` | 100 | 采样周期（10Hz） |
| `APP_BATCH_SIZE` | 10 | 一包 10 个点（= 1000ms / 100ms） |
| `APP_UPLOAD_PERIOD_MS` | 1000 | 上传周期（HTTPS 仍然 1 次/秒） |
| `APP_MAX_MERGE` | 30 | 网络慢时最多把 30 个包合并成一次请求 |

**② 板端：采集与上传拆成两个 FreeRTOS 任务**（这是本轮最关键的结构改动）

原来是"采集 → 上传 → 再采集"的单循环，实测出现过：隧道一次超时 10 秒 × 重试 3 次
= 采样被卡住 33 秒，库里出现 62 秒空洞。现在：

```
sampler_task (core 1, 优先级 6)           uploader_task (core 0, 优先级 5)
  每 100ms 读一次真实 IMU  ──指针──►  从队列取包 → 合并积压 → POST → 打印回显
  填进静态包池的一个槽位    队列       网络慢只影响上传队列，采样节奏不受影响
  打印 [DATA] 行
```

包池是 12 个静态缓冲（不动态分配内存），两个队列只传指针。每个采样点自带
`seq` 与包内序号 `idx`，所以"合并上传"之后仍然能与串口、数据库逐点对上。

**③ 后端：一次请求存 N 行，并支持增量查询**

`POST /api/v1/ingest` 接受 `samples[]` 数组，在**一个事务**里插入 N 行；
返回体前几个字段是 `ok/id/stored_count/sample_idx/seq/device_id/received_at_utc/stored`
（因为板端串口回显缓冲只有 512 字节，重要的字段必须排在前面）。
`GET /api/v1/records?after_id=<id>&limit=N` 支持按 id 增量拉取。

**④ 前端：增量拉取 + 逐点追加**

以前每次轮询只取 `/api/v1/latest` **一条**，800ms 里新产生的 8 个点会被直接丢掉，
曲线看起来"一段一段地跳"。现在改成 `after_id` 增量拉取，按 id 去重后逐点追加，
一个点都不漏；DOM 仍然**一个批次只写一次**（卡片显示该批次最新点的值）。

**实测结果（真实硬件，2026-10-08）**

| 指标 | 实测值 | 数据来源 |
|---|---|---|
| 采样间隔 | 中位 **100.0ms**，均值 100.0ms，**97~98% 落在 90~110ms** | `evidence/final_10hz_suite.log` |
| 实存采样率 | **10.01 Hz**（15 分钟窗口 9000 点 / 898.9 秒） | 同上 |
| 包大小 | 恒为 **10 点/包** | 同上 |
| 包间隔 | 中位 **1.01s** | 同上 |
| 后端换算校验 | **9000 / 9000 行全部通过** | 同上 |
| 串口采样节奏 | 中位 100.0ms，96.3% 在 ±10% 内，64 次 POST 全部 201 | `evidence/batch10hz_run.log` |
| 每次上传耗时 | 中位 **0.31s**（直连，之前经隧道是 0.88s） | 同上 |
| 网页 60 秒窗口内真实采样点 | **590 个**（stride=1，即每个点都画） | `evidence/final_10hz_suite.log` |
| 网页数值 | 全部来自接口，0 处兜底假值 | 同上 |
| 前端行为自检 | 全部通过（含新增的"一次 10 个点必须全部追加"断言） | 同上 |
| 三方核对 | 12/12 逐采样点一致（键 = boot+seq+包内序号） | `evidence/verify_report.json` |

**本轮踩到的两个真坑（都留了记录）**

1. **`LoadProhibited` 崩溃重启循环**：改成任务化之后板子开始反复重启
   （串口 `Guru Meditation Error: Core 1 panic'ed (LoadProhibited)`）。
   用 `tools/decode_backtrace.py` 直接把崩溃地址解成调用栈：

   ```
   0x420a6b24: i2c_master_transmit_receive at …/esp_driver_i2c/i2c_master.c:1326
   0x420040f9: reg_read_multi  at D:\ESP\firmware/src/imu_qma6100p.c:156
   0x420043a5: imu_read_raw    at D:\ESP\firmware/src/imu_qma6100p.c:296
   0x42004440: imu_read_raw_averaged at D:\ESP\firmware/src/imu_qma6100p.c:319
   0x4200370d: sampler_task    at D:\ESP\firmware/src/main.c:434
   ```

   栈顶落在 I2C 驱动里，但**根因不在 I2C**：包池的槽位释放回队列时没有把
   `n`（包内点数）清零，重新取到该槽位后 `pkt->s[pkt->n++]` 从 `n=10` 继续写，
   越界写了约 1240 字节，踩坏了相邻内存。修复 = 取用和归还时都重置 `n=0`。
   修复后连续运行 **15 分钟、采集 9000 点无重启**（`boot 808`，见
   `evidence/final_10hz_suite.log`）。
2. **抓串口本身会复位板子**：`serial_watch.py --attach` 也照样把芯片复位
   （`rst:0x15 USB_UART_CHIP_RESET`）。所以"长时间稳定性"不能用串口观察，
   改用 `tools/analyze_db_rate.py` 只读数据库 —— 它是零干扰观察者，
   还能直接列出每个 `boot_count` 的运行时长，短命 boot（重启循环）一眼可见。
