## 1. 交付一：远程采集功能

### 1.1 「刷新已存数据」vs「采集最新数据」——两种行为在代码上如何区分

| | 刷新已存数据 | 采集最新数据 |
|---|---|---|
| 用户意图 | 看数据库里**已经存下来**的记录 | 让设备**现在当场读一次**真实寄存器 |
| 前端调用 | `GET /api/v1/records`、`GET /api/v1/latest`、`GET /api/v1/stats`、`GET /api/v1/devices` | `POST /api/v1/collect_requests`，随后 `GET /api/v1/collect_requests/<id>` 轮询 |
| 后端动作 | 只 `SELECT`，不写任何表 | 写 `collect_requests` + `pending_commands`（排一条 `collect_now` 指令） |
| 设备侧流量 | **零** | `commands/poll` → `device/ack` → `observations` 三跳 |
| 可观测差异 | 串口无新 `[DATA]`/`[POST]` 行 | 串口出现 `[CMD] recv`、`[ACK]`、`[CMD-DATA]`、`[OBS]` 四类新行 |
| 页面按钮 | `#refreshBtn` | `#collectBtn` |

代码落点：
- 前端：`web/app.js` 的 `refreshStoredData()` 与 `createCollectRequest()`。
  **`refreshStoredData()` 里刻意不调用任何以 `collect_requests` 开头的接口**
  （连动作执行追踪列表都不刷新），这样"刷新 = 零设备侧流量"在代码上是可审计的。
- 后端：`create_collect_request()` 是唯一会往 `pending_commands` 排指令的地方。

### 1.2 设备 / 传感源 / request_id / 任务完成条件

| 项 | 落地值 | 说明 |
|---|---|---|
| 目标设备 | `device_id = esp32s3eye-1C701C` | 由芯片 eFuse MAC 派生，重启不变（`main.c::init_device_id`） |
| 传感源 | `sensor = "qma6100p"` | 板载 QMA6100P，I2C `0x12`、CHIP_ID `0x90` |
| `request_id` | `uuid4()` 字符串，`collect_requests` 主键 | 一次点击 = 一行 |
| `nonce` | `uuid4().hex`（32hex） | 随指令下发、随观测回传，**L1 身份绑定**的凭据 |
| 基线快照 | `baseline{boot_count, seq_last, uptime_ms}` | 取 `devices.last_*`，**L2/L3 的参照点** |
| 超时 | `timeout_ms = 15000`，由后端决定 | 前端传 `timeout_ms` 一律忽略（`TC-W2-07`） |
| `deadline_utc` | 设备**取走指令那一刻** + `timeout_ms` | 不是提交时刻 —— 见下面 §1.4 的坑 |

**任务完成条件（L1 ∧ L2 ∧ L3 同时成立）**，实现见 `backend/server.py::submit_observation()`：

| 层 | 判定 | 失败码 |
|---|---|---|
| L1 身份 | `obs.nonce == req.nonce` | `REQ_ID_MISMATCH` |
| L2 新旧 | `boot_count > 基线boot` （跨重启）**或** 同 boot 且 `seq_first > 基线seq` | `STALE_OBSERVATION` |
| L3 时间 | 跨 boot 直接成立；同 boot 要求 `up_ms > 基线up_ms`，且服务端接收时刻 ≥ 下发时刻 | `STALE_OBSERVATION` |
| 附加 | 每个 sample 必须含 `raw.x/y/z` | `MISSING_FIELD` |

**任一不成立 → `409` + 写 `rejected_observations` 留痕 + `collect_requests.status` 绝不改写。**

### 1.3 请求–回执–观测 记录（三表联查）

一次真实采集在库里产生的行（真机实测的 `request_id` = `077648d6-…`）：

```
collect_requests   request_id=077648d6-…  status=completed
                   submitted=02:21:09.331  dispatched=02:21:13.100  acked=02:21:13.373  completed=02:21:14.032
                   baseline={boot:840, seq:0, up:…}   timeout_ms=15000
        │
        ├── request_acks      ack_type=received   ack_at=02:21:13.373  nonce=…
        │
        └── observations      boot_count=840  seq_first=seq_last=151
                              record_id=108835  upload_id=12079
                              freshness=new_monotonic  verify_ok=1
                              value={|a|=1.543535, raw=(-2601,170,5760)}
                                   │
                                   ├── sensor_records  id=108835  request_id=077648d6-…  report_mode=manual
                                   └── raw_uploads     id=12079   sha256=…  body=<逐字节原文>
```

时间关系满足 `提交 ≤ 下发 ≤ 回执 ≤ 完成`（实测 4701ms / 1102ms）。
查询语句：

```sql
SELECT r.request_id, r.status, r.submitted_at_utc, r.dispatched_at_utc,
       r.acked_at_utc, r.completed_at_utc, a.ack_type, o.seq_last,
       o.freshness, o.value_json, o.record_id, o.upload_id
FROM collect_requests r
LEFT JOIN request_acks a ON a.request_id = r.request_id
LEFT JOIN observations o ON o.request_id = r.request_id
WHERE r.request_id = '<RID>';
```

### 1.4 实现过程中踩到并修掉的两个真坑（都只在真机上才暴露）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 板子每秒都成功收到含 `collect_now` 的响应（HTTP 200 / 402 字节 / 连收 11 次），却**从不**打印 `[CMD] recv`，请求最后超时。看起来像"设备没收到指令" | 固件 `json_get_str()` 按 `"type":"` 匹配，而后端 `json.dumps` 输出的是 `"type": "`（**冒号后带空格**）。分隔符写死 → 一条指令都解析不出来 | 解析时跳过 `:` 后的空格：`while (*p==' ') p++;`（`cmd_client.c`，已写进注释） |
| 2 | 采集任务与周期上传任务共用同一个 keep-alive 句柄，出现**响应张冠李戴**（cmd 拿到 `/ingest` 的响应体，"指令解析失败"疯狂刷屏） | 两个任务并发在同一个 `esp_http_client` 上 `open/write/read` | 给 `uploader_post_json_url()` 加互斥锁（`uploader.c::s_http_lock`），一次请求串行完成，连接照旧复用 |

另外一处设计性修正：
- **`deadline_utc` 必须从"设备取走指令"起算**，而不是提交时刻。否则设备离线期间排队的请求会在还没下发时就先超时（`TC-W2-11` 要求"断网期间保持 submitted"）。实现在 `poll_commands()` 里第一次取走时重算 deadline。
- **设备自报的 `periodic_enabled` 不得覆盖服务端暂停决定**。否则"暂停 → 设备下一次轮询自报 true → 暂停被自己解除"。只有 `pause_reports`/`resume_reports` 回执才允许改 `devices.periodic_enabled`。

## 2. 交付二：请求状态图

### 2.1 状态机（与 `backend/server.py` 实现逐边一致）

```
                              POST /api/v1/collect_requests
                                        │
                                        ▼
                                 ┌─────────────┐
                                 │  submitted  │ 已提交（后端已落库）
                                 └──────┬──────┘
                                        │ 设备 poll 取走指令
                                        │   → 写 dispatched_at_utc
                                        │   → deadline = dispatched + timeout_ms
                                        │
                            ack: received │
                                        ▼
                                 ┌─────────────┐
                                 │    acked    │ 设备接收回执  ← 页面蓝徽标
                                 └──────┬──────┘
                                        │ ack: started（可选中间态）
                                        ▼
                                 ┌─────────────┐
                                 │ collecting  │ 设备采集中
                                 └──────┬──────┘
                                        │
                 观测到达且 L1∧L2∧L3 全真 │
                                        ▼
                                 ┌─────────────┐
                                 │  completed  │ 完成（终态）← 页面绿徽标
                                 └─────────────┘

  旁支（都是终态）：
  ┌────────────────────────────────────────────────────────────────────┐
  │ ack: rejected            → failed     失败      （页面红）           │
  │   reason=SENSOR_ERROR 才是"硬件问题"的唯一来源                       │
  │ ack: superseded          → cancelled  failure_reason=SUPERSEDED      │
  │ 操作者 cancel            → cancelled  failure_reason=CLIENT_CANCELLED│
  │ deadline 到期仍未回报    → timeout    超时      （页面橙）           │
  │   ★ 由服务端 1s 扫描任务置位；只写 device_events(command_timeout,    │
  │     source='server')，绝不改 devices.last_status、绝不写 sensor_error│
  └────────────────────────────────────────────────────────────────────┘

  自环（★ 关键：拒收不改写状态）：
  ┌────────────────────────────────────────────────────────────────────┐
  │ 观测被拒收（409） ─────► 状态**保持不变**，只往 rejected_observations │
  │   REQ_ID_MISMATCH / STALE_OBSERVATION / DUPLICATE_BATCH /           │
  │   REQUEST_ALREADY_FINAL / MISSING_FIELD                             │
  └────────────────────────────────────────────────────────────────────┘

  终态集合 = { completed, failed, timeout, rejected, cancelled }
  终态后到达的观测一律 409 REQUEST_ALREADY_FINAL，状态不改写。
```

### 2.2 页面徽标 ↔ 后端 `status` 映射（`web/app.js::REQ_STATUS_TEXT`）

| `status` | 徽标文案 | 颜色 | 判据 |
|---|---|---|---|
| `submitted` | 已提交 | 灰 | 后端已落库 |
| `acked` | 设备接收回执 | 蓝 | 有 `ack_type=received` |
| `collecting` | 设备采集中 | 蓝 | 有 `ack_type=started` |
| `completed` | 完成 | 绿 | 有合法 `observation` |
| `failed` | 失败 | 红 | 有 `ack_type=rejected` |
| `timeout` | 超时 | 橙 | `now > deadline_utc` |
| `rejected` | 请求被拒 | 灰红 | 创建时校验不过 |
| `cancelled` | 已撤销 | 灰 | 操作者撤销 / `superseded` |

页面**不自造状态**：拿不到 `status` 时显示 `—（未知状态）`，而不是猜一个业务状态词。
`acked` 的文案明确写「**还不算采集完成**」，并断言不得出现观测数值区（`tools/test_web_collect.js` 有 DOM 断言）。

### 2.3 `timeout` 文案红线（页面禁止说"硬件故障"）

| 后端事实 | 页面显示 | 页面禁止 |
|---|---|---|
| `timeout` + 设备近 15s 有轮询 | 「设备在线，但未在 15s 内回报」+「这不等于设备故障」 | ❌ 设备故障 / 传感器损坏 |
| `timeout` + 设备超 15s 无轮询 | 「设备当前离线（可能关机或断网）」+「无法据此判定硬件状态」 | ❌ 硬件故障（离线含关机与断网两种，不得断言） |
| `ack_type=rejected` + `reason=SENSOR_ERROR` | 「设备明确拒绝——传感器读取失败」 | ❌ 超时 |

判定脚本 `tools/test_web_collect.js` 用 `assertsHardwareFault()` 做**否定语境感知**检索：
页面写「这不等于设备故障」是正确的（明确否认），不能因为出现这四个字就判失败。

## 3. 交付三：动作执行追踪

### 3.1 接口

`GET /api/v1/collect_requests?device_id=&status=&limit=` （`limit` 默认 50，上限 500，按 `submitted_at_utc DESC`）

每项含：`request_id / device_id / status / submitted_at_utc / dispatched_at_utc /
acked_at_utc / completed_at_utc / deadline_utc / failure_reason / rejections_count /
observation{observation_id, seq_first, seq_last, magnitude_g, freshness}`

### 3.2 页面

`#reqList` 表格（提交时刻 / request_id / 状态 / 设备回执 / 完成 / 被拒次数 / 观测摘要），
点任意一行即把上方详情切到该请求 —— 用来复盘"连点两次各自终局"。

### 3.3 重复点击的两种确定行为

| 场景 | 机制 | 结果（真机/自检实测） |
|---|---|---|
| **双击**（2 秒内同一意图） | 前端复用同一个 `client_request_key`，后端在其上做幂等 | 返回**同一个** `request_id`，HTTP `200` + `deduplicated:true`，`collect_requests` 该 key 只有 1 行 |
| **刻意连点**（不同 key） | 两条独立请求 | `collect_requests` 新增 **2 行**，各自独立走状态机、各自留终局 |
