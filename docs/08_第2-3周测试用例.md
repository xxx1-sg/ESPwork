## 0. 阅读与使用方式

1. 执行前先读 §1（环境与前置）与 §2（编号/层级/字段规则），并按 §1.5 把脚本路径、COM 口、`device_id` 填成实测值。
2. 按 §3 → §4 → §5 的顺序执行；§5（当堂验证）必须由验收人在场、可独立复现。
3. 每条用例执行后：把「实际结果」列填成**与期望逐条对应的通过/不通过**（不要写"正常"），
   并在 `evidence/` 落下 §1.6 规定的文件；文件名必须能被本用例的「证据留存方式」列精确定位。

   且**不得**计入实物验收（规则见 §7）。

### 1.4 数据准备

1. **取 `device_id`**：`curl.exe -s http://127.0.0.1:8000/api/v1/devices`，取 `data.devices[].device_id`。
2. **必须先让设备轮询一次再创建采集请求**（否则 `409 NO_BASELINE`）：
   板子上电后等 ≥1 秒，使设备侧发出 `POST /api/v1/device/commands/poll`；
   随后确认基线可读：
   ```powershell
   curl.exe -s "http://127.0.0.1:8000/api/v1/devices" | Select-String "<DID>"
   ```
   基线来源 = `devices.last_boot_count` / `devices.last_seq`；这两个值非 `null` 才允许建单。
3. **是否新建测试设备的判定**：
   - 实物用例（P0）：**只能**用真实板子自然轮询产生的 `devices` 行，**禁止**手工插入；
   - 接口/边界用例（如 `NO_DEVICE`）：用**不存在**的 `device_id`（如 `esp32s3eye-NOTEXIST`）即可，无需造数据；
   - 只读/回归用例：直接对现有生产库跑脚本，不造行。
4. **需要"干净起点"时的两种做法**：
   - 首选（不动生产库）：`$env:SENSOR_DB="D:\ESP\backend\data\w23_test.db"` 后启动后端，用一个独立测试库；
   - 次选（清测试库）：先停后端，再 `Remove-Item D:\ESP\backend\data\w23_test.db*`，重启后端由 `SCHEMA` 自动建表。
5. **回归基线快照（第 1 周证据不许变）**：在测试开始前落一份只读快照：
   ```powershell
   & D:\ESP\.venv\Scripts\python.exe -c "import sqlite3,json;c=sqlite3.connect(r'D:\ESP\backend\data\sensor.db');print(json.dumps({'raw_uploads':c.execute('select count(*) from raw_uploads').fetchone()[0],'sensor_records':c.execute('select count(*) from sensor_records').fetchone()[0],'max_id':c.execute('select max(id) from sensor_records').fetchone()[0],'max_sha':c.execute('select sha256 from raw_uploads order by id desc limit 1').fetchone()[0]}))" | Tee-Object D:\ESP\evidence\w2_baseline_snapshot.json
   ```

## 2. 测试分层与编号规则

### 2.1 编号规则

| 前缀 | 含义 | 数量 |
|---|---|---|
| `TC-W2-xx` | 第 2 周（远程采集指令与执行结果反馈） | 48 条（`TC-W2-01` … `TC-W2-48`） |
| `TC-W3-xx` | 第 3 周（按键触发与物理反馈闭环） | 29 条（`TC-W3-01` … `TC-W3-29`） |
| `TC-LIVE-W2-xx` / `TC-LIVE-W3-xx` | 当堂验证（必须由验收人在场复现，单列于 §5） | 6 条（W2 4 条 + W3 2 条） |

编号自左向右顺序执行；`TC-LIVE-*` 是对 §3/§4 中被标注用例的**现场复现版**（同一事实、更强的现场约束）。

### 2.2 层级定义（`层级` 列的取值）

| 层级 | 测试对象 | 判定方式 |
|---|---|---|
| 单元 | 单一函数/单条规则（如 `poll_after_ms` 取值、换算公式、前端文案映射函数） | 断言输入→输出，不需要板子与网络 |
| 接口 | 单个 HTTP 端点的报文、状态码、错误码、落库效果 | `curl.exe`/`Invoke-RestMethod` + SQL 断言 |
| 集成 | 跨两个及以上角色（Web↔后端↔设备）的一次完整交互 | 串口 + 后端日志 + 数据库三方可对齐 |
| 系统 | 端到端现象（页面徽标、物理蜂鸣/LED、断网） | 页面/物理/串口实测 |
| 当堂验证 | 验收人在场、可独立复现、带阈值与留证据命令 | 现场打印 + 现场截图，见 §5 |

### 2.3 优先级定义

| 优先级 | 含义 | 与本工程对应 |
|---|---|---|
| P0 | 不变量被破坏即判失败（旧值被标成本次完成 / 超时被报成故障 / 无回执显示已收到 / 断网后本地反馈失效） | 三条红线相关用例 |
| P1 | 功能主链路或字段契约不成立，但未破坏三条不变量 | 状态机、幂等、列表、暂停上报 |
| P2 | 展示、文案、可用性、次要一致性 | 文案措辞、可选屏幕、列表排序 |

### 2.4 每条用例的字段说明（本文件所有用例表统一使用下列 9 列）

| 列 | 填写规则 |
|---|---|
| 用例ID | `TC-W2-xx` / `TC-W3-xx` / `TC-LIVE-xx` |
| 标题 | 一句话说明"测什么"，含被断言的事实 |
| 层级 | 取 §2.2 的枚举之一 |
| 优先级 | `P0` / `P1` / `P2` |
| 前置 | 必须已满足的状态（设备在线、基线已就绪、后端已起，等） |
| 步骤 | 可直接照做的最小步骤序列（`1)` `2)` `3)`），涉及命令时给出可复制命令或指向 §8 |

## 6. 缺陷分级与判定标准

### 6.1 分级定义

| 级别 | 定义 | 典型情形 | 处理要求 |
|---|---|---|---|
| **P0** | **不变量被破坏**，或数据真实性/安全底线被破坏 | ① 旧值被标成本次完成（拒收未拦截、`status` 被回写成 `completed`）；② 超时被报成硬件故障（写 `sensor_error` / 改 `devices.last_status` / 页面出现"设备故障"）；③ 无远端回执却显示"对方已收到"；④ 断网后本地反馈失效（按键无蜂鸣/无 LED）；⑤ 历史记录被改写（`sha256`/值变化）；⑥ 令牌校验失效导致任意设备可下发指令 | 立即停止当堂验证，修复后**重跑全部 P0 用例**与当堂验证 |
| **P1** | 功能主链路或字段契约不成立，但三条不变量未破 | 字段名与 06 号文档不一致；幂等失效（重复 ack/观测产生多行）；暂停上报后周期包仍在跑；`ids` 列表缺失；`unreachable`/`pending_local` 未实现；`cancel_reason` 未校验 | 当轮修复，重跑相关分组 + 受影响的回归 |
| **P2** | 展示、文案、可用性、次要一致性 | 徽标颜色与文档不符；`age_ms` 误差 >2s；列表排序或 `limit` 夹取不生效；可选屏幕显示问题 | 记录进问题清单，可在不影响 P0/P1 的前提下延后 |

2. **当堂验证全通过**：§5 的 6 条 `TC-LIVE-*` 全部现场通过，证据文件齐全且含现场截图/串口行。
3. **第 1 周回归全绿**：`TC-W2-42` … `TC-W2-45`、`TC-W3-28` 全部通过，具体即
   `tools/selftest_backend.py` 退出码 0、`tools/verify_three_way.py` 判 `PASS`（三方逐点一致、不一致点数 0）、
   `tools/analyze_db_rate.py` 无短命 boot 告警、`tools/check_web_contract.py` 全项通过、

## 7. 模拟回执与备用路径的标注规则

### 7.1 `SIMULATED` 强制标注规则

   `evidence/w23_test_db_SIMULATED.db`，生产库只留真实设备产生的行。

### 7.2 共享设备轮换与设备锁（谁在用串口）

**事实约束**：整块板子只有一个 USB 串口（`COM5`）；`tools/serial_watch.py` 打开串口会让芯片**复位一次并重新枚举 USB**
（第 1 周已记录该现象与"开两次"规避策略）。因此同一时刻**只能有一个人**抓串口。

| 规则 | 内容 |
|---|---|
| **设备锁** | 抓串口前在共享位置（`evidence/device_lock.txt` 或课堂共享文档）写入：`使用者 / 时间段 / COM 口 / 用途 / 用例 ID`；离开时删除该行。文件里已有未过期的行 → 禁止抢占 |
| **排班** | 每轮 ≥30 分钟，按用例分组分配（如 09:00–09:30 `TC-W2-13/14`；09:30–10:00 `TC-W3-06/07/08`）；当堂验证时段（§5）**独占**，任何人不得抓串口 |
| **冲突处置** | 若 `serial_watch.py` 报"串口被占用/打不开"，即视为设备锁已被他人持有，**停止重试**并记录等待；不得用其它工具强行抢占 |
| **不抓串口的替代** | 需要长时间观测时用 `tools/analyze_db_rate.py`（只读数据库、不碰串口、**不复位板子**）；需要接口证据时用 `curl.exe`/`Invoke-RestMethod`（不碰串口） |
| **换人交接** | 交接时必须：① 断开自己的抓取进程；② 在设备锁里写清"当前 `boot_count`"与"已暂停/未暂停周期上报"；③ 确认板上 LED/蜂鸣处于已知状态 |
| **共用同一块板的副作用** | 他人抓串口会导致你正在进行的 `collect_now` 观测因复位而变成 `new_after_reboot`（甚至 `timeout`）→ 该次结果作废重做，并在证据中注明"因排班冲突复位" |
