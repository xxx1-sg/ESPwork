# 第 7 周：按需获取一张环境图像

> 一句话：**用户点一下，系统要么给他一张"请求之后真的拍到的"图，并说明是"哪一刻"的；
> 要么明确告诉他这次没拍到、为什么没拍到 —— 绝不给上一张。**

## 0. 结论先行（如实说明）

本周要求共 11 项，全部落地并有实测证据。但有几件事必须写在最前面：

| 项 | 结论 |
|---|---|
| 采集成功/失败有明确状态 | ✅ 7 个状态 + 终局不可改写，`snapshots` 列表与单个查询都能查到 |
| 不把旧图冒充本次结果 | ✅ 帧序号必须**严格大于**基线，否则 `400 SNAPSHOT_STALE_IMAGE`（真机实测拦截） |
| 超时/取消后到达的图要隔离 | ✅ 另存 `-late.jpg`，终局一个字段都不改（真机实测 `cancelled` 后到图 → 仍是 `cancelled`） |
| 失败/超时不得回退上一张 | ✅ 取图口 409，返回体是 JSON 错误、**不是** JPEG 字节 |
| 图像落盘且可复现 | ✅ `backend/data/snapshots/<dev>/<sid>.jpg` + SHA256，可直接下载比对 |
| 能回答"哪一刻的画面" | ✅ 请求 / 快门（估计）/ 到达 三个时刻分开存，前端同屏并列 |
| 区分真实/模拟/回放 | ✅ `counts_as_live` 只对"真机 + 本次 + 新帧 + 成功"为 1 |
| 提供模拟器或回放路径 | ✅ 协议级模拟设备（`--sim`）+ 回放历史照片两条路径 |
| 保留策略 | ✅ 按"天数 + 每设备最少保留"清理图像文件，**记录永不删** |
| 测试与文档 | ✅ 接口 150 项 / 前端 53 项 / 端到端 41（模拟）+ 39（真机） |
| 分支与提交 | ✅ `feature/week7-on-demand-snapshot` |

**必须如实说明的三点限制**（详见 §12）：

1. **快门时刻是估计值**，不是设备时钟。误差上界是"连接建立 + 首字节前的排队"，量级几十毫秒。
2. **测这段代码时，镜头前是暗的**（实测 `mean_luma` 16~24），所以截图里是"画面不可用"而不是一张好看的图。
   这不是程序问题，但也说明：**判据是对的，画面得由现场决定**。
3. **链路慢时会显著变慢**。QVGA 一张图 3KB，正常 1~4 秒；Wi-Fi 抖动时实测最慢端到端 18.4 秒。

## 2. 一次请求的完整状态机

```
                    POST /api/v1/cam/snapshot
                              │
                              ▼
                        ┌──────────┐   设备从未上传过帧
                        │ pending  │──────────────► failed
                        └────┬─────┘   (NO_FRAME_STREAM)
             下一帧的响应里带 id │
                              ▼
                        ┌───────────┐   25/35 秒没动静
                        │ requested │──────────────► timeout (DEVICE_SLOW)
                        └─────┬─────┘
        设备自报"开始取图" │           等太久用户点了取消
                              ▼                    │
                        ┌───────────┐               ▼
                        │ capturing │         ┌───────────┐
                        └─────┬─────┘         │ cancelled │
            上传图像（带 sid） │                └───────────┘
                    ┌─────────┴─────────┐          │
                    ▼                   ▼          │
              ┌──────────┐        ┌──────────┐     │
              │    ok    │        │ occluded │     │
              └──────────┘        └──────────┘     │
                    ▲                   ▲          │
                    └────── 终局之后到的图 ────────┘
                              （不改终局，另存 -late.jpg）
```

**红线：终态集合一旦命中，任何字段都不再被"更好的结果"改写。**
终态 = `ok / occluded / failed / timeout / cancelled / replayed`。

一个容易被忽略的点：`requested` 不是"设备收到了"，而是"服务端把 id 挂到了某一帧的响应上"。
所以**它是服务端可观测的事实，不是推断**——这也是为什么"已送达"这类措辞在本周只用于描述
"请求已下发"，绝不用于描述"图像已收到"。后者的唯一判据是 `captured_at_utc` 非空。

## 3. 三条红线，各自守在哪一行

### R1：陈旧帧拦截（不把旧图当本次结果）

```python
# backend/server.py  snapshot_accept_image()
seq  = meta.get("seq")
base = rec.get("baseline_seq") or rec.get("requested_seq")
if base is not None and seq is not None and seq <= base:
    resp = _error("SNAPSHOT_STALE_IMAGE",
                  "送回来的帧序号(%s)不比基准(%s)新 —— 这不是请求之后重新取到的画面"
                  % (seq, base), retryable=False)
    return HTTPStatus.BAD_REQUEST, resp
```

基线取**两个**序号里更晚的那个：

- `requested_seq`：登记请求那一刻设备最新的帧号 → 挡住"重发请求之前的旧图"；
- `baseline_seq`：**下发那一帧**的帧号 → 挡住"把下发那一帧本身原样交回来"。

只取前者是不够的：下发那一帧的 seq 恰好比 `requested_seq` 大 1，把它当结果交回来能蒙混过关。
这个坑是在冒烟测试里踩出来的（见 §11 D3）。

### R2：终局不改写，迟到图另存

```python
if rec["state"] not in _SNAP_OPEN:
    if rec["state"] in ("timeout", "cancelled"):
        rel, _ = _snap_save_file(rec["device_id"], sid, jpeg, suffix="-late")
        _snap_update(sid, late_at_utc=..., late_sha256=..., late_filename=rel)
        return HTTPStatus.OK, {"ok": True, "accepted": False, "late": True, ...}
    return HTTPStatus.CONFLICT, _error("SNAPSHOT_ALREADY_FINAL", ...)
```

- 超时/取消后到的图 → **收下**（证据不能丢），但标 `late`，`state` 不动；
- 已经 `ok`/`occluded` 后再来一张 → 409，**不许覆盖已确认的那一张**。

### R3：没有本次图像时，不回退到上一张

```python
# GET /api/v1/cam/snapshot/<sid>/image
if not rec["filename"]:
    return 409, _error("SNAPSHOT_NO_IMAGE",
                       "这次请求没有属于它的图像（%s）。系统不会拿上一次成功的画面顶替。" % state)
```

前端也守着同一条：`snapShowImage()` 只在 `has_image` 为真时才 `setAttribute("src", ...)`，
否则 **`removeAttribute("src")`** ——留着旧地址就等于把旧图当新图。

## 4. "哪一刻的画面"：三个时刻，两种精度

| 时刻 | 来源 | 精确性 |
|---|---|---|
| `requested_at_utc` | 后端收到 POST 的时间 | **精确** |
| `captured_at_utc` | 到达时刻 − 设备自报"取帧→开始发请求" − 服务端量到的"开始收 body→收完" | **估计**（`captured_is_est=1`） |
| `received_at_utc` | 后端收齐字节的时间 | **精确** |

```python
# snapshot_accept_image()
upload_ms = meta["upload_ms"]   # 设备自测：取帧 → 准备发请求
rx_ms     = meta["rx_ms"]       # 服务端自测：开始收 body → 收齐
captured  = recv - (upload_ms + rx_ms)
is_est    = 1                   # 恒为 1：设备没有与服务器对齐的时钟，这终究是推算值
```

**为什么两段都要减**：第一版只减了 `upload_ms`，而它只有 0~2 ms，
结果是 `captured == received`、`latency_capture == latency_total`（真机第一次跑就是 11513 ms == 11513 ms）。
这等于**把估计说成了精确**。加上服务端量到的 `rx_ms` 之后，真机实测变成
快门 `06:58:38.068Z` / 到达 `06:58:38.156Z`，差 88 ms —— 这才是"图像在路上"的真实样子。

**误差上界**：连接建立 + 首字节之前的排队，量级几十毫秒（QVGA）/ 数百毫秒（弱网）。
`rx_ms` 会一起入库，任何一条记录都能**重新算一遍**快门时刻。

## 5. 判断"到底拍到没拍到"：从字节里量，不猜

`backend/img_quality.py`，**纯标准库**，不依赖 Pillow：

1. 解 baseline JPEG 的段表，找到 `SOF0` 与 `DHT`；
2. 用霍夫曼表解出每个 MCU 的 **DC 系数**（跳过 IDCT，不算像素也能拿到块的平均亮度）；
3. 采样部分 MCU（默认 600 个，约 4% 行数）算出 `mean_luma` / `luma_std` / `dark_ratio`。

```python
DARK_LUMA_MAX  = 28.0   # 平均亮度低于它 → 太暗
FLAT_STD_MAX   = 10.0   # 标准差低于它 → 太平
VERY_FLAT_STD  = 3.0    # 极平（纯色）→ 直接判遮挡
```

判定结果三档：`occluded` / `usable` / `unknown`（解析失败时**不猜**，如实返回 unknown）。

实测数字（都可复算）：

| 样本 | mean_luma | luma_std | dark_ratio | 判定 |
|---|---|---|---|---|
| 第 4 周真机照片（1600×1200 白天） | 144.49 | 63.63 | — | usable |
| 合成"纯黑平图" | 18.00 | 0.00 | 1.000 | occluded |
| 真机（镜头前偏暗，实测 4 条） | 17.96~22.30 | 3.77~5.28 | ≈1.0 | occluded |
| 真机（可用，实测 4 条） | 42.19~55.97 | 12.83~16.67 | 0.11~0.24 | usable |

耗时：**15.6 ms/张**（600 MCU 采样）。

`occluded` 不等于"失败"：图**照样存、照样能取**（`S4.5` 已断言），
只是结论写成"这次没看到环境"。这是"不可用"和"没拍到"的区分。

## 6. `counts_as_live`：三个口径绝不合并

| 来源 | `simulated` | `is_replay` | `counts_as_live` | 含义 |
|---|---|---|---|---|
| 真机拍到且可用 | 0 | 0 | **1** | 真的看到了环境 |
| 真机拍到但暗/平 | 0 | 0 | **1** | 真的拍到了，但画面不可用 |
| 协议模拟器 | 1 | 0 | **0** | 链路通了，但不是这台机器拍的 |
| 回放历史照片 | 0 | 1 | **0** | 当年那一刻的画面，不是现在 |

汇总接口 `GET /api/v1/cam/snapshot/summary` **分开返回**：

```json
{"live_ok": 2, "live_occluded": 4, "simulated": 7, "replayed": 9,
 "last_live_ok": {...}, "by_state": {"ok":13,"occluded":6,"timeout":7,...}}
```

合成一个"成功次数"就再也回答不了本周那个问题 —— 所以它压根没被合成。

`last_live_ok` 只认 `counts_as_live=1 && state=ok`：回放和模拟**不会**顶掉"最近一次真正可用采集"。
（`S5.5` 就是钉这条：回放前后 `last_live_ok` 必须一模一样。）

## 7. 设备在 NAT 后面，请求怎么送进去

设备不能听端口，只能主动出站。所以请求**搭便车**：

```
设备 POST /api/v1/cam/frame  ──►  后端  ┌ 顺手检查有没有待下发的快照请求
                                        └ 有就塞进这一条响应：{"snapshot_id": "...", "snapshot_mode": "qvga"}
设备读响应 → 发现 snapshot_id → 取一帧新图 → POST /api/v1/cam/snapshot/upload?sid=...
```

### 7.1 at-least-once（不是"恰好一次"）

第一版是"挂上一次就摘掉"。真机实测会丢包（`ESP_ERR_HTTP_CONNECT` / HTTP -1），
那一帧的响应没到设备，请求就**凭空消失**，前端只能看到"采集超时"——把链路抖动说成了设备问题。

改成：**只要设备还没确认（状态仍是 `pending`/`requested`），每一帧都带同一个 id**。
设备侧按 id 去重（`s_snap_last_sid`），所以不会连拍。

```c
// firmware/src/camera.c
if (!s_snap_pending && strcmp(sid, s_snap_last_sid) != 0) {   // ← 去重
    snprintf(s_snap_sid, sizeof(s_snap_sid), "%s", sid);
    snprintf(s_snap_last_sid, sizeof(s_snap_last_sid), "%s", sid);
    s_snap_pending = true;
}
```

状态一离开 `pending`/`requested`（设备 `begin` / 上传 / 失败 / 超时 / 取消），队列条目自动清掉，
不会无限重发。接口自检 `C7b` / `C13b` 分别钉住"重发"和"收尾后不再发"。

### 7.2 为什么默认 QVGA

用户要的是"现在环境长什么样"，不是一张存档原图。
QVGA 取帧 + 上传只要 0.1~0.5 秒；UXGA 需要**重建相机**（第 4 周实测 8.7 秒），
只在后端显式要求 `mode=uxga` 时才走。

## 8. 保留策略：只删文件，记录永不删

```python
snapshot_prune(device_id=None, dry_run=False, keep_min=10, days=7)
```

三条不可动摇：

1. **只删图像文件**，`cam_snapshots` 一行都不删 —— "某天某人请求过并失败了"这个事实比一张过期的图重要；
2. 每台设备最近 `keep_min`（默认 10）张**带图**的快照无论如何保留；
3. 只删超过保留期（默认 7 天）的；`dry_run=1` 时**只报告**，`bytes_freed` 恒为 0。

删除后把 `image_pruned=1` 写进记录，`has_image` 随之为 false，
`/image` 返回 409 并说明"图像已按保留策略清理，记录仍在"。

参数可用环境变量覆盖：`SENSOR_SNAPSHOT_TIMEOUT_S` / `SENSOR_SNAPSHOT_KEEP_MIN` /
`SENSOR_SNAPSHOT_RETENTION_DAYS` / `SENSOR_SNAPSHOT_DIR`。

## 11. 踩坑记录（全部真实发生，附修法）

### D1：`json_find_str` 不认冒号后的空格 → 板子"像没收到"

设备侧手写 JSON 提取，模式写的是 `"snapshot_id":"`。
后端是 Python `json.dumps`，输出的是 `"snapshot_id": ""`（**冒号后带空格**）。
于是：后端日志明明写了"已下发"，后端库里 `delivered_at_utc` 也有值，
但设备一次 `/snapshot/begin` 都没打，25 秒后超时 —— **固件不报任何错**。

第 4 周的 `"capture": true` 之所以没暴露，是因为那里手写了两个 `strstr` 变体。
修法：解析器里统一容忍可选空白，并且在 `uploader` 响应缓冲从 192 加到 384 字节
（实测这条响应 184 字节，只差 8 字节余量，多一个字段就会把 id 截成半截）。

判据：`grep -a -o -F "snapshot/upload?sid=" firmware.elf | wc -l` → 1（分支确实编进去了），
但**"编进去了"不等于"跑到了"** —— 必须看串口有没有 `后端请求按需快照: snp_...`。

### D2：Wi-Fi 省电让下行延迟 8~13 秒

设备默认 `WIFI_PS_MIN_MODEM`：射频睡到下一个 DTIM 才醒。
实测预览帧出现 11 秒断流（`06:40:58 → 06:41:10`），请求只能等下一帧搭车，
于是"登记 → 下发"用了 **8.1 秒 / 13.1 秒**。

修法：`esp_wifi_set_ps(WIFI_PS_NONE)`。改完同样的三次请求变成 **230 / 31 / 297 ms**。

### D3：一次投递 = 一次丢失机会

见 §7.1。修法：未确认期间每帧重发 + 设备按 id 去重。

### D4：把"估计"写成"精确"

见 §4。首次真机数据 `latency_capture == latency_total == 11513`，
看着很"精确"，实际是 `upload_ms≈0` 造成的假精确。修法：加 `rx_ms` 并恒标 `captured_is_est=1`。

### D5：断言把"正常结果"当失败

- 探针 `S1.3` 写死 `state == "ok"`，但镜头前是暗的，返回 `occluded` —— 这不是失败。
  改成 `in ("ok","occluded")`。
- `S6.2` 写死 `live_ok == 0`（以为库里只有本轮数据），但库里已有真机记录。
  改成"以本轮开始前的计数为基准"。
- 固件 `APP_CAM_SNAPSHOT_ENABLE` 加了 `#ifndef → #error` 兜底：开关宏缺失时
  `#if` 会按 0 处理、分支被**静默编译掉**（第 3 周 D7 的同一个坑），现在留在编译期报错。

## 12. 限制与如实说明

1. **快门时刻是估计值**。设备没有与服务器对齐的时钟，`captured_at_utc` 由
   `到达 − upload_ms − rx_ms` 推算，误差上界是连接建立与首字节前排队（几十毫秒量级）。
   `captured_is_est` 恒为 1，UI 上也一直显示"（估计）"。
2. **occluded 是"画面不可用"，不是"没拍到"**。判据只看亮度与平坦度：
   对着白墙、镜头盖、全黑房间都会判 occluded。它保证的是"不会把没信息的画面说成看到了环境"，
   而不是"准确识别遮挡物"。
3. **链路慢就是慢**。3KB 的 QVGA 图在弱网下实测要 6.4 秒才传完。
   这不是优化能解决的，所以超时窗口按实测分布定成 35 秒，并在文档里写清楚依据。
4. **本轮截图里的画面是暗的**（`mean_luma` 16~24），因为拍摄时镜头前没有可看的场景。
   面板、时刻、判据都是真实数据；要一张好看的图，需要现场有光。
5. **UXGA 快照仍会中断预览约 9 秒**（第 4 周既有结论，未改），因为必须重建相机才能拿到大分辨率缓冲。

## 14. 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/cam/snapshot` | 登记一次按需采集（`device_id`/`mode`/`trigger`/`reason`），202 |
| POST | `/api/v1/cam/snapshot/begin` | 设备自报开始取图（best-effort） |
| POST | `/api/v1/cam/snapshot/fail` | 设备明确回报取图失败 |
| POST | `/api/v1/cam/snapshot/upload?sid=&device_id=&seq=&w=&h=&upload_ms=&uptime_ms=` | body=原始 JPEG |
| POST | `/api/v1/cam/snapshot/<sid>/cancel` | 取消（终局，之后到的图只记迟到） |
| POST | `/api/v1/cam/snapshot/replay` | 回放历史照片，`state=replayed`，`counts_as_live=0` |
| POST | `/api/v1/cam/snapshot/prune` | 按保留策略清理图像文件（支持 `dry_run`） |
| GET | `/api/v1/cam/snapshots?limit=&device_id=` | 历史列表 |
| GET | `/api/v1/cam/snapshot/summary` | 三口径汇总 + 保留参数 |
| GET | `/api/v1/cam/snapshot/<sid>` | 单条（含 `explain` 一句人话） |
| GET | `/api/v1/cam/snapshot/<sid>/image` | 本次图像；没有就 409 |
| GET | `/api/v1/cam/snapshot/<sid>/image?late=1` | 迟到图像 |

设备侧上传需要 `X-Device-Token`；`sim=1` 表示协议模拟器。
