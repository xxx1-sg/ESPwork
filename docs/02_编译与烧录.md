# 02 · 编译与烧录

本工程是标准的 **PlatformIO + ESP-IDF** 项目（`framework = espidf`），
也可以直接当作 ESP-IDF 工程用 `idf.py` 编译。

---

## 1. 烧录前必须改的配置

打开 `firmware/src/app_config.h`，按你的环境改这几处：

```c
// ① 联网（主用 + 备用热点，主用连不上会自动切）
#define APP_WIFI_SSID       "YOUR_WIFI_SSID"        // ← 你的 Wi-Fi 名称（必须 2.4GHz）
#define APP_WIFI_PASSWORD   "YOUR_WIFI_PASSWORD"    // ← Wi-Fi 密码
#define APP_WIFI_FALLBACK_SSID     "YOUR_FALLBACK_SSID"       // ← 备用热点（可留成同一个）
#define APP_WIFI_FALLBACK_PASSWORD "YOUR_FALLBACK_PASSWORD"

// ② 后端上传接口
//    同网段直连（当前用的这条，板子与后端在同一可路由网络里，RTT ~50ms）：
#define APP_SERVER_URL      "http://10.1.41.182:8000/api/v1/ingest"
//    VPS / 内网穿透（https:// 开头会自动启用真实 TLS 校验）：
// #define APP_SERVER_URL   "https://你的域名/api/v1/ingest"
#define APP_DEVICE_TOKEN    "CHANGE_ME_DEVICE_TOKEN"       // ← 与后端 SENSOR_TOKEN 一致

// ③ 采集密度（默认就是 10Hz 采样、1 秒一个包）
#define APP_SAMPLE_PERIOD_MS  100    // 采样周期：100ms 一个点
#define APP_BATCH_SIZE        10     // 一包几个点（必须 = 上传周期 / 采样周期）
#define APP_UPLOAD_PERIOD_MS  1000   // 上传周期：1 秒发一次包
#define APP_MAX_MERGE         30     // 网络慢时最多合并几个包成一次请求
```

> `app_config.h` 里对这 4 个参数有 `_Static_assert` 自检：`APP_BATCH_SIZE` 与
> `APP_UPLOAD_PERIOD_MS / APP_SAMPLE_PERIOD_MS` 不一致时**编译期就会报错**，
> 避免"以为改了采样率其实没生效"这种坑。

> ESP32-S3 **只支持 2.4GHz** Wi-Fi。手机热点若开了「5GHz 优先」，请切到 2.4GHz，
> 否则日志会一直出现 `Wi-Fi 断开 (reason=201)`（201 = 找不到 AP）。

## 2. 安装工具链（本机已按此方式装好，可复现）

本机没有预装 ESP-IDF，且系统 Python 为 3.14，采用 **PlatformIO（纯 pip 包）** 最省事：

```powershell
# 1) 建一个工程内虚拟环境（不污染系统）
python -m venv D:\ESP\.venv

# 2) 安装 PlatformIO（本机把包直接装进 venv 的 site-packages）
python -m pip install --no-cache-dir --target D:\ESP\.venv\Lib\site-packages platformio

# 3) 验证
D:\ESP\.venv\Scripts\python.exe -m platformio --version
#   PlatformIO Core, version 6.2.0
```

### ⚠️ 本机遇到的两个坑（已解决，换机器可能也会遇到）

1. **`tempfile.mkdtemp` 建的目录不可写**
   Python 3.13+ 在 Windows 上会把 `os.mkdir(path, mode)` 真的翻译成 ACL，
   而 `mkdtemp` 用的是 `mode=0o700`，本机策略下这种目录随后完全不可访问，
   导致 pip 解包 / venv(ensurepip) 全部报 `PermissionError: [Errno 13]`。
   解决：`D:\ESP\.pylibs\sitecustomize.py` 里把 mkdir 的 mode 统一放宽为 `0o777`，
   并把该目录放进 `PYTHONPATH`（Python 启动时会自动 import `sitecustomize`）。
2. **`pip install esptool` 在 Python 3.14 下要现场编译而失败**
   不需要它 —— PlatformIO 自带 `tool-esptoolpy` 用于烧录。

### 环境变量（每次调用 pio 都要有）

```powershell
$env:PLATFORMIO_CORE_DIR = 'D:\ESP\.platformio'   # 让平台/工具链都装在工程目录里
$env:TMP  = 'D:\ESP\.tmp'
$env:TEMP = 'D:\ESP\.tmp'
```

## 3. 编译

```powershell
cd D:\ESP\firmware
D:\ESP\.venv\Scripts\python.exe -m platformio run
```

首次编译会自动下载 `espressif32` 平台 + xtensa 工具链（约 200~400MB），
之后再编译只需十几秒。成功时最后几行类似：

```

Flash: [==        ]  18.6% (used 389737 bytes from 2097152 bytes)
========================= [SUCCESS] Took 42.31 seconds =========================
```

## 4. 烧录（USB 仅作调试通道）

```powershell
# 确认串口（本机为 COM5，已写进 platformio.ini）
[System.IO.Ports.SerialPort]::GetPortNames()

cd D:\ESP\firmware
D:\ESP\.venv\Scripts\python.exe -m platformio run -t upload
```

只要 `platformio.ini` 里的 `upload_port = COM5` 与实际一致即可；
若插到别的口，改成对应 COM 号，或加 `--upload-port COMx`。

## 5. 看串口日志（硬件实测值）

```powershell
D:\ESP\.venv\Scripts\python.exe -m platformio device monitor
# 或直接用本仓库脚本把日志同时存盘（做证据用）：
python D:\ESP\tools\serial_watch.py --port COM5 --seconds 120 --out D:\ESP\evidence\serial_run.log
# 只想看核对用的关键行：
python D:\ESP\tools\serial_watch.py --port COM5 --seconds 30 --only-data
```

> ⚠️ 打开 USB-Serial-JTAG 串口会让 ESP32-S3 复位一次，USB 随之重新枚举，
> 刚打开的句柄会立刻失效（表现为 `ClearCommError failed (PermissionError(13, …))`，
> 且读不到任何数据）。`serial_watch.py` 用「第一次打开触发复位、第二次打开稳定读取」
> 的策略规避这个问题，并把**复位原因**记进日志，便于区分"人为复位"和"板子自己重启/掉电"。

正常运行时每秒一行，格式如下（这就是「三方核对」的第一方证据）：

```
I (15320) main: [DATA] dev=esp32s3eye-XXXXXX boot=3 seq=12 up=15320ms \
    ts=2026-06-05T13:04:05.123+0800 raw=(1234,-56,8190) \
    g=(0.301,-0.014,1.999) ms2=(2.95,-0.13,19.61) |a|=2.022g
I (15430) main: [POST] seq=12 http=201 resp={"ok":true,"id":12,...}
```

- `raw=(...)` = 芯片寄存器里的 14 位原始码值
- `g=(...)` = 换算后的重力倍数
- `ms2=(...)` = 国际单位制加速度
- `|a|` = 合矢量，静止时应 ≈ 1.000g
- `[POST]` 行的 `resp` 是**后端把数据存进数据库后回读的内容**，
  因此这一行本身就同时包含「板端实测」与「服务器已存」两方信息，可直接对照。

## 6. 常见问题

| 现象 | 原因与处理 |
|---|---|
| 串口完全没有输出 | 数据线插在了 UART 口而不是原生 USB 口；本项目控制台固定在 USB-Serial-JTAG |
| `CHIP_ID=0x00` 或 `读取 CHIP_ID 失败` | 传感器没上电/总线异常；确认是 ESP32-S3-EYE 且 I2C 未被其它任务占用 |
| 一直 `Wi-Fi 断开 (reason=201)` | SSID 写错，或热点是 5GHz（ESP32-S3 不支持） |
| `reason=15` | Wi-Fi 密码错误 |
| 上传 401 | `APP_DEVICE_TOKEN` 与后端 `SENSOR_TOKEN` 不一致 |
| 上传失败但网络正常 | 后端地址错、防火墙没放行、或用了 https 但域名证书不被信任 |
| 编译报 `i2c_master.h: No such file` | ESP-IDF 版本 < 5.2；源码里已有 legacy I2C 分支，检查 `ESP_IDF_VERSION` 是否正确 |
| 想改上传频率 | `app_config.h` 的 `APP_UPLOAD_PERIOD_MS`（默认 1000ms） |
| 想改数据密度 | `APP_SAMPLE_PERIOD_MS`（默认 100ms = 10Hz）。改完记得同步 `APP_BATCH_SIZE`，否则 `_Static_assert` 会直接编译报错 |
| 板子反复重启、串口出现 `Guru Meditation … LoadProhibited` | 固件跑飞（多半是数组越界/内存踩踏）。用调用栈定位：<br>`D:\ESP\.platformio\packages\toolchain-riscv32-esp\bin\riscv32-esp-elf-addr2line.exe -pfiaC -e firmware\.pio\build\esp32s3eye\firmware.elf <地址1> <地址2>` |
| 采集看起来"卡住"了几十秒 | 单循环固件里上传会阻塞采样。本工程已拆成 `sampler_task`+`uploader_task` 两个任务；若仍出现，用 `python tools\analyze_db_rate.py --minutes 10` 看真实缺口与 boot 时长 |

## 7. 用官方 ESP-IDF 编译（可选）

工程根目录的 `CMakeLists.txt` / `src/CMakeLists.txt` 就是标准 IDF 结构，装好官方 ESP-IDF 后：

```bash
cd firmware
idf.py set-target esp32s3
idf.py build
idf.py -p COM5 flash monitor
```
