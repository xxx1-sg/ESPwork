## 0. 一句话概括

第 2 周解决的是「**我点了采集，怎么证明设备真的采了一次**」；
第 3 周解决的是「**我按了求助键，怎么证明对方真的知道了**」。

两者的骨架完全同构 —— 都是「**本地动作 → 上传/下发 → 对端确认 → 才允许声称成功**」，
而第 3 周多了一条更硬的约束：**本地反馈必须脱离外网独立成立**（断网也得响、也得亮）。

## 1. 硬件清单与接线（W3-T5）

| 项目 | 选型 | 引脚 | 说明 |
|---|---|---|---|
| 实体按键（**实体输入**，必做） | ESP32-S3-EYE **板载 BOOT 键** | **GPIO0** | 按下为低电平，内部上拉；**无需任何外接线** |
| 指示灯 LED（实体输出） | 5mm 红色 LED + 220Ω~1kΩ 限流电阻 | **GPIO2** | GPIO → 电阻 → LED → GND |
| 蜂鸣器（实体输出） | 3.3V **有源**蜂鸣器 + NPN 三极管（S8050）驱动 | **GPIO3** | GPIO → 1kΩ → 基极；蜂鸣器接集电极；**不可直接挂 GPIO** |
| 板载传感器（第 1 周沿用） | QMA6100P 三轴加速度计 | SDA=**GPIO4** / SCL=**GPIO5** | 板载，无需接线 |
| 板载 LCD（**第 3 周补充**） | ST7789 **240×240** 彩色屏 | SCLK=**21** / MOSI=**47** / CS=**44** / DC=**43** / 背光=**48**（RST 未接，走软复位） | 板载，走 **SPI3**；★ **背光低电平点亮**（官方 BSP 口径），无需外接线 |

**引脚选择理由（写进 `app_config.h` 的编译期断言，占错引脚直接编译失败）**：

| 禁用引脚 | 原因 |
|---|---|
| GPIO19 / GPIO20 | 原生 USB D-/D+，是本工程**唯一的串口日志与烧录通道**（`CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`），占用后日志全丢 |
| GPIO26 ~ GPIO37 | N8R8 模组的 flash / PSRAM 占用 |
| GPIO4 / GPIO5 | 板载 QMA6100P 的 I2C 总线 |

> 器件**可用性如实上报**：若蜂鸣器配置失败，`local_feedback` 只会是 `led`，
> **绝不**在没接蜂鸣器时谎报 `buzzer+led`（`TC-W3-04(d)` 的落点，见 §6 走查项 W3-04）。

## 2. 三个概念的差别（W3-T2，本周核心理论点）

第 3 周最容易混为一谈的就是这三件事。它们的**发生位置、是否依赖外网、证据字段**全都不同：

| # | 概念 | 发生位置 | 依赖外网 | 证据字段 | 能证明什么 | **不能**证明什么 |
|---|---|---|---|---|---|---|
| ① | **本地确认** | 佩戴者设备（GPIO） | **否** | 串口 `[HELP] … local feedback done`；蜂鸣声 + LED 物理现象 | 佩戴者**确实按下了键**，且本机已知晓 | 任何与"远端"有关的事 |
| ② | **VPS 接收** | 设备 → 后端 | 是 | `help_events.received_at_utc`、`local_feedback_received_at_utc` | 事件**已到服务器**，查看者列表能看到 | 有人看过、有人回应过 |
| ③ | **查看者回应** | 查看者 → 后端 | 是 | `help_actions(action='responded')`、`responded_at_utc` | 有人**声明**他看到了 | **设备是否知道** —— 回应只是服务端事件 |
| ④ | **设备确认** | 后端 → 设备（`help_ack`）→ 设备回执 | 是 | `help_events.remote_acked_at_utc` | 佩戴者设备**真的收到了**回应 | —— |

### 2.1 由此推出的两条硬规则

**规则一：本地反馈不得依赖外网。**
按键识别与蜂鸣/LED 的整条路径**不调用任何网络函数**，上传是"之后尽力而为"的动作。
拔掉外网后按下按键，蜂鸣与 LED **仍然发生**（当堂验证第 1 项）。

**规则二：无远端回执不得声称已收到。**
`remote_acked_at_utc` 是"已送达"的**唯一**依据，它**只有**一条写入路径：
设备轮询取走 `help_ack` 指令 → 设备 `POST /api/v1/device/ack`（`ack_type=help_ack`）。
因此下面两种情形都**不允许**显示"对方已收到"：

- 仅本地反馈发生（事件甚至还没上传）→ 只能显示「佩戴者已按键（待回应）」；
- `status=responded` 但设备未 ack → 只能显示「我已回应，等待设备确认」。

> **"入队 ≠ 送达"**：后端把 `help_ack` 排进 `pending_commands` 只是"准备告诉设备"，
> 设备处于 NAT 后、只能自己轮询来取 —— 指令躺在队列里没人取，等于没送达。

### 2.2 五个时间字段的口径（不可混用）

| 字段 | 来源 | 格式 | 可为 NULL | 可比范围 | 用途 |
|---|---|---|---|---|---|
| `trigger_at_utc` | 设备侧（已 SNTP） | `…+0800` | 是 | 墙上时钟 | 佩戴者真实触发时刻 |
| `trigger_up_ms` | 设备侧 `esp_timer` | 整数 ms | 否 | **仅同 boot_count 内** | 断网时唯一可靠时间；算本地反馈时延 |
| `queued_at_utc` | 设备侧首次尝试上传 | `…+0800` | 是 | 墙上时钟 | 算断网滞留的真实时长 |
| `local_feedback_at_utc` | 设备侧反馈**实际发生**时刻 | `…+0800` | 是 | 墙上时钟 | 证明本地反馈已发生 |
| `local_feedback_received_at_utc` | **服务端**收到时刻 | `…Z` | **否**（永远非空） | 墙上时钟 | 服务端口径与未对时兜底 |

**硬性纪律**：① 两组字段**不得互相替代**；② **禁止**用 `trigger_up_ms` 减任何 `*_at_utc`
（单调时钟 ≠ 墙上时钟，跨重启更不可比）；③ 未对时时墙上时钟字段一律 `null`，
**不得**用服务端时间或"恢复联网时刻"顶替。

## 4. 取消逻辑的定义（W3-T4）

| 编号 | 规则 | 实现落点 | 用例 |
|---|---|---|---|
| **C1** | 取消**只有佩戴者侧**可发起（教学环境以操作者声明为准，记 `actor`） | `cancel_help_event()` 记录 `actor` 到 `help_actions.actor` | `TC-W3-23` |
| **C2** | 取消**可在任何非终态**发起：`created/uploaded/acked/viewed/responded` → `cancelled` | `if row["status"] in HELP_FINAL_STATUSES:` 才走幂等分支，否则一律可取消 | `TC-W3-21` |
| **C3** | 取消**不删除**任何记录（`help_events` 与 `help_actions` 全留痕），`cancel_reason` **必填** | 缺 `reason` → `400 MISSING_FIELD` 且**不改写状态**；全程只有 `UPDATE`/`INSERT`，**没有** `DELETE` | `TC-W3-23` |
| **C4** | 已经完全结束的求助再次取消 → `200` + `deduplicated:true`（幂等，不报错） | 终态分支直接返回原 `cancelled_at_utc`，时间戳逐字符不变、不新增动作行 | `TC-W3-22` |

**补充设计决定（本周新增，写在实现注释里）**：

- 取消时会 `DELETE FROM pending_commands WHERE request_id=? AND type='help_ack'` —— 
  否则会出现"求助已取消、但设备随后取到 help_ack，灯又变绿"的矛盾现象。
  注意这条 `DELETE` 删的是**待下发指令**，不是业务记录，与 C3 不冲突。
- 取消**不是**终态的"删除"，取消后再次按键会生成**新的** `help_id`，
  旧事件不会被复活（`TC-W3-25(f)`）。

### 5.4 板载 LCD 状态屏（第 3 周补充，源起于"屏不亮"的现场反馈）

**诊断（先定性，再动手）**：工程里**一行 LCD 代码都没有** —— 只有两处注释说"LCD 走 SPI"。
所以屏不亮**不是硬件损坏，而是固件从未初始化过这块屏、也从未驱动过背光**。
这属于第 1 周相机抽屉同一类的"**未接入**"，而不是"坏了"。

**引脚一律取官方 BSP，绝不臆测**（`esp-bsp/bsp/esp32_s3_eye`）：

| 信号 | GPIO | 说明 |
|---|---|---|
| SCLK | **21** | SPI3 时钟（官方 `BSP_LCD_PCLK`） |
| MOSI / DATA0 | **47** | 单数据线（官方 `BSP_LCD_DATA0`） |
| CS | **44** | 片选 |
| DC | **43** | 数据/命令 |
| RST | **未连接** | 官方 `BSP_LCD_RST` 为负值，走软复位 |
| **背光 BL** | **48** | ★ **低电平点亮** |

> 网上另有"`19/20/45/47/48`"一套引脚，那是**别人改自定义板子**的，且撞了原生 USB 引脚
> （GPIO19/20 是本工程唯一的日志/烧录通道）。**凡是引脚，只认官方 BSP。**

**★ 最容易踩的坑：这块板的背光是低电平点亮。**
官方 BSP 里 `brightness=100%` 对应的 LEDC `duty=0` → **把 GPIO48 拉高反而是"灭"**。
`lcd_status.c` 因此有 `APP_LCD_BL_ACTIVE_LOW=1`，并在初始化期间先置"灭"避免上电花屏。

**设计取舍（写下来免得下次纠结）**：
1. **不引入 LVGL**：四个状态只需"整屏底色 + 一个几何符号"，用 `esp_lcd` 的 `draw_bitmap`
   **分带刷屏**（每次 16 行 = 7680 字节，DMA 内存即可）就够，省掉一整套 GUI 依赖与整屏缓冲。
2. **不做文字**：写字要字库。用「颜色 + 符号」达到"一眼可辨"：待机=暗底空心环、
   等待=琥珀底感叹号、已送达=绿底对勾、取消=灰底叉。
3. **失败不致命**：SPI/面板任一步失败只打日志并把模块置为不可用，**返回 `ESP_OK`**；
   按键/蜂鸣/LED/上传完全不受影响 —— 屏幕是"补充输出"，不是求助链路的组成部分。

**★ 红线不变**：屏幕显示"已送达"的唯一来源仍是 `feedback_on_help_ack()`
（即 `cmd_client` 收到 `help_ack` 下行指令那一条路径）。屏幕**不做任何本地计时器推断**，
它只是把**同一份状态换个介质**显示出来。

**状态落点（`feedback.c` 四处）**：

| 触发 | 屏幕画面 |
|---|---|
| `feedback_start()` | 初始化 → 自检圆环 → 待机暗底环 |
| `feedback_fire_once()`（按键） | 琥珀 **！**（等待远端回应） |
| `feedback_on_help_ack()`（收到回执） | 绿 **✓** —— **同 LED"已送达"** |
| `feedback_on_clear_alert()`（查看者取消） | 灰 **✗**，**限时 2 秒**后自动回待机 |

> 取消画面用 `lcd_status_set_scene_timed(scene, 2000)` 实现：板端状态机如实只有
> IDLE/WAITING/DELIVERED 三态（取消是查看者侧动作，板端收到 `clear_alert` 就回 IDLE），
> 让屏亮 2 秒灰叉再回待机，是为了让用户**看得见"这次被取消了"**，
> 与 LED 熄灭、蜂鸣停止在时序上一致 —— 而不是伪造一个并不存在的板端状态。

**编译与验证（本次实测，中间翻过一次车）**：

- **第一版翻车**：`platformio run` → `EXIT=0`，`src/lcd_status.c.o` 也生成了，
  **但上电后屏全黑**。根因是条件编译写错（详见 §6.2 **D7**）：求值 `#if APP_LCD_ENABLE` 时
  该宏还没被包含进来，未定义标识符按 0 处理 → **整份 LCD 代码被静默编译掉**。
  ⇒ **"编译通过 + 有 `.o` 文件"根本证明不了功能分支被编进去。**

### 5.5 背光仍不亮：原理图级排查（2026-10-10 追加，**未关闭**）

修好 D7 之后，串口每一项都报 OK，**但用户现场反馈屏幕依旧全黑、没有任何背光**（按 RST 时那束绿光经确认是**板载 LED（GPIO3）**，与屏幕无关）。于是把排查推到**原理图级**，逐条排除软件侧嫌疑。

**① 硬件拓扑（官方原理图，已下载留档 `evidence/sub_sch.pdf`）**

- 这块板的 LCD **不在主板上**，而在**子板 ESP32-S3-EYE-SUB** 上；主板与子板通过 **2×5 排针（J8 / J9）**连接，**面板再经 12P FPC（J5）**接子板。
  - J8 恰好就是那 5 根 LCD 信号：`IO48 / IO47 / IO44 / IO21 / IO43`。
  - 已交叉核对**主板 MB V2.2** 原理图（用户实机丝印 `ESP32-S3-EYE-MB V2.2` / `…-SUB V1.1`）：
    `IO48 → J9 第 2 脚`，`IO47/IO44/IO21/IO43 → J9 第 4/6/8/10 脚`，与子板逐脚对应，
    **主板这一侧没有接错**。
- **面板 FPC（J5，型号 `FFC12-0P5-LCD`）引脚定义**：
  `1 GND / 2 LED_K / 3 LED_A / 4 VDD / 5 GND / 6 GND / 7 RS(DC) / 8 CS / 9 SCK / 10 SDA / 11 RESET / 12 GND`。
  ★ 注意：**背光 LED 在面板内部**，其电流要经这根 FPC 出去再回来 ——
  所以"FPC 没插好"会**同时**表现为**没有背光 + 没有画面**，与现场现象高度一致。
- **背光链路**：`IO48` → `Q2`（**AO3401A，P-MOSFET**）→ 面板 `LED_K`；门极**低电平导通** ⇒ **低电平点亮**。这与官方 BSP 的 `duty = 1023*(100-brightness)/100`（满亮 → `duty=0`）**互相印证**，说明"低电平点亮"不是猜的。
- `LCD_RST` 由**板上上拉**（测试点 TP1，丝印注明 `0=Reset / 1=Normal`），**不由 MCU 驱动** —— 与 `BSP_LCD_RST = NC` 一致。

**② 软件侧逐项排除（都已核对，无一可疑）**

| 检查项 | 结论 |
|---|---|
| 引脚 21 / 47 / 44 / 43 / 48 | 与官方 BSP 逐字段一致 |
| 背光极性 | `APP_LCD_BL_ACTIVE_LOW=1`，与原理图 P-MOSFET 低电平导通一致 |
| 初始化时序 | `reset → init → invert_color → swap_xy(false) → mirror(false,false) → disp_on_off(true)`，与官方 BSP 同序 |
| `gpio_config(GPIO48, OUTPUT)` | 返回成功（失败会打印"背光 GPIO 配置失败"；实测**没有**该行） |
| 实际驱动电平 | 上电后 `bl_write(true)` 会把 GPIO48 **持续拉低**；两段式诊断又各强制 8 秒"低/高" ⇒ **两种电平都试过了** |
| GPIO48 是否被别的外设占用 | 对 `sdkconfig.esp32s3eye` 全量检索：除 SOC 量程常量外**无任何外设占用** |

⇒ **软件侧已经把能做的做到头**：GPIO48 确实被配置为输出、并被驱动到两种电平，而屏幕始终无背光。

**③ 剩余原因只可能在物理层**（按可能性排序，**需现场确认**）

1. **主板 ↔ 子板 2×5 排针未插到位**（子板拿不到 3V3 → 背光与画面同时全无，与现象**完全吻合**）；
2. **面板 12P FPC（J5）未插紧 / 装反 / 折伤**；
3. 手上是**只有主板（MB）**的版本，或子板 / 面板本身故障；
4. **非官方复刻板**（背光脚不同）——若是这种，只需改 `app_config.h` 的 `APP_LCD_BL_GPIO`，**代码结构不用动**。

**④ ★ 第二轮排查：发现上一版诊断本身有缺陷（D8）**

第二版把自检改成**满屏纯色扫描**（阶段A 白→红、阶段B 绿→蓝），原因是上一版诊断
**方法论上就无效**：它只切换背光电平，画面却一直是"近黑待机"（`RGB(12,16,32)`），
于是"**背光亮着但显示近黑**"与"**背光全灭**"在肉眼上**无法区分**——
用户无论如何都只会看到"黑的"，判据根本立不住。
> **教训：诊断的"输出量"必须与"待测物理量"在可观测性上匹配。**
> 要判"屏亮没亮"，就得让屏上出现**饱和度拉满的大色块**，而不是一个本来就接近黑色的画面。

同时修掉一个真 bug（**D8-b**）：`lcd_status_init()` 把目标画面设为 `BOOT`，紧接着
`feedback_start()` 立刻写 `IDLE`；渲染任务 120ms 轮询，**等于一帧 BOOT 都没画过** →
"开机自检环"实际上永远不会出现。改为 `lcd_status_set_scene_timed(LCD_SCENE_BOOT, 1800)`，
保证自检环**必然被画一次**、之后自动回待机（也顺带保证自检色块结束后屏幕一定被重画）。

**⑤ 调试开关**：`app_config.h` 的 `APP_LCD_BL_SELFTEST=1`（**临时**）触发上述自检。
**现场确认后请改回 `0`**（正常行为 = 低电平常亮）。

> **纪律（本周第二次踩到同一类坑）**：`EXIT=0`、`.o` 生成、串口"就绪"日志，**都不等于"硬件真的动起来了"**。
> 凡是"看得见/听得见"的结论（屏亮、蜂鸣响、LED 亮），**必须以现场现象为准**，代码与日志只能证明"指令发出去了"。
> 未观察到现象之前，**不写"已通过"**。

> **D6 的教训（写进走查纪律）**：验证脚本**自己**也是被测对象。
> 只要它依赖"环境相关"的字符串匹配（编码、区域、终端宽度），就可能产生**假阴性**——
> 而假阴性比假阳性更危险：它会让人误以为产品坏了，或者反过来让人不再相信这套验证。
> 因此：① 判据优先用 ASCII 稳定串（`[HELP]`、`local feedback done`、`request_id`）；
> ② 必须用中文时，先统一编码；③ **最终裁判只认子进程退出码**，字符串匹配仅用于逐条展示。

> **D7 的教训（比 D6 更贵，必须记住）**：**"编译通过"不等于"功能分支被编译进去"。**
> 条件编译写错时**不会报任何错**，编译 `EXIT=0`、对象文件也照生成，唯一的症状是
> **运行期行为缺失**（这里是"屏黑"）——而人会本能地怀疑硬件，白折腾半天。
> 因此三条：① 开关宏必须在**判断之前**可见；② 关键开关用 `#error` / `#pragma message`
> 把编译期走向**打成可见输出**；③ 验证要落到**二进制判据**——在 `.elf` 里搜**该分支独有**的字符串。
> ⚠️ **挑判据本身也会错**：我第一版选了 `ST7789`，结果它其实来自 `feedback.c` 的另一句话，
> 属于**没有区分度**的判据；换成 `SCLK=%d`（只可能出现在启用分支）才得出正确结论。
> 这与 D6 是同一条纪律的两面：**别拿"看起来对"当证据。**

| 下行通道 | `commands/poll` 取 `collect_now` | `commands/poll` 取 `help_ack` / `clear_alert` | ✅ **同一条通道**，无 MQTT/WebSocket |
| 对端回执 | `device/ack`（`received`） | `device/ack`（`help_ack`） | ✅ 同一个端点，同一个幂等键 `(request_id, ack_type, attempt)` |
| **"收到"≠"完成"** | `acked` 只是回执，**不算采集完成** | `responded` 只是服务端事件，**不算已送达** | ✅ 同一条红线，两种表现 |
| 完成条件 | L1∧L2∧L3 三层互锁 | `remote_acked_at_utc` 单点判据 | ⚠️ **差异**：求助不需要判"新旧"，因为它是**事件**不是**观测** |
| 终态 | `completed/failed/timeout/rejected/cancelled` | `cancelled/expired` | ⚠️ **差异**：求助没有"超时"终态（等待本身不是失败） |
| 取消 | `POST /collect_requests/<id>/cancel`，终态 → `409` | `POST /help_events/<id>/cancel`，终态 → `200 + deduplicated` | ⚠️ **关键差异**（见下） |
| 取消留痕 | `failure_reason='CLIENT_CANCELLED'` | `cancel_reason` **必填** + `help_actions` 一行 | ✅ 都强调留痕，第 3 周更严 |

### 9.2 迁移时要改的三处（差异清单）

1. **终态重复取消的语义**：采集请求是"再取消就报错"（`409 REQUEST_ALREADY_FINAL`），
   求助是"再取消就幂等成功"（`200 + deduplicated:true`）。
   **求助场景必须用后者** —— 佩戴者可能慌张地连点取消，报错会让人以为没取消成功。
2. **判据维度**：采集要三层互锁（防"拿旧值冒充新采集"）；
   求助是**单一判据**（`remote_acked_at_utc` 非空）。不要把 L1/L2/L3 硬套到求助上。
3. **超时的含义**：采集有 `timeout` 终态（15s 没回报）；
   求助**故意没有**超时终态 —— "没人回应"是**社会事实**，不是**系统故障**，
   页面用 `age_ms` 持续显示等待时长，而不是把事件标成失败。

### 9.3 可直接复用到个人项目的骨架

```text
① 设备产生事件（本地先完成不可回滚的物理反馈，再尽力上传）
        ↓  幂等键 = f(boot_count, 触发单调时刻) 舍入到去抖窗口
② 服务端落库（status=created/uploaded，所有"远端事实"字段一律 NULL）
        ↓
③ 对端（人）声明已看到  →  只写"声明"相关字段（responded_at_utc / accepted_by）
        ↓  同时生成一条下行指令（入队 ≠ 送达）
④ 设备轮询取走指令 → 改本地表现 → 回执
        ↓
⑤ 服务端据此写"确认"字段（remote_acked_at_utc）→ 此时前端才允许显示"已送达"
        ↓
⑥ 取消：非终态均可取消、原因必填、记录不删除、终态重复取消幂等
```

**迁移检查单**：① 有无唯一 ID 与幂等键？② "本地事实"与"远端事实"是否分开存？
③ 下行是否只有一条主动轮询通道？④ 前端渲染"已完成/已送达"是否**只**依赖那个
唯一的确认字段？⑤ 取消是否留痕且不删记录？⑥ 超时是否被误当成故障？
