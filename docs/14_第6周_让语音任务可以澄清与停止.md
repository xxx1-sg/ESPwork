## 1. 三种"停" + 一种"被顶掉"

这是本周最容易做错的地方：**"停"不是一个功能，是四个**。它们的区别不在按钮，
而在"任务有没有跑过、音频有没有合成过、还允不允许播"。

| 动作 | 什么时候发生 | 打到哪个接口 | 对任务的影响 | 对播报的影响 | 终局 |
|---|---|---|---|---|---|
| **放弃录音** | 还在录，还没上传 | **不发请求**（本地丢弃） | 无（任务根本不存在） | 无 | 不留记录 |
| **取消本轮** | 已上传，在排队/识别/任务/合成中 | `POST /voice/turn/<tid>/cancel` 或 `/session/<sid>/cancel` | 还没跑到 → **一行都不执行**；已经跑了 → 收不回来 | 一律不许播 | `cancelled` |
| **停止播报** | 音频正在播 | `POST /voice/turn/<tid>/stop` | **完全不影响**（任务已经成功了） | 立刻停，记「停在第几毫秒」 | 仍是 `done` |
| **被新的一句顶掉** | 旧的还没回来，用户又说了新的 | 无（由半双工规则自动产生） | 旧的不再继续 | 旧的不许播 | `superseded` |

> ★ **最容易混的是"取消"和"停止播报"**。二者的差别不是文案，是**任务结果还在不在**：
> 取消是"这件事我不想要了"，停止播报是"这件事我做完了，只是不想听"。
> 所以 `stop` 永远不改 `final_state`，`cancel` 才改。前端也因此分成两个函数
> （`voiceStopSpeech` / `voiceCancelInflight`），避免某天顺手复用一个函数导致
> "点停止把已经成功的任务标成取消"。

前端在"停止"按钮上做了一件事：**它先判断当前阶段**，再决定发哪个请求。

```js
// web/app.js（节选，逻辑见 voiceStopAll）
//   录音中（还没上传）      → voiceAbortRecord()     ：不上传
//   有在途 turn             → voiceCancelInflight()   ：POST /cancel
//   只是音频在播            → voiceStopSpeech()       ：POST /stop
//   还挂着一张澄清卡片      → voiceAbandonClarify()   ：/cancel + /reset（放弃这次对话）
```

再看按钮文案的纪律：**点了取消之后，页面只说"已登记"，不说"已取消"**。
因为取消能不能生效，取决于服务端"跑到下一个检查点时发现它已被取消"——
在收到 `cancelled` 之前就宣称"已取消"，等于替服务端说谎。

```text
点停止 → 页面文案：「已登记取消，等这一轮跑到检查点会停下」
服务端把这一轮收尾 → 页面才显示：「已取消（停在识别之后，任务没有执行）」
```

## 2. 半双工会话：状态机与四张表

### 2.1 状态机

```text
                        ┌──────────────────────────────────────────┐
                        │                                          │
   ┌────────┐  提交一轮  ┌──────────┐  VAD 过  ┌──────────┐ 有回答 ┌───────────┐
   │ idle   │──────────►│listening │─────────►│ thinking │───────►│ speaking  │
   └────────┘           └──────────┘          └──────────┘        └───────────┘
       ▲                     │                     │                    │
       │                     │ 没声音               │ 有歧义              │ 播完/停止播报
       │                     ▼                     ▼                    │
       │                ┌─────────┐          ┌────────────┐             │
       └────────────────│ 终局态  │◄─────────│ clarifying │◄────────────┘
        reset / 取消/播完└─────────┘  补充一句 └────────────┘
```

| 状态 | 含义 | 谁能把它推进 |
|---|---|---|
| `idle` | 没人在说话 | 前端点"开始说话"→`listening`；或服务端收尾 |
| `listening` | 正在录 | 前端录完上传 → 服务端接手 |
| `thinking` | 已上传，识别/任务中 | 服务端（识别完、任务完） |
| `speaking` | 播报就绪/正在播 | 服务端（合成完）；前端播放器 `ended`/`pause` |
| `clarifying` | 正在等用户补一句 | 服务端（提出反问）；用户补充后回到 `thinking` |

> **`speaking` 不等于"人听到了"**。它是"有音频可播 / 播放器在播"。
> 真正"听到了"的唯一证据是用户点「我听到了」→ `POST /play`（第 5 周红线 V4，本周不变）。

### 2.2 四张表，各管一件事

| 表 | 干什么 | 为什么不能合并到 `voice_turns` |
|---|---|---|
| `voice_sessions` | 会话状态、`active_request_id`、`turn_seq`、待澄清上下文、`version` | 状态是会话的属性，不是某一轮的属性 |
| `voice_events` | **只追加**的关联日志（`turn_begin / turn_pending / clarify_ask / clarify_resolved / cancel_seen / superseded / stop_playback / finish`） | 日志一旦可改就不叫日志；按 `request_id` 一捞就能还原全过程 |
| `voice_cancels` | 取消请求（`request_id` 为主键） | ★ **取消可能比 turn 入库更早到**。用户点了停止，而 turn 还在解析音频、`voice_turns` 里那一行还不存在 —— 这条取消必须有地方待着，等 turn 入库后立刻生效 |
| `voice_supersedes` | "谁顶掉了谁"（`request_id → by_request_id`） | ★ 不能靠"我现在还是不是 active"临时推断，理由见 §5.2 的踩坑 |

`voice_sessions` 关键字段：

```sql
CREATE TABLE IF NOT EXISTS voice_sessions (
    session_id        TEXT PRIMARY KEY,
    device_id         TEXT,
    state             TEXT NOT NULL,
    version           INTEGER NOT NULL DEFAULT 0,   -- 每次状态推进 +1
    active_request_id TEXT,                         -- ★ 半双工：同时只允许一个在途
    active_turn_id    TEXT,
    turn_seq          INTEGER NOT NULL DEFAULT 0,   -- 会话内单调递增，钉住先后
    clarify_json      TEXT,                         -- 待澄清上下文（含轮次与候选）
    clarify_round     INTEGER NOT NULL DEFAULT 0,
    last_turn_id      TEXT,
    ...
);
```

`version` 是给前端用的：响应回来时如果 `version` 已经变了，说明这是**过期响应**，
不能拿它覆盖当前界面（这就是 C3 在会话层的兜底）。

### 2.3 预入库：能被"看见"才可能被"取消"

第 5 周的做法是"全部算完再一次性 `INSERT`"。那样有个致命问题：
**在算的过程中这一轮根本不在库里** —— 取消请求找不到它，`GET /voice/turns` 也看不到它。
而"能不能被取消"完全取决于"别人找不找得到你"。

所以本周一开口就先写一行 `final_state='running'`，然后每个阶段用增量 `_patch()` 往前推：

```python
# backend/voice_pipeline.py（节选）
    # ---- 预入库（能被"看见"才可能被"取消"）----
    _insert_running({... "session_id": session_id, "request_id": request_id,
                     "turn_seq": turn_seq, "received_at": received_at, ...})
    voice_session.log_event("turn_pending", session_id=session_id,
                            request_id=request_id, turn_id=turn_id, ...)
```

这条决定了三件事能不能成立：

1. 取消能命中它（`POST /cancel` 找得到 `turn_id`）；
2. 页面能显示"正在处理"（不用编一个假的 spinner 时长）；
3. 前端"再说一句顶掉旧的"时，旧的那条有 `request_id` 可比对（C3）。

## 3. 红线 C1：取消必须真的拦住任务段

### 3.1 检查点写在阶段边界上

```python
def guard(stage_key):
    """★ C1 / C3 的检查点：每个阶段边界都问一次"我还是被需要的那一条吗"。"""
    it = voice_session.interrupt_of(session_id, request_id)   # 取消？被顶掉？
    if it:
        raise _Interrupted(it, stage_key)
```

调用点（每个阶段之间）：

```python
guard("after_recorded")   # 录音/VAD 之后
guard("after_asr")        # 识别之后 → 任务之前  ★ 这一处最关键
guard("after_task")       # 任务之后 → 合成之前
guard("after_tts")        # 合成之后 → 收尾之前
```

`_Interrupted` 一路抛到 `while interrupted_info:` 分支统一收尾，
**并且必须把没跑到的阶段显式标成 `skipped`**：

```python
    # 被拦下的阶段必须显式标 skipped，否则前端会看到"永远在转圈"的格子
    _done_keys = {s["key"] for s in stages}
    for _k, _label in (("task", "任务执行"), ("tts", "语音合成")):
        if _k not in _done_keys:
            stage(_k, _label, "skipped", 0,
                  "整轮已被拦住（%s），这一段没有执行" % interrupted_info["kind"])
```

### 3.2 判据不是"状态是 cancelled"，而是"任务没跑"

这是本周最重要的判据设计。**只看 `final_state=cancelled` 是不够的** ——
一个取消可能落在任务之后（那一刻任务已经真的跑了，采了一条新数据、下发了一条采集指令）。
所以必须分开看两个字段：

| 字段 | 取值 | 含义 |
|---|---|---|
| `final_state` | `cancelled` | 这一轮"算被取消了" |
| `cancel_stage` | `after_recorded / after_asr / after_task / after_tts` | 在哪一步发现的 |
| `action_taken` | `0 / 1` | **任务段到底有没有真的发生副作用** |

于是有两条不同的事实，而页面必须分别说话：

```text
cancel_stage=after_asr, action_taken=0
  → 「取消发生在任务之前：任务段一行都没有执行」          （探针 S2 实测）

cancel_stage=after_tts, action_taken=1
  → 「取消发生在任务之后：动作已发生，收不回来（记录 action_taken=1）」（探针 S2b 实测）
```

自动化断言（`selftest_voice6.py` C 段 / `voice6_probe.py` S2）：

```python
check("★★ 关键：任务段一行都没执行（action_taken=false）", ...)
check("  任务格被标成跳过", [s["status"] for s in stages if s["key"]=="task"] == ["skipped"])
check("★ 没有新增采集指令", collect_count() == before)   # 这一条比任何文案都硬
```

> 为什么还要看"有没有新增采集指令"：`action_taken` 是管线自己记的账，
> 而"库里真的多了一条 `collect_requests`"是外部可观测的事实。
> 两者都成立才叫"真的没执行"，只信自家账本容易自欺。

## 4. 红线 C2：迟到结果不许播

### 4.1 交付资格是一个**落库的字段**，不是一个前端判断

每轮结束时服务端算一个 `delivery_state`，并且写 `playable`：

| `delivery_state` | 什么时候 | `playable` | `GET /reply/<id>.wav` |
|---|---|---|---|
| `deliverable` | 正常完成、合成成功 | 1 | 200（给文件） |
| `quarantined_cancelled` | 这一轮被取消了 | **0** | **410 Gone** |
| `quarantined_superseded` | 这一轮被新的一句顶掉 | **0** | **410 Gone** |
| `no_audio` | 没有音频（失败/无声/空回答） | 0 | 404 `NO_REPLY_AUDIO` |

**隔离写在服务端**，因为前端是可能被绕过的那一层：用户完全可以直接打开
`/api/v1/voice/reply/<id>.wav`。前端那一侧的检查只是"体验"，不是"安全"。

### 4.2 取消落点决定终局：404 还是 410，必须分开报

这是实测出来的区别，也是本周最"反直觉"的一条：

| 取消落点 | 音频有没有被合成过 | `GET /reply` | 为什么必须这样 |
|---|---|---|---|
| 识别期（`after_asr` 发现） | **从未合成** | `404 NO_REPLY_AUDIO` | 它本来就没有音频，说 410 会让人以为"被藏起来了" |
| 合成之后（`after_tts` 发现） | **合成出来了**（实测 563414 字节） | **`410 Gone`** | 音频真的存在，但这一轮不许播。用 404 会掩盖"它生成过"这个事实 |

```python
# backend/server.py（节选）
#  404 = 压根没有这条记录
#  404 + NO_REPLY_AUDIO = 这一轮本来就没产出音频（失败/无声）
#  410 Gone = 产出过，但按当前语义**不允许**给（取消 / 被顶掉）
#   用 403 会让人以为是权限问题，用 404 会掩盖"它其实生成过"这个事实。
if code == "REPLY_QUARANTINED":
    self._send_json(HTTPStatus.GONE, {"ok": False, "error": {
        "code": code, "message": why, "retryable": False,
        "details": {"turn_id": tid,
                    "hint": "要听这一轮的内容，请看记录里的文字回答；音频不会再给。"}}})
```

同时 `POST /play` 也必须拒：

```text
想上报「已播放」→ 409 NO_REPLY_AUDIO
  {"message": "这一轮没有产出播报音频（final_state=cancelled），没有可播放的内容。"}
```

> 只拦文件下载、不拦"上报已播放"是不够的：那样库里会出现
> `playback_started_at_utc` 有值、`playable=0` 的自相矛盾记录，
> 事后复盘时无法判断"到底播没播"。

### 4.3 探针里怎么"抢到"合成之后的窗口

取消能不能落在 `after_tts`，取决于"取消到达时这一轮跑到哪了"。
探针 S2b 用**固定时序偏移**去撞这个窗口：先提交一轮，再等 0.42 s 发取消。

```text
偏移 0.42 s → final=cancelled stage=after_tts reply=410（撞到 1 个窗口）
```

这个断言有两处必须写清楚，否则测不出东西：

1. **允许"这次没撞到"**：时序是真实并发，撞不到不许硬说成功，
   但撞到了必须断言 `stage == after_tts`（而不是"随便哪个阶段都算过"）。
2. **`tts.bytes > 0` 必须保留**：证明"它真的合成过"，而不是被伪造成"没合成"：
   `check("记录里仍然留着「合成成功过」的事实", tts_bytes > 0)`。

## 5. 红线 C3：只认最后一个 request_id

### 5.1 从哪一方判定"我被顶掉了"

半双工规则：会话里同时只允许一个在途 turn。新的一轮提交时，
旧的那一轮如果还没回来，就在 `voice_supersedes` 里记一笔 `A → by B`。
旧的跑完后，检查点是这么判的：

```text
interrupt_of(session_id, request_id):
    cancel  : voice_cancels 里有我            → 「被取消」
    supersede: voice_supersedes 里有我 → 「被顶掉」  ← 两者分开
```

于是 A 的终局是 `superseded`（不是 `cancelled`），交付资格是
`quarantined_superseded`，音频 410，并且 **A 不许改写会话状态**：

```text
探针 S3 实测：B → done；A → superseded（superseded_by=B）
             A 拿不到可播音频；B 的播报 200
             会话 last_turn_id = B（A 回来时没有把它改回去）
```

### 5.2 踩坑：A 慢 B 快，A 被误判成 cancelled

开发期实测过这个 bug：

> A 提交后很慢，用户又说了一句 B。B 很快跑完，会话回到 `idle`、
> `active_request_id=NULL`。这时 A 才醒来。
> 如果按"我还不是 active ⇒ 我被取消了"去判，A 会被记成 `cancelled`
> —— 但用户**从来没取消 A**，A 只是输给了更新的一轮。

这两种情况的处置完全不同：

| 终局 | 用户视角 | 要不要问原因 | 该说的话 |
|---|---|---|---|
| `cancelled` | "我不想要了" | 要（`cancel_reason` 必填） | 已取消（停在识别之后…） |
| `superseded` | "我又说了一句" | 不要 | 被「后一句」顶掉了，结果不再播放 |

修法是**把"谁顶掉了谁"落库**（`voice_supersedes`），而不是从 `active` 是不是我反推。
库里的事实比推断可靠。

### 5.3 前端这一侧的丢弃判据

前端只认一个东西：**这次响应还是不是我当前那一个 `request_id`**。

```js
// web/app.js（voiceSubmit 里，源码级断言钉住这一行）
VOICE.inflight = req;
...
const j = await r.json();
if (VOICE.inflight !== req) { voiceDropLate(req, j, r.status); return; }  // ★ 整轮丢弃
VOICE.inflight = null;
```

`voiceDropLate()` 做的是"整轮丢弃"：不渲染、不播放、不改阶段、不动会话条，
只在日志区写一句"这一轮的结果回来晚了，已丢弃（当时在途的是 …）"。

> 只丢弃"播放"是不够的。踩过的坑：一开始只拦了 `audio.src`，
> 结果旧答案的**文字**还是渲染进了结果区，用户看到"上一句的答案"配着"这一句的问题"。

## 6. 澄清：听不准时先问一句，问到上限就停

### 6.1 三个约束

| 约束 | 值 | 为什么 |
|---|---|---|
| 最多几轮 | `MAX_CLARIFY_ROUNDS = 2` | 问第三遍还说不清，说明这条路走不通，该给退路 |
| 谁来消解 | **纯确定性规则**，不调模型 | 选错设备会真的下发采集指令，代价是物理世界的 |
| 反问轮做什么 | 只问，**不调任何业务工具** | 反问轮的任务格来源必须写"未调用" |

### 6.2 消解顺序（可核对，不是"猜"）

| 顺序 | `how` | 判据 | 结果 |
|---|---|---|---|
| ① | `device_name` | 回答里出现设备 ID 全名或尾部（≥4 字符） | 精确匹配那台设备 |
| ② | `device_ordinal` | 回答里有"第一/第二/第 2…" | 取上一轮给过的第 N 个候选 |
| ③ | `intent_ordinal` | 同上（意图类歧义） | 取第 N 个候选说法 |
| ④ | `intent_keyword` | 回答里出现意图关键词（"查看/采集/在线"…） | 取对应那句候选 |
| ⑤ | `freeform` | 是一句 ≥4 字、能独立成立的话 | **整句重放**（重新解析，不是从候选里挑） |
| ✗ | `unresolved` | 都不满足 | 再问一次；到上限 → `clarify_exhausted` |

实测（探针 S4）：

```text
反问：「你是想「查看已有记录」，还是「请求设备重新采集一次」？」
候选：['查看上次数据', '重新采集一次', '设备在线吗']
反问轮来源：无（未调用业务工具）   轮次：1/2
补充「查看上次数据」→ how=intent_keyword → 重放那句 → done
```

### 6.3 文字补充轮：它是"打字"，不是"语音"

澄清的时候，让用户对麦克风说第二个字是最糟糕的体验。所以页面给了输入框，
但它走的是**同一条 `handle_turn`**、同一张表、同一套取消/隔离/时序：

```text
POST /api/v1/voice/text
  {"text": "查看上次数据", "session_id": "vs_…", "request_id": "…",
   "device_id": "…", "capture_location": "keyboard:…"}

返回：audio_source = "text_input"    ← 不伪装成麦克风
      asr.engine  = "keyboard"       ← 没有调用识别引擎
      vad_passed  = null             ← 没有"有没有声音"这回事
      audio_url   = null             ← 没有原始录音
```

| 为什么必须这样标 | 说明 |
|---|---|
| 不伪装成麦克风 | 否则事后统计"语音使用率"会把打字算成说话，数据是假的 |
| 不调用识别引擎 | 打字不需要识别；标成 `keyboard` 才能证明"这一步没花钱" |
| 复用同一条链路 | 多轮上下文只实现一次；否则"语音轮流 A、文字轮流 B"，必然出现两套不一致 |

### 6.4 反问也要念出来

语音助手不能在屏幕上问问题。所以 `do_tts()` 被抽成函数，**反问一样走合成**：

```python
def do_tts(text, note_full_chars, outcome_state):
    """合成播报。抽成函数是因为"反问"也要念出来 —— 语音助手不能在屏幕上问问题。"""
```

### 6.5 到上限说什么

```text
已经问了 2 轮还没说清，先停下。你可以直接说「查看上次数据」/「重新采集一次」/
「设备在线吗」，或者改用文字入口打字 —— 打字的歧义更少。
```

`clarify_exhausted` 这一轮**不执行任何工具**，并且**不再接受补充输入**
（前端把输入框和候选项都收起，只留上面这段退路）。

## 7. 时序：四个数，每个都能对上物理动作

### 7.1 t0 定义

| 时间点 | 取值方式 | 为什么这么定 |
|---|---|---|
| **t0** | **服务端收到完整音频的那一刻** | "用户说完"是不可直接观测的；"服务端拿到完整音频"是它的**可证代理量** |
| `first_feedback_ms` | t0 → 识别出文本 | 用户第一次看到/听到**实质内容**的时刻 |
| `task_done_ms` | t0 → 任务段结束 | 业务动作真正完成的时刻 |
| `tts_ready_ms` | t0 → 合成好 WAV | "播报就绪"（不是"播放完"） |
| `client_ack_ms` | **前端本地** | 本地"已提交"提示的耗时；属**本地事实**，服务端不代算 |
| `total_ms` | t0 → 收尾 | 一轮服务端总耗时 |

实测（2026-10-26 01:37，`evidence/voice6_probe.log`）：

```text
t0=2026-10-26T01:37:41.674Z
首次反馈 165 ms → 任务完成 427 ms → 播报就绪 534 ms → 合计 574 ms
客户端 RTT 730 ms（含浏览器与服务端之间的网络往返）
```

**2026-10-28 复跑（本机无音频设备，TTS 降级 tone）**，同一份代码、同一套断言：

```text
t0=2026-10-28T01:11:16.422Z
首字 40 ms → 任务 329 ms → 播报就绪 401 ms → 合计 407 ms（客户端 RTT 472 ms）
```

> 两组数字的差别正好印证了 §11 D10：`tts_ready_ms - task_done_ms`
> 从 **107 ms** 缩到 **72 ms**（合成音比 SAPI 快），而**"任务完成"那一段几乎没变**
> （427→329 / 534→401 是识别段的差别，注入不花时间）。
> 也就是说：**真正变的是"合成"这一段，状态机与任务的语义没有变。**
> 引用任何时序数字时都必须同时说明当次用的是哪个 TTS 后端。

单调性被断言钉住（`first_feedback ≤ task_done ≤ tts_ready ≤ total`）：
一旦顺序反了，说明某一处在"提前写时间戳"，比数字大小更值得警惕。

### 7.2 为什么要单独记 `client_ack_ms`

它和另外三个不是一类：另外三个是服务端算的，它是**前端自己报的本地事实**。
分开记的理由是查问题时能立刻区分：

```text
总耗时 1.2 s，但 client_ack_ms = 900 ms  →  慢在前端（录音重采样 / 网络提交）
总耗时 1.2 s，但 client_ack_ms = 5 ms    →  慢在服务端（识别/任务/合成）
```

如果把两者混成一个"总耗时"，出问题只能靠猜。

## 8. 测试注入：可以让流程"慢下来"，但必须留痕

### 8.1 三个注入参数

| 参数 | 作用 | 典型用途 |
|---|---|---|
| `inject_delay_ms` | 在识别段之前人为等待 | 抢"取消落在识别期"的窗口 |
| `inject_task_ms` | 让任务段人为变慢 | 抢"取消落在任务期"的窗口 |
| `inject_asr_text` | 直接指定识别文本 | 不依赖麦克风与模型，做确定性用例 |

### 8.2 三道闸，缺一不可

```text
① 服务端开关：VOICE_ALLOW_INJECT 未开启 → 带 inject_* 直接 400
② 记录留痕 ：asr.engine = "injected" + inject_json 保存原始设定值
③ 页面标注：注入区默认 <details> 收起，展开后写明「这不是真实识别结果」
```

真实记录（探针 S1）：

```json
"inject_json": {
  "delay_ms": 0, "task_ms": 0, "asr_text": "查看上次数据",
  "raw": {"inject_asr_text": "查看上次数据"},
  "note": "这是**注入**的一轮：延迟/识别文本是人为设定的，不是引擎实测结果。
           记录里 inject_json 会保留设定值。"
}
```

> ★ **为什么注入必须留痕**：注入的参数如果和真实参数长得一样，
> 那么"我们那天测出来 165 ms"这句话就失去了意义 —— 因为没人能证明
> 那个 165 ms 是真引擎跑出来的，还是注入出来的。留痕让这句话可核对。

前端源码级断言：


## 11. 踩坑记录（真实发生，附修法）

### D1 在 `_lock` 里调 `log_event()` → 整个服务卡死

`voice_pipeline._lock` 与 `voice_session._lock` 都是**普通 `threading.Lock()`（非重入）**。
而 `log_event()` 自己也要拿锁。于是：

```python
with _lock:
    voice_session.log_event("cancel_seen", ...)   # ✗ 等自己已持有的锁 → 死锁
```

症状不是报错，而是**这个请求永远不返回**，其它线程也开始排队，最后表现成"后端卡住"。

**修法**：`log_event()` 一律在 `with _lock` **外面**调用。
现在的代码里所有 `log_event` 调用点都在锁外（`_insert_running` 结束之后、
`_patch` 调用之间）。同理 `_patch()` 内部只做 `execute/commit`，不写日志。

### D2 取消落在合成之后 → 已算完的一轮被判 `internal_error`

`sqlite3.OperationalError: attempt to write a readonly database`
在板子 10 Hz ingest + 摄像头 ~10 fps + 语音三路并发写同一个 `sensor.db` 时偶发。
它落在 `_patch()`（阶段增量 / 收尾记账）里，而原本异常直接从 `flush()` 冒出去：

```text
结果：已经算完的这一轮（识别文本、任务回答全都有了）被整轮判成 internal_error，
      用户看到"语音链路内部异常"，他要的东西全丢了。
```

**修法**：`_patch()` 重试一次；仍失败就写 stderr 警告后**继续**。
理由是**记账失败不能毁掉结果** —— 那一轮的业务价值已经产生了。

```python
for attempt in (1, 2):
    ...
    except sqlite3.OperationalError as e:
        if attempt == 2:
            sys.stderr.write("[voice] 阶段增量写入失败（已重试一次，跳过）：%s\n" % (e,))
            return
        time.sleep(0.05)
```

而 `_insert_running()`（预入库）**反过来**：不能"写不进去就算了"，
因为后面所有阶段都要落脚在那一行上。所以它退避重试 3 次，
仍失败就抛 `StorageBusy` → 接口回 **503 `VOICE_STORAGE_BUSY`（retryable）**，
并且**一件事都不做**（探针 M2 断言"没有新增采集指令、没有半条记录"）。

> 同一类异常，两处处理相反 —— 判据不是"这个异常严不严重"，而是
> **"这时候账本有没有、"后面还做不做得下去"**。

### D3 老库上 `CREATE INDEX` 早于补列 → 后端启动即崩，永远起不来

第 6 周的 DDL 里带了：

```sql
CREATE INDEX idx_voice_request ON voice_turns(request_id);
```

而 `CREATE TABLE IF NOT EXISTS` 在**老表上等于什么都不做**，补列却写在 DDL 之后。
新库一切正常（自检跑的就是新库），**真实库**每次启动都崩在 `db_init`：

```text
sqlite3.OperationalError: no such column: request_id
```

守护进程 3/6/12/24 秒退避重拉、永远起不来，日志里只有一行看起来像"库坏了"的报错。

**修法**：`db_init` 分三步，索引挪到独立常量 `_DDL_INDEX_W6`：

```python
def db_init(conn):
    conn.executescript(DDL)                                   # ① 建表（老库上是空操作）
    have = {r[1] for r in conn.execute("PRAGMA table_info(voice_turns)")}
    for col, typ in (("tts_truncated","INTEGER"), ("reply_full_chars","INTEGER")) + _NEW_COLS_W6:
        if col not in have:
            conn.execute("ALTER TABLE voice_turns ADD COLUMN %s %s" % (col, typ))  # ② 补列
    conn.executescript(_DDL_INDEX_W6)                          # ③ 最后建索引
    voice_session.db_init(conn)
```

并且**留了回归**（`selftest_voice6.py` L 段）：造一个"第 5 周形状"的老表，
跑一遍 `db_init`，断言不抛异常、列补齐、索引建出、**老数据一个值都没被改写**。

> 教训：**只在新建的临时库上跑自检，会漏掉"升级"这条最重要的路径。**
> 凡是"给已有表加东西"的改动，必须有一个在旧形状上跑的用例。

### D4 `HTTP_PROXY` 让"后端没起"变成 502

宿主环境里有 `HTTP_PROXY=127.0.0.1:53528`，而 Python `urllib` 默认**读它**。
于是探针连 `http://127.0.0.1:8000` 时请求被送去代理，代理回 502。
排查方向一度跑偏成"后端挂了"，其实后端好好的。

**修法**：探针显式绕开代理（连本机不该走代理）：

```python
_OPENER = urllib.request.build_opener(urllib.request.ProxyHandler({}))
```

### D5 澄清上限轮把真正的错误信息覆盖掉了

到第 3 轮时先写了"已经问了 2 轮还没说清…"，紧接着通用错误收尾又写了一遍
`error_message`，把上一句覆盖成了"请再说一次"。用户看到的是一句毫无信息量的话。

**修法**：`clarify_exhausted` 这一支**只由澄清逻辑负责写文案**，
通用错误收尾看到已有 `clarify_ctx["fallback"]` 就不再覆盖；
自检里加了"上限轮给出了退路说明"这条断言（除了断言状态，还要断言**说的话有用**）。

### D6 `superseded` 被误判成 `cancelled`（见 §5.2）

根因是拿"我还是不是 active"反推终局。A 慢 B 快时 `active=NULL`，
A 被记成"用户取消"。修法是 `voice_supersedes` 单独落库。
附带修了一处：`cancel_reason` 对 `superseded` **要求必填**是错的
（用户根本没取消，没有原因可填）。

### D7 字符串 `error` 让 `/api/v1/nl/query` 直接 500

某处把 `error` 字段赋成了字符串，而下游按 `dict` 取 `.get("code")`：

```text
AttributeError: 'str' object has no attribute 'get'  →  500
```

修法：错误对象统一由 `_error(code, message, **details)` 构造，
调用方只允许塞 dict。**错误结构不一致，比错误本身更难查。**

### D8 引擎 TTS 临时文件被 safe-delete 清掉 → 连接静默断开

合成完把 WAV 写回来后，临时文件被环境里的批量删除保护机制顺手清掉，
读取时连接已断，客户端只看到 `Remote end closed connection`。
修法：引擎侧把结果**先读完再删**（并且读失败时如实报 `tts_failed`，不返回半截音频）。

### D9 探针断言把"404 也对"写成了"必须 410"

第一版 S2 断言 `reply == 410`，实测拿到 404 就判失败。
但那个用例的取消落在**识别期**，这一轮**从未合成**，404 才是正确答案。

**修法**：断言改成"拿不到可播音频"（`cod in (404, 410)`），
另外加 S2b 用固定时序偏移**专门**抢"合成中"的窗口，在那里才断言 410。

> 教训：**断言要对着"语义"写，不要对着"碰巧观测到的那个数字"写。**
> 否则测试会把正确的行为判成失败，然后你为了让它变绿去改对的代码。

### D10 复跑时 TTS 全线崩溃：机器没有音频输出设备（环境退化，不是代码回归）

2026-10-28 复跑第 6 周的三套测试时，`selftest_voice6.py` 在 B 段直接抛异常停下：

```text
_ctypes.COMError: (-2147200960, None, (None, None, None, 0, None))
  File "backend/voice_engine.py", line 320, in tts_sapi
    voice.Speak(text)
```

**排查过程（每一步都证伪掉一个猜测）**：

| 猜测 | 验证 | 结论 |
|---|---|---|
| 并发/状态污染 | 用全新进程单独调 `tts_sapi()` | 同样失败 → 否 |
| comtypes 与 Python 3.14 不兼容 | `CreateObject("SAPI.SpVoice")`、`GetVoices()` 都正常，能列出 Huihui/Zira | 否 |
| 中文语音的 token 坏了（指向 OneCore 引擎） | 换成英文 Zira（真 SAPI5 引擎）重试 | 仍失败 → 否 |
| 写文件权限问题 | 改写 `%TEMP%`，文件读写正常 | 否 |
| **SAPI 取不到音频设备** | `SpVoice.GetAudioOutputs("","").Count` | **返回 0 → 是** |

`Win32_SoundDevice` 在本机返回 **0 个**，`AudioEndpointBuilder`/`Audiosrv` 都在跑但没有任何音频适配器。
**SAPI 的 `Speak()` 即使只想把语音写进文件，也要求系统至少存在一个音频输出设备**，
所以 FileStream / MemoryStream / 默认输出三条路全部失败。

> ★ 这是**环境退化**，不是本周代码的回归：第 5 周的实测记录
> （`evidence/voice_week5/*.json`）里 TTS 明明是好的
> ——`engine=sapi`、`voice="Microsoft Huihui Desktop"`、`ms=407`、`563414` 字节。
> 同一份代码、同一台机器，10-23 能合成、10-28 不能，差别只可能是驱动/设备层。

**修法（分三层，每一层都不许"假装成功"）**：

1. **先诊断再失败**：`do_tts()` 调 `Speak()` 之前先探 `GetAudioOutputs()`，
   为 0 就直接给出人能读懂的错：

   ```python
   n_out = _sapi_audio_outputs()
   if n_out == 0:
       raise RuntimeError("系统没有可用的音频输出设备（GetAudioOutputs() 返回 0）。"
                          "SAPI 即使只想把语音写进文件也要求存在音频设备。")
   ```

   原来的 `COMError(-2147200960)` 对排查毫无帮助，这一步把 30 分钟的瞎猜变成一行结论。

2. **降级但不冒充**：新增 `tone` 后端（`VOICE_TTS_FALLBACK=1` 默认开）。
   它生成一段**能被 VAD 判为"有声音"的合成音**（实测 RMS 0.193 / 峰值 0.275，
   阈值是 0.006 / 0.02），让状态机、取消、隔离、澄清、时序这些**与"是不是真人声"无关**的
   语义仍然能在真实音频上跑通。但它**绝不冒充语音**：
   `X-Tts-Engine: tone`、记录里 `tts.engine="tone"`、`voice=None`、
   还有一句 `note: "这是合成音占位，不是语音"`。

3. **自检自己感知环境**：`selftest_voice6.py` 启动时读 `/health` 的 `tts.speaks`，
   为 `false` 就把需要"听出指定文本"的轮次改为 `inject_asr_text`（教师侧注入入口，
   本来就有），并在**结尾汇总里如实报告**：

   ```text
   ★ 环境说明：本机没有可用的音频输出设备，SAPI 无法合成真人语音。
     因此本轮自检有 8 个 turn 用 inject_asr_text 指定了识别文本（记录里标 asr.engine=injected）。
     被测的取消/隔离/澄清/时序语义不受影响，
     但『识别引擎真的听懂了这句话』这一条本周没有被验证 —— 那属于第 5 周的结论。
   ```

   顺带修掉一个**假绿**风险：`turn_async()` 透传 `**kw`，异步调用点漏传 `say=` 时，
   注入文本会退到兜底值"设备在线吗"（意图 `device_status`），于是 D 段
   "取消落在任务之后"测的其实是个**不发采集指令**的意图，`collect_requests` 当然为 0。
   这个用例会以"看起来像实现错了"的方式失败，实际是**测试自己没把话说对**。

**连带修的两处**：

- `voice6_probe.py` 的 S2b 原本用固定偏移 `(0.42, 0.48, 0.60, 0.54, 0.66)` 去撞
  "合成之后"的窗口——那是按**真实 SAPI 约 400 ms** 标定的。换成合成只要 17 ms 的引擎后，
  `after_tts` 窗口前移到 300~355 ms，固定偏移**永远撞不到**，断言恒失败。
  改成**先标定再撞**：跑一轮读出 `task_done_ms / tts_ready_ms`，在两者之间生成偏移序列
  （实测打印 `标定：task_done=301ms tts_ready=355ms → 尝试偏移 [0.32, 0.328, ...]`，
  在 `0.336 s` 命中 `stage=after_tts → reply=410`）。
- `selftest_voice.py`（第 5 周）里"非法 audio_source 的允许值集合"断言写死了三个值，
  而第 6 周**有意**新增了 `text_input`。这是过时断言，不是回归，已同步为四个值。

> 教训一：**"在我机器上是好的"要能证伪。** 这里能快速定位，靠的是
> 先问"这台机器现在和上次跑的时候差在哪"，而不是先怀疑自己刚改的代码。
> 教训二：**降级路径必须自带标签。** 如果 tone 生成的音频长得和真语音一样、
> 记录里也不标，那么"本周实测 TTS 正常"这句话就变成了假的。
> 教训三：**测试跑不过时，先分清是"实现错了"还是"测试说错话了"。**
> 这次两类都出现了（D9 是前者、D10 的 `collect_requests` 是后者）。
> 教训四：**降级警告要打一次，不要打一千次。** 第一版把
> `[voice] SAPI 合成不可用…` 写在每次合成失败处，于是一次全量回归刷了几百行 stderr
> （每个 turn 合成一次播报 + 一次反问），把真正的诊断信息彻底淹没。
> 现在按错误内容去重（`_warn_fallback_once()`）：第一次说清楚，之后静默；
> **每轮的事实仍然逐条落在记录的 `tts.engine` / `fallback_reason` 里**，
> 日志可读性和可核对性都不牺牲。这条其实是个通用规律：
> **"状态性"的警告适合去重，"事件性"的记录必须逐条。**

## 12. 迁移：为个人项目选一个"真的需要能停"的语音任务

### 12.1 三条判据（不满足就别选）

| 判据 | 要问的问题 | 反例 |
|---|---|---|
| **① 有真实的副作用** | 这个任务会不会改变物理世界/发出指令？ | "讲个笑话"——取消了也没损失，学不到东西 |
| **② 有真实的"说不清"** | 用户的话是否经常需要澄清一句？ | 固定口令的开关灯——不需要澄清，也就测不到澄清 |
| **③ 有真实的"等不及"** | 用户是否会在等待中想停止/改口？ | 100 ms 就返回的本地查询——没有可停的窗口 |

三条都满足，才能同时练到 **澄清 / 取消 / 迟到隔离** 三件事。

### 12.2 选题（按"能落到真实设备"排序）

| 选题 | ①副作用 | ②说不清 | ③等不及 | 落地要点 |
|---|---|---|---|---|
| **语音控制采集/巡检设备**（推荐） | 会真的下发采集指令 | "采哪个/采多久"经常要问 | 采集要 1~3 s，用户会想停 | 复用本周的 `request_collect` + `action_taken` |
| 语音录入家庭记账 | 会写一条账目 | "多少钱/哪一类"常要确认 | 记账要等网络 | 取消要能**回滚已写入的那条**（比本课难一档） |
| 语音预约/挂号 | 会占用号源 | 科室/医生/时间三重歧义 | 排号要等 | 取消必须**释放号源**，幂等尤其重要 |
| 语音点单（自家小店） | 会生成订单 | 规格/口味多 | 出单要等 | 同上，要注意"取消了但厨房已开工" |

### 12.3 迁移步骤（照着做就行）

1. **先找"能被取消的那一行"**：你的系统里哪一个状态是"在途"？没有就造一个
   （预入库 `running` 这一手就是干这个的）。
2. **在每个阶段边界插检查点**，而不是在"用户点取消"时直接改状态。
   前者是"跑到下一个安全点再停"，后者是"边跑边改，随时可能半截"。
3. **给每一轮算交付资格**（`deliverable / quarantined_* / no_audio`），
   并且**把判断放到服务端**。
4. **把"说不清"写成有限轮**（≤3 轮），并且**消解用规则不用模型**。
5. **留一个注入开关**，以后你才能在没有麦克风、没有设备的情况下复现问题。

### 12.4 迁移检查表

```text
[ ] 在途的任务在库里看得见（有 running 行）
[ ] 取消打的是 /cancel，停止播报打的是 /stop，两者不共用一个接口
[ ] 被取消的一轮里，任务段的状态是 skipped 而不是 failed
[ ] 有一个字段能说明"任务到底跑没跑"（action_taken）
[ ] 被隔离的音频不是 404 而是 410（除非它真的没合成过）
[ ] "上报已播放"也被拦（否则库会自相矛盾）
[ ] 迟到结果的判据是 request_id，不是"我觉得它过期了"
[ ] 澄清有轮数上限，到上限给退路而不是继续问
[ ] 打字补充没有伪装成语音（来源字段如实）
```

## 13. 限制与如实说明

1. **本周没有使用板载麦克风。** 音频来源仍是浏览器麦克风 / 授权录音文件。
   ESP32-S3-EYE 的 PDM 麦克风属于端侧硬件课，本课**不把它作为前提**（与第 5 周一致）。
2. **注入轮必须被当成"演示"而不是"实测"。** `inject_asr_text` 指定的文本、
   `inject_*_ms` 指定的延迟都是人为设定的。凡引用这类数字，必须同时说明
   `asr.engine="injected"`。真实识别数字（0.4~0.7 s）见第 5 周文档 §6.2。
3. **`text_input` 不是语音。** 它只是"澄清时可以用键盘补一句"，
   记录里 `audio_source=text_input`、`asr.engine=keyboard`。统计"语音使用率"时不能算进去。
4. **`speaking` 不代表"人听到了"。** 它只表示"有音频可播 / 播放器在播"。
   唯一证据是用户点「我听到了」（`POST /play`）。
5. **半双工是"服务端记账 + 前端自觉"，不是音频层抢占。** 我们没有在麦克风层面做回声消除/打断；
   如果用户边说边播，音频会重叠。真正的"可打断"（barge-in）需要 AEC，本课不做。
6. **澄清消解是确定性规则，不是"模型听懂了"。** 它只认序号、意图关键词、设备名三类回答；
   说得太绕就是 `unresolved`（然后问第二次、再不行就给退路）。这是**故意的**：
   选错会真的下发采集指令。
7. **时序是"服务端视角"的。** `t0` 是服务端收到完整音频的时刻，不含"用户说完→浏览器上传"这一段；
   那一段由 `client_ack_ms` 如实标为本地事实。
8. **数据库仍是单机 SQLite。** 本周的三表并发写已经能撞出 `readonly database`
   （见 D2），生产环境请换 PostgreSQL/MySQL，并给"取消"这类请求用上真正的事务。
9. **`_patch` 的"记账失败就跳过"是有代价的**：极端情况下某一轮的阶段增量会丢，
   表现为"记录页上某一段没有耗时"。这是有意的取舍——**宁可账本缺一角，也不能把结果扔掉**。
10. **本机当前没有音频输出设备，TTS 走的是 `tone` 降级后端**（见 §11 D10）。
    `tone` 产出的是**合成音不是语音**，记录里 `tts.engine="tone"`、`voice=null`。
    凡是引用本周时序数字的地方，都要注意：`tts_ready_ms` 里那一段是合成音耗时（约 17 ms），
    比真实 SAPI（约 400 ms）短一个数量级。**换成有声卡的机器重跑，数字会变，语义不变。**
11. **注入轮与降级轮都不许当作"真实语音能力"的证据。**
    本周有三类轮次要分清：真实识别（`asr.engine=vosk`）、
    教师注入（`asr.engine=injected`）、键盘输入（`asr.engine=keyboard`）。
    自检结尾会报出本次各类各有多少轮。

> 本周的中心句：**"能停下来"不是一个按钮，而是三件可核对的事实** ——
