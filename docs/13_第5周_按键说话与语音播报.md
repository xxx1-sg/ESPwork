## 1. 「说一句话」到「听到回答」的全景

```text
                 ┌──────────────── 浏览器（运行位置：本机 PC）────────────────┐
                 │ 点一下开始 → WebAudio 采集 → 重采样到 16 kHz → 写 RIFF 头    │
                 │                        ↓  PCM 16bit mono WAV               │
                 │ ①录音   ②静音检测  ③识别  ④任务  ⑤合成  ⑥播放  ← 六格状态  │
                 │                        ↑ <audio> 播报                      │
                 └────────────────────────┼───────────────────────────────────┘
                                          │ POST /api/v1/voice/turn (body=WAV)
                 ┌────────────────────────▼───────────────────────────────────┐
                 │ backend/server.py（零第三方依赖）                           │
                 │  · 校验 WAV 头（16k/16bit/mono）→ 不符就 400 并报实际参数    │
                 │  · 算 RMS/峰值/过零率（VAD，写在服务端，前端不参与判定）     │
                 │  · 录音落盘 + SHA256                                        │
                 │  · 调 ASR ──HTTP──┐                                        │
                 │  · 文本 → nl_assistant.handle_query（第 4 周同一函数）       │
                 │  · 回答 → 取前 2 句 → 调 TTS ──HTTP──┐                      │
                 │  · 六段状态 + 运行位置 一次性入库                            │
                 └───────────────────┼──────────────┼─────────────────────────┘
                                     │              │
                 ┌───────────────────▼──────────────▼─────────────────────────┐
                 │ backend/voice_engine.py（独立进程 127.0.0.1:8013）           │
                 │   ASR: vosk 离线中文模型（CPU，不联网）                      │
                 │   TTS: Windows SAPI 中文语音（Huihui，离线）                 │
                 └─────────────────────────────────────────────────────────────┘
```

**为什么要拆成三个进程/位置**：

| 位置 | 承担 | 为什么在这里 |
|---|---|---|
| 浏览器 | 采集、播放 | 麦克风和扬声器在用户身边；采集必须发生在"说话的地方" |
| `server.py` | 编排、校验、判定、落库 | 全工程一直只用标准库，语音的重依赖不能塞进来 |
| `voice_engine.py` | 识别、合成 | 模型常驻内存（加载 184 ms），独立启停；挂了只影响语音，不影响文字 |

一句话概括本周的设计取舍：**能"看见"的东西全部由服务端算出来，前端只负责采集和展示。**

## 2. 必交内容：音频来源与运行位置

### 2.1 每条记录都带来源与位置

`voice_turns` 表里有两列专门记这件事，**缺任何一项就 400 拒收**（红线 V5）：

```text
audio_source      必须是 browser_mic / uploaded_file / device_mic 之一
capture_location  字符串，必须写清"录音发生在哪台机器"
run_location_json {"capture":…, "asr":…, "task":…, "tts":…, "playback":…} 五段都有值
```

对应实现：`voice_pipeline.handle_turn` 开头两个检查，以及末尾的：

```python
run_location = {
  "capture": capture_location,                       # 前端如实上报
  "asr":     "http://127.0.0.1:8013 · vosk/<model>（离线）",
  "task":    "server.py · nl_assistant.handle_query（第 4 周同一函数，进程内调用）",
  "tts":     "http://127.0.0.1:8013 · sapi/Microsoft Huihui Desktop",
  "playback":"browser <audio> · 本机 PC",
}
```

> **为什么"位置"要写这么细**：本周最容易出的事故是"我以为在板上跑的，其实在电脑上跑的"。
> 把五个位置逐条写进记录，事后回看一条记录就知道每一段到底发生在哪。

### 2.2 为什么本周不用板载麦克风

ESP32-S3-EYE 主板上确实有 PDM 麦克风，但本周**不**把它作为前提，理由有三条（都可核对）：

1. **课程约定**：本周题目是"接通按键说话与语音播报"，端侧课另行验证音频设备能力。
   把麦克风驱动开发塞进来，会挤掉本周真正的重点——**状态可观察 + 失败可理解**。
2. **识别质量取决于模型，而不是麦克风**：本机实测，系统自带 SAPI 中文听写引擎把
   「查看上次数据」识别成「他看上去瘦的」（置信度 0.06），换成 vosk 小模型就正确了（§6.3）。
   换句话说，**瓶颈在识别引擎，不在采集端**——这一周更该把力气花在引擎选型与链路可观测上。
3. **可复现性**：电脑音频（浏览器麦克风 / 授权录音）任何人拿到工程就能跑，
   不依赖"板子当时接没接好"。

所以本课的音频来源是**电脑音频**，而记录里 `audio_source` 会如实写 `browser_mic`
或 `uploaded_file`，绝不会写成 `device_mic` 来"显得更厉害"。

### 2.3 引擎怎么起来

```powershell
# ① 一次性：装依赖（三个包，约 30 秒；不进主后端）
D:\ESP\.venv\Scripts\python.exe -m pip install comtypes pythonnet vosk

# ② 一次性：下载离线中文识别模型（43.9 MB）
#    来自 https://alphacephei.com/vosk/models/vosk-model-small-cn-0.22.zip
#    解压到 D:\ESP\.models\vosk-model-small-cn-0.22
D:\ESP\.venv\Scripts\python.exe -c "import zipfile;zipfile.ZipFile(r'D:\ESP\.models\vosk-cn.zip').extractall(r'D:\ESP\.models')"

# ③ 每次都开：语音引擎（默认 127.0.0.1:8013，只监听本机）
#    推荐用脚本：它会帮你设全 3 个必需的环境变量、检查模型目录、起完立刻自检并打印
#    「到底哪个引擎在哪台机器上跑」——这几行字可以直接抄进交付记录。
powershell -ExecutionPolicy Bypass -File D:\ESP\tools\start_voice_engine.ps1

#    也可以手起（等价，但要自己保证模型目录对、语速别留默认值以外的东西）：
#    $env:VOICE_ASR_MODEL_DIR = "D:\ESP\.models\vosk-model-small-cn-0.22"
#    $env:VOICE_TTS_RATE = "1"
D:\ESP\.venv\Scripts\python.exe D:\ESP\backend\voice_engine.py

# ④ 检查引擎是否就绪
curl -s --noproxy '*' http://127.0.0.1:8013/health
```

> `curl` 记得带 `--noproxy '*'`：本机 `http_proxy` 会把 `127.0.0.1` 也代理出去（见 §12 **D3**）。
> 脚本内部已经把这条绕开了（`urllib` 用空 ProxyHandler）。

引擎不依赖外网：模型在本地、合成用系统语音。**断网也能识别和播报**（这一点在课堂上很好演示）。

## 3. 采样格式：为什么是 16 kHz / 16 bit / 单声道

| 参数 | 取值 | 理由 |
|---|---|---|
| 采样率 | **16000 Hz** | 人声有效频带上限约 8 kHz，按奈奎斯特定理 16 kHz 足够；vosk 中文模型就是按 16k 训练的 |
| 位深 | **16 bit** | PCM 信噪比约 96 dB，远超人声动态范围；模型输入也是 int16 |
| 声道 | **单声道** | 识别只用一路；双声道会让数据量翻倍且模型不认 |
| 容器 | **RIFF/WAVE + PCM** | 头 44 字节，任何端都能直接解析，**不需要解码器**（没有 ffmpeg 也能跑） |

### 3.1 前端为什么要主动重采样

`getUserMedia` 拿到的音频采样率由**系统/驱动**决定（常见 44.1k 或 48k），
不是你想要 16k 就是 16k。所以前端做了两步：

```js
// ① 请求 16k 上下文（浏览器多数会照做）
VOICE.ctx = new AudioContext({ sampleRate: 16000 });
VOICE.ctxRate = VOICE.ctx.sampleRate;   // ★ 以实际拿到的为准，不信"我请求了 16k"

// ② 如果实际不是 16k，线性插值重采样（和后端 resample_to_16k 同一套朴素做法）
const int16 = voiceResample16k(f32, VOICE.ctxRate);
```

界面上会如实显示：`采集 48000 Hz → 上传 16 kHz · 16 bit · 单声道`。
**"我请求了什么"和"我实际得到了什么"是两件事**，页面显示后者。

### 3.2 后端不"顺手帮你转"

如果上传 44.1k 立体声，后端**不会**自动转换后接受，而是 400 + 报出实际参数：

```json
{"code":"AUDIO_FORMAT_INVALID",
 "message":"只接受单声道，实际收到 44100 Hz / 16 bit / 2 声道 / format=1",
 "details":{"expected":{"sample_rate":16000,"bits":16,"channels":1,
                        "container":"RIFF/WAVE PCM"}}}
```

理由：**采样格式是本课要讲的知识点**。如果后端偷偷转换，"格式不对"就永远学不到，
而且转换本身会引入"到底是哪一段把音质弄坏了"的排查困难。
本工程的一贯做法是：**明确拒绝 + 说清实际值 + 给出期望值**。

## 4. 按键说话：录音这一段怎么实现

### 4.1 采集链路

```text
点击「开始说话」
  → getUserMedia({audio: {channelCount:1, echoCancellation, noiseSuppression, autoGainControl}})
  → MediaStreamSource ──► ScriptProcessorNode(4096) ──► destination
                              │ 每 4096 帧回调一次
                              ├─ 收集 Float32 样本
                              └─ 算实时 RMS（只用于电平条）
点击「结束说话」
  → 停止轨道、关闭 AudioContext
  → 拼接所有 Float32 → 重采样 16k → Int16 → 写 44 字节 RIFF 头 → Blob
  → POST /api/v1/voice/turn
```

### 4.2 三个必须踩过才知道的坑

**坑 1：`ScriptProcessorNode` 必须连到 `destination` 才会回调。**
不连就一个 `onaudioprocess` 都不触发，表现为"点了开始、进度条不动、结束没数据"。
它输出的缓冲是全 0，所以不会啸叫。

**坑 2：`AudioContext` 关闭之后 `sampleRate` 就读不到了。**
所以在 `close()` 之前把 `ctxRate` 存下来（`VOICE.ctxRate`），否则重采样会用错比率。

**坑 3：`getUserMedia` 的错误名要分开处理，因为它们对应完全不同的处置。**

| 错误名 | 真实原因 | 页面给出的下一步 |
|---|---|---|
| `NotAllowedError` | 权限被拒 | 到地址栏左侧允许麦克风，然后重试 |
| `NotFoundError` | 没有输入设备 | 直接用文字入口 |
| `NotReadableError` | 被别的程序占用 | 关掉占用麦克风的程序（会议软件） |

把三种都笼统写成"录音失败"是没用的——用户不知道下一步该干什么。

### 4.3 前端也会算 RMS，但只用于电平条

电平条是 `AnalyserNode` 之外的一条朴素实现：每块样本算一次 RMS。
它**只驱动进度条宽度**，页面上显示的 RMS 数值一律来自后端返回（`audio.rms`）。
理由：判定必须只有一个来源，否则"前端说有声、后端说无声"时无从裁决。

## 5. 六个可观察环节与六条红线

### 5.1 状态从哪来

`stages[]` 由 `voice_pipeline.handle_turn` 按实际执行顺序生成，前端只做渲染：

| # | key | 内容（全部是实测值） |
|---|---|---|
| ① | `recorded` | 字节数、SHA256、采样率、位深、声道、时长 |
| ② | `vad` | RMS、峰值、过零率、阈值、是否通过 |
| ③ | `asr` | 引擎名、模型名、耗时、识别文本（或失败原因） |
| ④ | `task` | 意图、claim、远端状态、证据来源、耗时 |
| ⑤ | `tts` | 引擎、语音名、耗时、产出音频字节、是否节选 |
| ⑥ | `playback` | 前端上报的"播放器开始播放"时间（服务端不预写） |

### 5.2 `final_state` 七类

| final_state | 触发条件 | 这一轮有没有文本 | 有没有执行任务 |
|---|---|---|---|
| `done` | 识别 + 任务 + 合成 全成功 | 有 | 有 |
| `no_speech` | VAD 判定无有效语音 | **无** | 无 |
| `asr_failed` | 识别引擎报错 | **无** | 无 |
| `asr_timeout` | 引擎超时未返回 | **无** | 无 |
| `asr_unavailable` | 引擎连不上 / 未配置 | **无** | 无 |
| `task_failed` | 识别成功但任务失败 | 有 | 失败 |
| `tts_failed` | 识别与任务都成功，只有合成失败 | 有 | 有（文字回答完整） |

> 注意 `task_failed` 和 `tts_failed` 的"有文本"——**这两类失败发生在链路的后半段，
> 前半段的成果必须保留**。否则用户明明看到识别对了，却因为合成挂了什么也拿不到。

### 5.3 六条红线（每条都有自动化断言）

#### V1 没有识别就没有文本

识别失败 / 超时 / 无声时，`transcript` **必须是 `null`**，数据库里也必须存 `NULL`（不是空串）。
绝不允许：关键字匹配猜一个、拿上一轮结果顶上、用规则"补"一句。

```python
# voice_pipeline.handle_turn
if not passed:                      # VAD 未通过
    asr_status = "skipped"          # ★ 根本不调 ASR
    transcript = None
```

前端对应实现（`web/app.js`）：

```js
const hasText = typeof v.transcript === "string" && v.transcript.length > 0;
if (!hasText) {
  trEl.textContent = "";            // ★ 必须清空，不能只把区块隐藏
  ...
}
```

**踩过的真坑**：一开始只写了 `result.classList.add("hidden")`，结果 DOM 里还留着上一轮的
识别文本——把面板重新展开、或直接用读屏软件，都会以为"这一轮也识别出了这句话"。
`tools/test_web_voice.js` 的 `[3][4]` 两节就是为这件事加的断言。

#### V2 语音入口与文字入口同源

`task` 段调的是 `nl_assistant.handle_query` —— **第 4 周的同一个函数、同一套工具、同一套 claim 分档**。
不允许为语音另写一套意图解析，否则同一句话在两条入口会得到不同结论。

```python
voice_pipeline.bind(
    nl_query=lambda payload: nl_assistant.handle_query(payload),  # 同一函数
    ...
)
```

#### V3 文字入口不被语音故障连带

引擎挂掉时，`POST /api/v1/nl/query` 必须仍然 200 且结论正确。
这一条靠**进程隔离**保证（引擎是独立进程），并有一条专门的断言（自检 F 段）。

#### V4 播放 ≠ 听到

服务端只记录 `playback_started_at_utc`（前端上报"播放器开始播放"这个**事实**），
不产生 `heard` / `delivered` / `已听到` 之类字段。

页面文案只有一句：**"播放器已开始播放（是否真的听到只能由现场判断）"**。
`test_web_voice.js` 里有一条**源码级**断言：`app.js` 里不许出现"已听到"这四个字。

#### V5 来源与位置必须记录

见 §2.1。缺 `audio_source` 或 `capture_location` 直接 400。

#### V6 采样格式必须校验并回报

见 §3.2。

## 6. 语音识别（ASR）

### 6.1 为什么选 vosk 小模型

三条路线都实测过（都在本机、同一段音频上跑）：

| 方案 | 结果 | 结论 |
|---|---|---|
| Windows 系统 SAPI 中文听写（`MS-2052-80-DESK`） | 「查看上次数据」→ **「他看上去瘦的」**，置信度 0.06 | ✘ 不可用。系统自带的是"命令式"识别器，中文听写质量很差 |
| faster-whisper（本地） | 依赖能装上，但模型要从 HuggingFace 下载，**握手超时**（≈500 MB 拿不下来） | ✘ 本机不可行 |
| **vosk 小模型（43.9 MB）** | 「查看上次数据」→ **「查看上次数据」** | ✔ 采用 |

vosk 的额外好处：模型加载只要 **184 ms**、单句识别 **0.5~0.7 s**、**完全离线**。
在课堂上"点一下就能出结果"，不用等网络。

### 6.2 实测识别质量（真实数据，不是挑好的例子）

用系统中文语音合成 6 句标准任务句，再喂给识别引擎（语速 rate=0）：

| 原句 | 识别结果 | 逐字一致 | 合成耗时 | 识别耗时 |
|---|---|---|---|---|
| 查看上次数据 | 查看上次数据 | ✔ | 529 ms | 670 ms |
| 重新采集一次 | 重新采集一次 | ✔ | 282 ms | 626 ms |
| 设备在线吗 | 设备在线吗 | ✔ | 275 ms | 371 ms |
| 最近三十分钟的数据 | 最近三十分钟的数据 | ✔ | 356 ms | 633 ms |
| **开发板在哪里** | **开发反在哪里** | ✘ 差一个字 | 355 ms | 610 ms |
| 今天天气怎么样 | 今天天气怎么样 | ✔ | 355 ms | 686 ms |

**5/6 逐字正确。** 而那一句差一个字的，恰好是最好的教学材料：

```text
识别结果：开发版在哪里   （语速 rate=1 时；rate=0 时是"开发反在哪里"）
第 4 周意图解析：intent=location · claim=no_evidence · status=insufficient_evidence
回答：「开发板在哪里」：这个问题我没法回答。本工程的数据包字段…
      不含任何位置、经纬度、GPS 或基站信息；缺少位置证据时我不会推断或生成坐标。
```

也就是说：**识别错了一个字，任务意图仍然被正确识别**。这说明"受限工具 + 意图白名单"
这套第 4 周的设计对 ASR 的少量字错是**有韧性**的——这比"识别 100% 正确"更接近真实工程。

> 同一段话在不同语速下识别结果可能不同（`rate=0` 是「开发反」，`rate=1` 是「开发版」）。
> 这不是 bug，是真实 ASR 的常态；所以记录里要存**识别原文**（`asr.raw_text`）与
> **规范化后文本**（`transcript`）两份，便于事后核对。

### 6.3 中文识别结果里的空格

vosk 中文会在词之间插空格：`"查看 上次 数据"`。规范化规则只有一条：

```python
re.sub(r"(?<=[\u4e00-\u9fff])\s+(?=[\u4e00-\u9fff])", "", t)   # 只合并"汉字之间"的空格
```

**只合并汉字之间的空格**，保留英文/数字之间的间隔（否则 `esp32 s3` 会变成 `esp32s3`，
那是另一种失真）。也**不做任何同义词改写**——那等于替识别引擎改答案。

### 6.4 备用路径：授权录音文件

录音设备故障时，页面上的「选择 WAV 文件」走这条：

```text
任意 WAV/MP3 → OfflineAudioContext(16 kHz) 解码（多声道真实混成单声道）
             → 重采样 16 k → 写 RIFF 头 → 走同一条上传路径
```

记录里的 `audio_source` 会是 `uploaded_file`，`capture_location` 会写清"来自文件"。
**识别、任务、合成三段都是真实的**，唯一不同的是"这句话不是现场对着麦克风说的"。

## 7. 任务执行：复用第 4 周

### 7.1 接线方式

```python
# backend/server.py
voice_pipeline.bind(
    db_path=DB_PATH,
    nl_query=lambda payload: nl_assistant.handle_query(payload),   # ★ 同一函数
    utc_now=utc_now_iso,
    voice_dir=VOICE_DIR,
)
```

走的是**进程内函数调用**，不是 HTTP 回环到自己的 `/api/v1/nl/query`。
这样做的两层好处：不会因为 `SENSOR_PORT` 改端口而失效；也避免多一次网络往返。

### 7.2 同一句话的两条入口对照（本周的"对照实验"）

命令：

```powershell
D:\ESP\.venv\Scripts\python.exe D:\ESP\tools\voice_probe.py --compare "查看上次数据" --device esp32s3eye-1C704C
```

实测输出（2026-10-23 10:30）：

```text
【语音入口】/api/v1/voice/turn
  识别文本 : 查看上次数据
  意图 : query_latest   claim : old_record   状态 : answered
  来源 : sensor_records.id=446399

【文字入口】/api/v1/nl/query
  输入 : 查看上次数据
  意图 : query_latest   claim : old_record   状态 : answered
  来源 : sensor_records.id=446409

【对照】
  意图     query_latest   query_latest   一致
  claim    old_record     old_record     一致
  状态     answered       answered       一致
  来源     …id=446399     …id=446409     不同

  ── 结论 ──
  ✔ 语义一致：意图 / claim / 远端状态三项完全相同 —— 语音只是换了一种输入方式。
  · 来源 id 不同是**正常的**：设备仍在 10 Hz 持续上传，两次查询之间确实来了新采样点，
    两次读到的都是各自当时「最新的一条」。这不是解析不一致，是数据在动。
    要做逐字对照，可以先点「暂停周期上报」，再依次跑两条入口。
```

> **这个"不一致"比"一致"更有价值**：它说明对照实验必须考虑"数据在动"这件事。
> 如果两条入口都返回同一个 id，反而要怀疑是不是有缓存或写死了。
> 页面上也有「⇄ 用文字入口问同一句」按钮，做同样的对照，并把差异标红/标绿。

## 8. 语音合成（TTS）

### 8.1 引擎与语音

Windows SAPI，中文语音 `Microsoft Huihui Desktop - Chinese (Simplified)`（系统自带，离线）。
合成一条 12 秒的音频约 **300 ms**，产出 WAV（22.05 kHz/16 bit/单声道，SAPI 默认格式）。

返回给浏览器的音频**原样落盘**并记 SHA256：
`backend/data/voice/<turn_id>_out.wav`，回放走 `GET /api/v1/voice/reply/<turn_id>.wav`。
回放时读的是**已经存下来的那一份文件**，不现场重新合成——否则"你听到的"就不是"那一轮产生的"。

### 8.2 播报为什么只念前几句

第 4 周的文字回答动辄 300~500 字（含设备 ID、采样时间、三轴数值、来源、状态）。
全文念出来实测 **64.3 秒**。听 64 秒的数字串，听完什么也记不住。

所以语音通道只念**回答的前 2 句（≤160 字）**，实测降到 **12.8 秒**。规则写死在
`voice_pipeline.speech_excerpt`：

```text
① 按句末标点（。！？!?；;）与换行切句，保留标点与换行
② 取前 2 句，且累计不超过 160 字
③ 只在句子边界处切 —— 绝不在字中间截断（那会改变语义）
④ 节选时末尾追加一句提示语「（完整回答见屏幕。）」
⑤ 只截断、不改写、不概括 —— 播报文本一定是原文的一个前缀
```

第 ⑤ 条是硬约束，自检里有专门断言：
**把播报文本去掉提示语后，原文必须以它开头**（严格 `startswith`）。

> 为什么不"让模型概括一下再念"：概括就可能编造。本周所有语音内容都必须能在文字回答里
> **逐字找到**。这条约束看起来保守，但它保证了"听到的"和"看到的"不会打架。

页面上如实标注：

```text
语音只念回答的前几句（原文前缀，未改写）；完整回答共 88 字，请看上面的文字。念出的是 26 字。
```

可用环境变量调整（`VOICE_TTS_EXCERPT_SENTENCES` / `VOICE_TTS_EXCERPT_CHARS` /
`VOICE_TTS_FULL=1` 播全文）。

## 12. 踩坑记录（真实发生，附修法）

### D1 系统自带中文听写不可用

- **现象**：`System.Speech.Recognition` 识别「查看上次数据」得到「他看上去瘦的」，置信度 0.06。
- **排查**：注册表确认系统装了 `MS-2052-80-DESK`（zh-CN）——引擎在，但它是命令式识别器，
  自由听写质量极差。
- **修法**：换 vosk 离线模型。**教训：识别质量要先用真实音频量一遍，别信"系统有中文引擎"就上。**

### D2 pythonnet 默认跑 coreclr，加载不到 System.Speech

- **现象**：`clr.AddReference("System.Speech")` 抛 `FileNotFoundException`。
- **原因**：pythonnet 3.x 默认用 .NET 8（coreclr），而 `System.Speech` 只存在于 .NET Framework 的 GAC 里。
- **修法**：按 GAC 绝对路径加载
  `C:\Windows\Microsoft.NET\assembly\GAC_MSIL\System.Speech\v4.0_4.0.0.0__31bf3856ad364e35\System.Speech.dll`。
  （最终这个方案没用上——因为 SAPI 听写质量不行，见 D1。）

### D3 本机代理把 127.0.0.1 也代理了，接口稳定 502

- **现象**：`curl 127.0.0.1:8013/health` 正常，但后端调引擎一直
  `HTTP Error 502: Bad Gateway`，`/api/v1/voice/health` 显示"引擎未就绪"。
- **原因**：环境变量里设了 `http_proxy`，`urllib` 默认连 127.0.0.1 也走代理。
- **修法**：`voice_pipeline` 建一个专用 opener：
  ```python
  _LOCAL_OPENER = urllib.request.build_opener(urllib.request.ProxyHandler({}))
  ```
  只影响"访问本机引擎"这一条路径；访问外部 ASR 服务仍走系统代理。
- **教训**：**"curl 好、程序不好"时先怀疑代理**。这个错误极容易被误判成"引擎没起"。

### D4 INSERT 有 44 个占位符对着 43 个列

- **现象**：`sqlite3.OperationalError: 44 values for 43 columns`，只在真的有请求时才炸。
- **修法**：把"列名 → 取值"写成一张表 `_COLS`，占位符由 `len(cols)` 生成。
  **手写一长串 `?` 一定会错**，而且错在运行期。

### D5 识别失败时只隐藏了结果区，DOM 里还留着上一轮的文本

- **现象**：`test_web_voice.js` 断言"页面上没有任何识别文本"失败，读到的是上一轮的「查看上次数据」。
- **危害**：把面板重新展开、或读屏软件，都会以为这一轮也识别出了这句话——**这是红线 V1 的实质违反**。
- **修法**：`!hasText` 分支里显式清空 `voiceTranscript / voiceAnswer / voiceAsrMeta / 意图 / claim`，
  并把播放器 `src` 也移除（否则点播放会播上一轮的音频）。

### D6 播报节选后换行被吃掉，读成一长串

- **现象**：`设备：esp32s3eye-1C704C采样时间：2026-10-23…` 粘成一句。
- **原因**：切句后对每段做了 `strip()`，把句子末尾的 `\n` 去掉了。
- **修法**：不对每段 strip，只在拼接后整体 strip。
  **换行就是"该停顿"的地方**，去掉就听不清了。

### D7 全量播报 64 秒

- **现象**：第 4 周的回答平均 300+ 字，全文念出来 64.3 秒。
- **修法**：只念前 2 句（≤160 字）→ 12.8 秒；并明确标注"节选，完整内容在屏幕"。
  规则见 §8.2，硬约束是"只截断不改写"。

### D8 `Start-Process` 直接抛「已添加项。字典中的关键字…」

- **现象**：写了个 `start_voice_engine.ps1` 一条命令起引擎，结果在自己机器上失败：

  ```text
  Start-Process : 已添加项。字典中的关键字:“HTTPS_PROXY”所添加的关键字:“https_proxy”
  ```

  而且连带 `Get-ChildItem Env:` 都报同一个错。
- **根因**：这台机器的进程环境里**同时存在大小写两份代理变量**（`HTTP_PROXY` 与 `http_proxy`、
  `HTTPS_PROXY` 与 `https_proxy`，值相同）——Git Bash 拉起的会话常这样。
  Windows 的环境变量块允许这种重复（变量名本来就不区分大小写），但 .NET 把环境块读进
  **不区分大小写的字典**时就会判定"键重复"，于是 `Start-Process`、`Get-ChildItem Env:` 全炸。
- **这不是脚本写错，是环境脏**。而且**从 PowerShell 侧删不掉**：实测
  `[Environment]::SetEnvironmentVariable("http_proxy", $null, "Process")` 之后，
  大小写两个名字读出来还是都在（写入不区分大小写，删除只命中其中一条）。
- **修法**（脚本里已实现，双路兜底）：
  1. 先照常试 `Start-Process`（干净机器走这条，行为最标准）；
  2. 捕获到这个特定异常时，**自己建 `ProcessStartInfo` 且不碰 `EnvironmentVariables`**
     ——子进程于是原样继承父进程环境块（重复键在环境块里是合法的，无害），
     再把 stdout/stderr 交给 Python 自己 `open(log,'a')` 重定向，日志一样能留。
  3. 顺手关掉 `$ProgressPreference`：非交互宿主里 `Invoke-WebRequest` 的进度条会把整段输出
     重绘一遍，看起来像"脚本打印了两遍"（纯显示问题，但极误导）。
- **教训**：**验证脚本本身也是被测对象**。一条命令起服务，必须在"环境不干净"的机器上真的跑一次，
  否则你验的只是自己那台机器。

### D9 客户端提前断开，日志里冒出"Exception occurred…"

- **现象**：引擎日志里偶发一整段 `ConnectionResetError: [WinError 10054] 远程主机强迫关闭了一个现有的连接`，
  栈顶在 `socketserver.handle_error`。看起来像引擎崩了，其实下一次请求照常 200。
- **根因**：探活（`GET /health`）和前端超时取消都会**让客户端先 close**；
  服务端 `rfile.readline()` 于是读到 0/抛 reset。HTTP/1.1 keep-alive 下这是正常收尾。
- **修法**：自定义 `ThreadingHTTPServer.handle_error`，把
  `ConnectionResetError / ConnectionAbortedError / BrokenPipeError / TimeoutError` 静默掉，
  其余异常照旧打印。
- **教训**：**日志里的"异常"要和"故障"分开**。把正常收尾当故障打印，会训练人忽略真故障。

## 13. 迁移：为个人项目选一种真正有操作价值的语音任务

本周的链路是通用的，换一个"任务"就能迁移到个人项目。选任务的三条判据：

| 判据 | 说明 | 反例 |
|---|---|---|
| **一句话能说清** | 语音天然是短的；需要多轮追问的任务不适合 | "帮我分析一下最近一周的数据趋势" |
| **有明确副作用边界** | 要么纯读（安全），要么是有限、可撤销的写 | "把所有旧数据删掉" |
| **失败可解释** | 失败了能说清"是没听清 / 没这台设备 / 服务挂了" | 任何"黑盒调用第三方"的任务 |

按这三条，本工程里已经可迁移的三类：

| 场景 | 语音说法 | 走哪条路 | 副作用 |
|---|---|---|---|
| 值班巡检 | "设备在线吗" / "查看上次数据" | `device_status` / `query_latest` | 无（只读） |
| 现场取证 | "重新采集一次" | `request_collect` | 一次真实采集（可追踪到 observation） |
| 夜间告警播报 | 由后端触发 TTS，念最近一条求助事件 | 不走 ASR | 无 |

**建议的个人项目选题**（三选一，都能在本周代码上直接改）：

1. **"念一下我今天的步数/久坐提醒"** —— 只读 + 定时触发 TTS，最适合当第一个迁移任务。
2. **"把这条记下来"** —— ASR 文本直接落一条 note 表（写入有边界、可删除、可追溯）。
3. **"刚才那条数据的合矢量是多少"** —— 读最新记录并只念一个数，播报天然很短。

不建议选的：需要多轮对话才能完成的任务、需要外部账号权限的任务、任何"删除/清空"类任务
（本周的工具白名单里也没有这类工具）。

## 14. 限制与如实说明

1. **音频不是现场人声**（`voice_probe.py` 的路径）。脚本用系统 TTS 合成后回灌，
   对应课程写明的**备用路径**"录音设备故障时用授权录音完成真实识别"。
   要补验"人对着麦克风说话"，请打开页面点「语音助手」→「点击开始说话」。
   **识别、任务、合成三段在两条路径上是同一套代码。**
2. **没有在 ESP32-S3-EYE 的板载麦克风上验证**。本周不以前提（§2.2）。
3. **识别率不是 100%**。实测 6 句里 5 句逐字正确、1 句差一个字（§6.2）。
   这个水平对"短指令 + 意图白名单"是够用的，对"自由听写长句"不够。
4. **"用户是否真的听到"无法由系统证明**。服务端只能记录"播放器开始播放"，
   是否听到必须现场判断（红线 V4）。
5. **播报是节选**。只念前 2 句、原文前缀，不改写（§8.2）。
6. **引擎只监听 127.0.0.1**。它是本机服务，不要暴露到公网；`/health` 只报
   "有没有密钥"，不报密钥值。
7. **模型文件不入库**。`.models/` 与 `backend/data/voice/` 已在 `.gitignore` 中忽略；
   复现时按 §2.3 重新下载。

## 16. 一次完整的复现步骤

```powershell
# 1) 起语音引擎（本机，离线）
D:\ESP\.venv\Scripts\python.exe D:\ESP\backend\voice_engine.py

# 2) 确认引擎
curl -s http://127.0.0.1:8013/health

# 3) 确认后端有语音路由（常驻后端已在 8000）
curl -s http://127.0.0.1:8000/api/v1/voice/health

# 4) 跑接口自检
D:\ESP\.venv\Scripts\python.exe D:\ESP\tools\selftest_voice.py

# 5) 跑前端自检
node D:\ESP\tools\test_web_voice.js

# 6) 真实链路：单句
D:\ESP\.venv\Scripts\python.exe D:\ESP\tools\voice_probe.py --say "查看上次数据" --device esp32s3eye-1C704C

# 7) 真实链路：两入口对照
D:\ESP\.venv\Scripts\python.exe D:\ESP\tools\voice_probe.py --compare "查看上次数据" --device esp32s3eye-1C704C

# 8) 浏览器里点一下「语音助手」，对着麦克风说一句（这一步只能人工做）
#    http://127.0.0.1:8000/ → 工具栏「语音助手」→ 点击开始说话 → 再点结束
```

第 6/7 步的产物全部落在 `evidence/voice_week5/`：
`<turn_id>.json`（完整记录）+ `_in.wav`（录音）+ `_out.wav`（播报音频），
`_out.wav` 可以直接双击播放，听到的就是这一轮真实合成的音频。

> **体积提醒（如实说明）**：一次完整跑（套件 5 句 + 无声 + 对照）会留下约 **15 MB** 的 wav。
> json 只有 0.2 MB，wav 是主要体积。这些 wav 是"这段音频确实被识别成这句话"的唯一硬证据，
> 所以默认保留、随仓库一起提交。如果只想留结论，可以只删音频、留 json：
>
> ```powershell
> Get-ChildItem D:\ESP\evidence\voice_week5\*.wav | Remove-Item   # 只删音频，json 全留
> ```
>
> 删掉之后 `<turn_id>.json` 里的 `audio.sha256 / audio.bytes / duration_ms / rms` 仍然在，
> **"有没有这段音频、多长、指纹是什么"这四件事不会因为删文件而失真**；
> 但接口层的 `GET /voice/audio/<id>.wav` 会 404（它读的就是落盘的那一份）。
