## 2. 数据流

```
OV2640 ──DVP(8bit)──> ESP32-S3 ──JPEG(片内压缩，不转码)──> POST /api/v1/cam/frame
                                                             │
                                              ┌──────────────┴──────────────┐
                                              │ 内存只保留"最新一帧"（不落库） │
                                              └──────────────┬──────────────┘
                                                             │
                      网页 GET /api/v1/cam/status（450ms）──> 帧号变了才取图
                      网页 GET /api/v1/cam/frame   ──────────> image/jpeg
```

拍照：

```
网页 POST /api/v1/cam/capture ─> 后端记一个待拍照标记（TTL 10s）
                                        │
        设备下一次上传预览帧的响应里带 {"capture": true}
                                        │
              设备切 UXGA(1600×1200) → 丢 2 帧等 AE 稳定 → 抓拍
                                        │
             POST /api/v1/cam/photo（原图 + SHA256）→ 落盘 + 入库
                                        │
        网页轮询 /api/v1/cam/photos 拿到新照片 → 显示缩略图 + 下载原图
```

### 为什么拍照指令"搭在帧上传的响应里"

- 设备在 NAT 后面，只能主动出站，没有现成的下行通道给拍照；
- 预览帧本来就在 5Hz 往返，响应里夹一个 bool 的时延 < 200ms；
- 不新增轮询任务、不改第 2 周已经验证过的指令状态机（拍照 ≠ 采集，混在一起会把回执语义搅乱）。

## 3. 硬件：引脚与"共用 I2C 总线"

引脚全部来自 Espressif 官方 ESP32-S3-EYE 原理图 / `esp-bsp`（`esp32_s3_eye`）：

| 信号 | GPIO | 信号 | GPIO |
|---|---|---|---|
| XCLK | 15 | PCLK | 13 |
| VSYNC | 6 | HREF | 7 |
| D0 / D1 / D2 / D3 | 11 / 9 / 8 / 10 | D4 / D5 / D6 / D7 | 12 / 18 / 17 / 16 |
| SIOD (SDA) | **4** | SIOC (SCL) | **5** |

★★ **GPIO4/5 与板载 QMA6100P 共用同一条 I2C 总线**（官方板就是这么接的）。

处理方式（`camera.c` 里写死，别改）：

```c
.pin_sccb_sda  = -1,      // 不自己建总线
.sccb_i2c_port = 0,       // 复用 IMU 在 I2C0 建好的 bus
```

`esp_camera_init()` 于是走 `SCCB_Use_Port(0)` 分支，OV2640(`0x30`) 与
QMA6100P(`0x12`) 挂在同一条总线上，互不覆盖。

> 如果改成传 `4/5` 让摄像头自己建 bus，会和 IMU 抢 GPIO4/5，
> 表现为"加速度计读不到"或"摄像头探测失败"（取决于谁后初始化）。

### 初始化顺序很关键

`camera_start()` 必须放在 **采样任务启动之前**（`main.c` 里已调整）：

采样任务以 10Hz 读写 `0x12`，如果摄像头在它之后初始化，SCCB 探测会与之竞争。
虽然实测这不是本次失败的原因（调整前后都是 `NOT_SUPPORTED`），但顺序仍按"初始化阶段独占总线"处理。

### 供电与复位（原理图 J4，24P FPC）

- `CAM_PWDN` 经 R63 10K 下拉到 GND ⇒ `0` = Normal（工作）
- `CAM_RESET` 经 R57 10K 上拉到 DOVDD_2V8 ⇒ `1` = Normal（不复位）

所以固件里 `pin_pwdn = -1`、`pin_reset = -1` 是**正确**的：硬件已固定在工作状态。

**供电是常开的，没有软件开关**（这一点很关键，排除"忘了使能摄像头电源"这类原因）：

| 电源 | 来源 | 使能 |
|---|---|---|
| `DOVDD_2V8` / `AVDD_2V8` | U8 = ME6211C28M5G-N（2.8V LDO） | EN 直接接 `VDD_3V3`，上电即输出 |
| `DVDD_1V5` | U7 = ME6211C15M5G-N（1.5V LDO） | EN 同样接 `VDD_3V3` |

J4（`FPC_24P_CAM`）信号引脚（左右两列是同一个网络在连接器两侧的标注）：

| 脚 | 网络 | 脚 | 网络 |
|---|---|---|---|
| 1 | NC1 | 13 | `XMCLK`（XCLK） |
| 2 | AGND | 14 | `DVP_Y8` (D6) |
| 3 | `I2C_SDA`（与 QMA6100P 共用，GPIO4） | 15 | DGND |
| 4 | `AVDD`（2.8V） | 16 | `DVP_Y7` (D7) |
| 5 | `I2C_SCL`（共用，GPIO5） | 17 | `DVP_PCLK` |
| 6 | `CAM_RESET` | 18 | `DVP_Y6` (D5) |
| 7 | `DVP_VSYNC` | 19 | `DVP_Y2` (D2) |
| 8 | `CAM_PWDN` | 20 | `DVP_Y5` (D4) |
| 9 | `DVP_HREF` | 21 | `DVP_Y3` (D3) |
| 10 | `DVDD`（1.5V） | 22 | `DVP_Y4` (D1) |
| 11 | `DOVDD`（2.8V） | 23/24 | NC2 / NC3 |
| 12 | `DVP_Y9` (D0) | | |

排线没插时，能够用万用表在**连接器焊盘**上直接量到：脚 4/11 应为 2.8V、脚 10 应为 1.5V、
脚 6 应为 2.8V（上拉）、脚 8 应为 0V。四个都对而 `0x30` 仍无应答 ⇒ 问题在模组/排线本体。

## 4. 固件实现（`firmware/src/camera.c/.h`）

| 项目 | 取值 | 说明 |
|---|---|---|
| 预览分辨率 | 320×240 (QVGA) | 一帧约 8~15KB，5fps ≈ 50KB/s |
| JPEG 质量 | 12 | 0~63，越小越清晰 |
| 拍照分辨率 | 1600×1200 (UXGA) | 只在点「拍照」时临时切换，拍完立刻切回 |
| 帧缓冲 | 2 个，位于 PSRAM | 内部 SRAM 装不下 UXGA 帧 |
| XCLK | 10MHz | OV2640 支持 6~27MHz；20MHz 也试过，结果相同 |
| HTTP | 独立 keep-alive 句柄 | 与 uploader 的 JSON 句柄分开，避免 Content-Type 互相污染 |

可靠性细节：

- 非 2xx 一律当作失败，**不静默吞掉**（令牌错会一直 401，日志会明确打出来）；
- 取帧失败时**不重发上一帧**（否则网页看到的是"卡住的旧画面"，比没画面更误导）；
- 拍照失败不拿预览帧冒充照片；
- 摄像头初始化失败只停用图像功能，采样/上传/远程采集/按键求助全部照常；
- **探测失败会自动重试**（5s → 10s → 20s → 30s，30s 封顶）：现场把 J4 排线插紧后
  最多等 30 秒画面自动出现，**不必断电重启**。每次都走完整的 `esp_camera_init` /
  `esp_camera_deinit`（库的 `fail:` 路径自己 deinit，XCLK 与 SCCB 都被释放），
  不会累积 LEDC 通道或 I2C 设备表；重试阶段只打一行 `摄像头重试仍失败`，不刷屏。
- 未就绪期间状态**持续上报**后端，所以后端重启后网页依然能拿到"探测失败 + 原因"，
  不会退化成含糊的"还没有画面"。

### 拍照为什么要"重建相机"（真机踩到的坑）

`esp_camera` 的帧缓冲与 DMA 节点是 `esp_camera_init()` 时按
`recv_size = width * height / 5` **一次性**分配好的。QVGA 建的是 16KB 级缓冲；
只调 `set_framesize(UXGA)` 时缓冲不会变大，于是 UXGA 的 JPEG（约 90KB）直接冲破缓冲：

```
W cam_hal: FB-OVF           ← 帧缓冲溢出
W cam_hal: NO-EOI - JPEG end marker missing
W cam_hal: Failed to get frame: timeout
W cam: UXGA 取帧失败（本次无照片，不补拍假的）
```

所以拍照的正确做法是 **deinit → 用 UXGA 重新 init → 抓帧 → 再 deinit → 用 QVGA 重建预览**。
实测日志（新板）：

```
I (17635) cam: 收到拍照指令 → 以 1600x1200 重建相机（DMA 缓冲要按目标分辨率重分配）
I (17725) cam_hal: Allocating 384000 Byte frame buffer in PSRAM
I (26385) cam: 照片已上传: 1600x1200, 89832 字节
I (26475) cam_hal: Allocating 15360 Byte frame buffer in PSRAM
I (26865) cam: 已恢复 320x240 预览
```

端到端约 **8.7 秒**（17635 → 26385 ms）：UXGA 每帧输出就接近 1 秒，外加丢 3 帧等 AE 稳定
和 90KB 图片上传。网页「拍照」按钮因此按 **20 秒**上限等待，不会误报失败。
代价是拍照期间预览会停约 9 秒（画面停在最后一帧），拍完自动恢复推流 —— 这是真实代价，
不做"边拍边推"的假象。

启动成功时串口必须出现（真机判据）：
```
I (16275) cam: 板载摄像头就绪：OV2640 (PID=0x26) 320x240 JPEG q12，目标 5 fps
I (16275) cam: 画面开始上传：320x240 JPEG @ 5fps → http://<host>/api/v1/cam/frame
```

## 5. 后端接口（`backend/server.py`）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/cam/frame` | 设备上传预览帧（body = 原始 JPEG，需 `X-Device-Token`） |
| POST | `/api/v1/cam/photo` | 设备上传照片（body = 原始 JPEG） |
| POST | `/api/v1/cam/state` | 设备启动时自报摄像头可用性（ready/pid/error） |
| GET | `/api/v1/cam/frame?device_id=` | 最新一帧 JPEG（`X-Frame-Seq/W/H/Bytes` 头） |
| GET | `/api/v1/cam/status?device_id=` | 帧元数据 + `camera` 自报状态 + `cameras[]`（全部设备）+ 照片数 |
| POST | `/api/v1/cam/capture` | 点「拍照」（`{device_id}`），无画面返回 409 |
| GET | `/api/v1/cam/photos?device_id=&limit=` | 照片列表（含 SHA256） |
| GET | `/api/v1/cam/photo/<id>.jpg` | 下载原图 |

设计约束：

1. **预览帧不落库**：5fps × 24h ≈ 43 万帧，写库没有意义。内存只保留最新一帧，
   服务重启后无画面，网页如实显示"还没有画面"，绝不回放旧帧。
2. **照片必须落盘 + SHA256**：它是用户主动触发的证据，要能逐字节核对。
3. **JPEG 完整性校验**：必须以 `FFD8` 开头、`FFD9` 结尾，否则 400 拒收
   （半截帧在网页上是裂图，比不显示更误导）。
4. **照片先写 `.part` 再原子改名**：避免下载端读到半截文件。
5. 二进制上传上限 2MB（`SENSOR_CAM_MAX_BODY`），与 16KB 的 JSON 上限互不影响。

## 6. 故障排查：`Detected camera not supported`

### 实测日志（当前板子）

```
I (3795) s3 ll_cam: DMA Channel=0
I (3795) cam_hal: cam init ok
E (3805) camera: Detected camera not supported.
E (3805) camera: Camera probe failed with error 0x106(ESP_ERR_NOT_SUPPORTED)
I (3825) cam: 诊断: I2C0 上应答的地址: 0x12（共 1 个）
W (3825) cam: 诊断: 总线上没有 0x30（OV2640 的 SCCB 地址）
```

读法：

- `cam init ok` = DVP/I2S 外设初始化成功（说明引脚配置、PSRAM 都没问题）；
- `Detected camera not supported` = `esp_camera` 对**所有已知传感器地址**做 `i2c_master_probe`，全部无应答；
- 扫描结果 `0x12`（QMA6100P）在线、`0x30`（OV2640）不在线
  ⇒ 总线/上拉/驱动都是好的，是**摄像头侧没有应答**。

### 硬件排查顺序

1. **主板上的 24P 摄像头 FPC 座（J4）**：翻开锁扣 → 排线插到底 → 扣紧。
   这是最常见原因（排线松/没插/装反）。
2. **摄像头模组是否在位**：ESP32-S3-EYE 的摄像头在**主板**上（不是 LCD 那块子板），
   通过 24P FPC 连接；确认模组没被拔掉。
3. **排线方向**：金手指朝向以官方模组为准，装反时通常表现为完全无应答。
4. **不用断电重启**：插好后等 ≤30 秒，固件会自动重新探测（串口出现
   `摄像头第 N 次自动重试成功` 紧随 `板载摄像头就绪：OV2640 (PID=0x26)`）。
   网页会从「摄像头未就绪」自动切到实时画面——刷新都不用点。
5. 若以上都对仍无应答：用万用表量 J4 的 `DOVDD_2V8` / `AVDD_2V8` / `DVDD_1V5`
   （模组供电），以及 SDA/SCL 对 3.3V 的上拉（应约 4.7k）。

> 网页此时会明确显示「摄像头未就绪：ESP_ERR_NOT_SUPPORTED」并提示检查 J4 排线，
> 而不是让用户误以为网页坏了 —— 这就是 `/api/v1/cam/state` 存在的意义。

### 坑：页面把"硬件原因"藏在了"还没有画面"后面

现场现象：设备在线、`/api/v1/cam/state` 也已经把 `ESP_ERR_NOT_SUPPORTED` 报上来了，
但网页仍显示「还没有画面 / 请确认 ① 固件已烧录第 4 周版本…」。

根因（两层，都修了）：

1. 前端在"全部设备"模式下请求 `GET /api/v1/cam/status` **不带 `device_id`**，
   而后端只在带了 `device_id` 时才返回 `camera` ⇒ `d.camera` 为 `null`，
   于是走了兜底文案。
2. 兜底文案本身把排查方向指错了（"确认固件已烧录"），而真相是硬件。

修法：

- 后端：不带 `device_id` 时返回 `camera` = 最近一次上报的那台，并新增 `cameras[]` 全量列表；
- 前端：`camera` → `cameras[0]` 两级回退；`ESP_ERR_NOT_SUPPORTED` 时直接把
  "只应答 0x12、没有 0x30、供电常开无开关"写进文案；
- 自检新增场景 5（`cameras[]` 回退），把这条路径钉住 —— 之前的用例只测了 `camera` 直传，
  所以这个 bug 是在真机页面上才暴露的。

## 8. 已知限制

- 预览帧率固定 5fps（`APP_CAM_PREVIEW_FPS`），为的是控制 VPS 带宽；
  局域网内可调到 10~15fps。
- 拍照会中断预览**约 9 秒**（deinit + UXGA 重建 + 丢 3 帧等 AE + 90KB 上传），
  拍完自动恢复；期间画面停在最后一帧，不做"边拍边推"的假象。
- 照片分辨率固定在 1600×1200（OV2640 的 UXGA）；若要更高只能换传感器。
- 帧不落库，服务重启后"最新一帧"为空（这是刻意的，避免回放旧画面）。
- 照片按设备分目录存于 `backend/data/photos/<device_id>/`，未做自动清理。
