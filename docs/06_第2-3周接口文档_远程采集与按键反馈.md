## 0. 设计红线（第 2 周核心问题的答案）

第 2 周的核心问题是：

> **点击「采集最新数据」，如何证明开发板做了新采集，而不是读取数据库里的旧值？**

本文用**三层互锁证据**回答，任意一层不成立就**不允许**显示「本次采集完成」：

| 层 | 证据 | 数据来源 | 判定字段 |
|---|---|---|---|
| L1 请求身份绑定 | 回传观测里带**本次请求的 `request_id` + `nonce`**，且与下发的完全相等 | 设备回传 | `observation.request_id` / `observation.nonce` |
| L2 新旧性判定 | 本次观测的 `(boot_count, seq_last)` **严格大于**下发时刻的基线快照 | 设备回传 | `baseline.boot_count/seq_last` |
| L3 时间性判定 | 设备采集时刻 `up_ms`/`ts_utc_ms` **晚于**后端下发时刻 | 设备 + 后端 | `dispatched_at_utc` |

**只要 L1 或 L2 或 L3 任一不成立** → 该观测被**拒收**（HTTP `409`），落 `rejected`
表留痕，请求**保持原状态**（通常继续等到 `timeout`），**绝不**回写成 `completed`。
这条规则就是当堂验证里的「旧记录不可改写为本次完成」。

**第二条红线（区分超时与硬件故障）**：
`timeout` 只表示「设备未在时限内回报」，**不等于**硬件故障。二者是**独立字段**：

- `requests.status = timeout` —— 请求维度的结论；
- `devices.last_status` + `device_events` —— 设备维度的事实（在线/离线/传感器错误码）。

页面上**禁止**把 `timeout` 渲染成「硬件故障」（见 §7.4 的文案映射表）。

**第三条红线（第 3 周）**：
**无远端回执时不得显示「对方已收到」。** 本地反馈（蜂鸣/灯光）只证明**本机已知晓自己按下了**，
远端可见性必须由服务端 `acked`/`accepted` 事件驱动（见 §8）。

## 1. 术语与整体链路

| 术语 | 含义 | 本工程对应物 |
|---|---|---|
| 刷新已存数据 | 只查库，不碰设备。返回已有记录 | `GET /api/v1/records`、`GET /api/v1/latest`（**第 1 周已有**） |
| 采集最新数据 | 下发指令让**设备当场读一次真实寄存器**，再把结果带回来 | `POST /api/v1/collect_requests`（第 2 周新增） |
| 请求 request | 一次「远程采集最新数据」任务，有唯一 `request_id` 与状态机 | `collect_requests` 表 |
| 回执 ack | **设备**对指令的接收确认（我收到了，我要开始采了） | `POST /api/v1/device/ack` |
| 观测 observation | **设备**当场采到并绑定了 `request_id` 的真实测量值 | `POST /api/v1/observations`、`observations` 表 |
| 完成条件 | L1∧L2∧L3 全部成立（§5.2）且后端落库成功 | `requests.status = completed` |
| 求助消息 help | 佩戴者按下按键产生的事件（第 3 周） | `POST /api/v1/help_events` |
| 回应 response | 查看者「我看到你了」的确认 | `POST /api/v1/help_events/<id>/response` |
| 取消 cancel | 佩戴者主动撤销求助 | `POST /api/v1/help_events/<id>/cancel` |

链路总览（第 2 周）：

```
Web 页面                后端 server.py                   设备固件
  │                        │                                │
  │ ①POST /collect_requests│                                │
  │───────────────────────►│ 落库 requests(status=submitted) │
  │◄──201 request_id ──────│                                │
  │                        │◄─②GET /device/commands?device_id ── 轮询(1Hz)
  │                        │──200 指令体(collect_now+nonce)──►│
  │                        │                                │ 读 QMA6100P 寄存器
  │                        │◄─③POST /device/ack(id,nonce) ──│ 立刻回执
  │                        │  status=acked                  │
  │                        │◄─④POST /observations ──────────│ 带 request_id+nonce+新seq
  │                        │  L1∧L2∧L3 校验 → status=completed
  │ ⑤GET /collect_requests/<id> （1s 轮询）                   │
  │───────────────────────►│  返回 status + ack + observation
  │◄── 状态徽标 + 真实数值 ─│
```

链路总览（第 3 周，叠加上去）：

```
佩戴者按键 ──► 按下瞬间本地反馈(蜂鸣+LED)  ← 断网也必须发生
      │
      ├─POST /help_events──► 后端 ──GET /device/commands──► 设备
      │                        │                              │
      │                        │◄── POST /device/ack ─────────┘
      │                        │
查看者打开页面 ◄── GET /help_events?status=open
查看者点「我看到了」──► POST /help_events/<id>/response（服务端事件）
      │                        │
      │                        └── 回执事件 ──► 设备轮询拿到 → 远端已收到 → LED 转绿
佩戴者点「取消」──► POST /help_events/<id>/cancel ──► 设备收到 → 灯灭+停止重复蜂鸣
```

## 2. 约定与公共部分

### 2.1 基址与认证

| 项 | 值 |
|---|---|
| 版本前缀 | `/api/v1` |
| 传输 | HTTP（本机联调）/ HTTPS（VPS）；沿用第 1 周 `APP_SERVER_URL` 与 TLS 校验策略 |
| 设备认证 | 请求头 `X-Device-Token: <令牌>`，与第 1 周 `SENSOR_TOKEN` / `APP_DEVICE_TOKEN` **同一套令牌**，不新增凭证 |
| Web 认证 | 教学环境沿用第 1 周（无登录）；若已加会话，则记为 `X-Operator`（可选，不改变协议语义） |
| 字符集 | `application/json; charset=utf-8` |
| 时间格式 | UTC ISO8601 带毫秒：`2026-10-08T05:49:30.462Z`；本地时间串沿用板端 `2026-10-08T13:49:29.337+0800` |
| 单调时钟 | 板端 `up_ms`（`esp_timer_get_time()/1000`），**仅设备侧可比**，跨重启不可比 → 必须配 `boot_count` |

> ⚠️ **`boot_count` 是必须项**：第 1 周已踩过坑——重启后 `seq` 从 1 重新开始
> （见 README「三方核对键 = boot_count + seq + 包内序号」）。第 2 周的新旧性判定
> **同样必须**带上 `boot_count`，否则「重启后的小 seq」会被误判成「旧数据」。

### 2.2 公共枚举

**指令类型 `command.type`**

| 值 | 周次 | 语义 | 期望设备动作 |
|---|---|---|---|
| `collect_now` | 2 | 立即采集一次最新数据 | 读一次传感器 → 回执 → 回传观测 |
| `pause_reports` | 2 | 暂停周期上报 | 停止周期上报任务，保留接收指令能力 |
| `resume_reports` | 2 | 恢复周期上报 | 重启周期上报任务 |
| `clear_alert` | 3 | 撤销本地求助反馈 | 关闭蜂鸣、指示灯回待机色 |
| `help_ack` | 3 | 告知设备「查看者已收到」 | LED 由「等待中」转为「已送达」颜色（**这是唯一允许显示「已收到」的来源**） |

**设备状态 `status`（设备维度，独立于请求维度）**

| 值 | 含义 | 判定依据（可核对） |
|---|---|---|
| `online` | 近 `DEVICE_ONLINE_WINDOW_S`(=15s) 内有任何请求 | 服务端收到设备请求的时间戳 |
| `offline` | 超过该窗口无请求 | 同上 |
| `sensor_error` | 设备自报传感器读取失败 | `device.health.sensor_ok = false` + `sensor_err` |
| `paused` | 周期上报已暂停 | 最近一条 `pause_reports` 回执 |

**请求状态 `requests.status`**（第 2 周状态机，见 §5.1）
`submitted` → `acked` → `collecting` → `completed`；旁支 `failed` / `timeout` / `rejected` / `cancelled`

**求助状态 `help_events.status`**（第 3 周，见 §8.2）
`created` → `uploaded` → `acked` → `viewed` → `responded`；旁支 `cancelled` / `unreachable` / `expired`

### 2.3 统一响应包裹

**成功**：`2xx`
```json
{ "ok": true, "server_time_utc": "2026-10-08T05:49:30.462Z", "data": { } }
```

**失败**：`4xx/5xx`
```json
{
  "ok": false,
  "server_time_utc": "2026-10-08T05:49:30.462Z",
  "error": { "code": "REQUEST_NOT_FOUND", "message": "request_id 不存在", "retryable": false }
}
```

**错误码表**

| HTTP | code | 触发条件 | 前端应显示 |
|---|---|---|---|
| 400 | `BAD_JSON` | 报文非法 JSON | 「请求格式错误」（属开发缺陷，非设备问题） |
| 400 | `MISSING_FIELD` | 缺必填字段（如 `request_id`/`raw`） | 「数据不完整，已拒收」 |
| 401 | `BAD_TOKEN` | `X-Device-Token` 不匹配 | 「设备令牌不匹配」 |
| 404 | `REQUEST_NOT_FOUND` | `request_id` 不存在 | 「该请求不存在或已被清理」 |
| 404 | `NO_DEVICE` | `device_id` 从未上报过 | 「设备未接入」 |
| 409 | `REQUEST_ALREADY_FINAL` | 请求已 `completed/failed/cancelled`，又来一个观测 | 「本次请求已结束，该观测被拒收」 |
| 409 | `REQ_ID_MISMATCH` | L1 失败：`request_id`/`nonce` 不等于下发值 | 「观测与本次请求不匹配，已拒收」 |
| 409 | `STALE_OBSERVATION` | L2/L3 失败：`(boot_count,seq_last)` 或时间戳表明是旧值 | 「这是一条旧观测，不能作为本次新采集」 |
| 409 | `DUPLICATE_BATCH` | 同一 `(request_id, boot_count, seq_first)` 重复提交 | 「重复上报，已忽略」 |
| 422 | `DEVICE_REJECTED` | 设备明确拒绝（如传感器故障） | 「设备拒绝执行：<原因>」 |
| 500 | `INTERNAL` | 服务端异常 | 「服务端异常，请重试」 |
| 503 | `DB_BUSY` | 数据库锁/写失败 | 「服务端繁忙，请稍后重试」 |

> `409` 一律**不改变请求状态**，只写 `rejected_observations` 留痕——这是「旧记录不可改写为本次完成」的落地点。

### 2.4 幂等与重复点击

| 场景 | 机制 | 结果 |
|---|---|---|
| 同一用户**双击**（<2s 两次相同点击） | Web 生成 `client_request_key`（同一意图恒定），后端在其上做幂等 | 返回**同一个** `request_id`，HTTP `200` + `deduplicated: true` |
| 用户**刻意连点两次**（>2s，或换了 key） | 生成两条独立请求 | 两条各自走状态机，**都留记录**；设备按接收顺序处理，后一条指令在回执里标注 `superseded_request_id` |
| 设备重复回执同一指令 | `ack` 幂等键 = `(request_id, attempt)` | 第二次返回 `200` + `deduplicated: true`，不新增行 |
| 设备重复回传同一批观测 | 幂等键 = `(request_id, boot_count, seq_first, seq_last)` | `409 DUPLICATE_BATCH`，不新增行 |

### 3.2 第 2 周新增表

```sql
-- 采集请求（一次点击 = 一行）
CREATE TABLE IF NOT EXISTS collect_requests (
  request_id        TEXT PRIMARY KEY,          -- UUIDv4，字符串；接受 B 方案下为确定性短 ID
  device_id         TEXT NOT NULL,
  sensor            TEXT NOT NULL,             -- 目标传感器，如 'qma6100p' / 'all'
  requested_by      TEXT,                      -- 操作者标识（教学环境可空）
  client_request_key TEXT,                     -- 幂等键（前端生成）
  status            TEXT NOT NULL,             -- submitted|acked|collecting|completed|failed|timeout|rejected|cancelled
  nonce             TEXT NOT NULL,              -- 32hex 随机数，与 request_id 一同下发/回传（L1）
  timeout_ms        INTEGER NOT NULL,          -- 由后端决定（不由前端随意指定）
  submitted_at_utc  TEXT NOT NULL,
  dispatched_at_utc TEXT,                      -- 后端把指令交给设备通道的时刻（L3 基准）
  acked_at_utc      TEXT,                      -- 设备回执到达时刻
  collecting_at_utc TEXT,                      -- 收到上机序号但尚无合法观测（可选中间态）
  completed_at_utc  TEXT,
  failed_at_utc     TEXT,
  deadline_utc      TEXT NOT NULL,             -- = dispatched_at_utc + timeout_ms
  attempt           INTEGER NOT NULL DEFAULT 0,-- 下发次数（含重投）
  failure_reason    TEXT,                      -- DEVICE_REJECTED|SENSOR_ERROR|NETWORK|CLIENT_CANCELLED|...
  error_code        TEXT,
  -- 下发时刻的基线快照：判新旧用（L2 基准）
  baseline_boot_count INTEGER,
  baseline_seq_last   INTEGER,
  baseline_uptime_ms  INTEGER,
  notes             TEXT
);
CREATE INDEX IF NOT EXISTS idx_creq_device_time ON collect_requests(device_id, submitted_at_utc DESC);
CREATE INDEX IF NOT EXISTS idx_creq_status      ON collect_requests(status, deadline_utc);

-- 设备回执（指令接收/开始执行/拒绝）
CREATE TABLE IF NOT EXISTS request_acks (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  request_id      TEXT NOT NULL,
  device_id       TEXT NOT NULL,
  ack_type        TEXT NOT NULL,   -- received|started|rejected|superseded
  ack_at_utc      TEXT NOT NULL,   -- 服务端接收时刻（权威）
  device_uptime_ms INTEGER,        -- 设备侧单调时间（参考）
  boot_count      INTEGER,
  attempt         INTEGER NOT NULL DEFAULT 1,
  reason          TEXT,
  detail_json     TEXT,
  remote_addr     TEXT,
  UNIQUE(request_id, ack_type, attempt)
);

-- 绑定请求的新观测（L1∧L2∧L3 通过后才写入）
CREATE TABLE IF NOT EXISTS observations (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  request_id        TEXT NOT NULL,
  nonce             TEXT NOT NULL,
  device_id         TEXT NOT NULL,
  record_id         INTEGER,        -- → sensor_records.id（逐点行的首行）
  upload_id         INTEGER,        -- → raw_uploads.id（逐字节原文）
  boot_count        INTEGER NOT NULL,
  seq_first         INTEGER NOT NULL,
  seq_last          INTEGER NOT NULL,
  sample_count      INTEGER NOT NULL,
  sensor            TEXT,
  ts_utc_ms         INTEGER,
  ts_local          TEXT,
  up_ms             INTEGER,
  value_json        TEXT NOT NULL,  -- 本次观测的结论值（如 magnitude_g / raw 三元组）
  freshness         TEXT NOT NULL,  -- new_monotonic|new_after_reboot
  verify_ok         INTEGER,        -- 沿用第 1 周自洽校验
  received_at_utc   TEXT NOT NULL,
  UNIQUE(request_id, boot_count, seq_first, seq_last)
);

-- 被拒收的观测（必须留痕，不允许静默丢弃）
CREATE TABLE IF NOT EXISTS rejected_observations (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  request_id      TEXT,
  device_id       TEXT,
  reason_code     TEXT NOT NULL,  -- REQ_ID_MISMATCH|STALE_OBSERVATION|DUPLICATE_BATCH|REQUEST_ALREADY_FINAL|...
  reason_detail   TEXT,
  claimed_json    TEXT NOT NULL,  -- 设备声称的内容，原样保存（可追溯）
  received_at_utc TEXT NOT NULL,
  remote_addr     TEXT
);

-- 设备状态与事件（timeout ≠ 硬件故障 的事实来源）
CREATE TABLE IF NOT EXISTS devices (
  device_id        TEXT PRIMARY KEY,
  last_seen_utc    TEXT,
  last_status      TEXT,      -- online|offline|sensor_error|paused
  last_boot_count  INTEGER,
  last_seq         INTEGER,
  periodic_enabled INTEGER NOT NULL DEFAULT 1,
  paused_at_utc    TEXT,
  notes            TEXT
);

CREATE TABLE IF NOT EXISTS device_events (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  device_id       TEXT NOT NULL,
  event_type      TEXT NOT NULL, -- boot|pause|resume|sensor_error|sensor_recovered|command_timeout|power_off
  event_at_utc    TEXT NOT NULL,
  detail_json     TEXT,
  source          TEXT           -- device|server|operator
);
```

## 4. 设备侧契约（板端 → 后端 / 后端 → 板端）

### 4.1 `POST /api/v1/device/commands/poll` —— 设备拉取待执行指令（第 2 周新增，走既有 HTTP 通道）

> **只新增一个应用层端点，复用第 1 周 `uploader_post_json` 同族的 HTTP 客户端与令牌**。
> 不引入 MQTT / WebSocket / 新端口 / 新协议——因为设备处于 NAT 后，且第 1 周已验证板子能主动出网。

**请求**（设备 → 后端，`1 Hz` 轮询）
```json
{
  "device_id": "esp32s3eye-1C701C",
  "boot_count": 808,
  "up_ms": 318340,
  "seq_last": 3190,
  "periodic_enabled": true,
  "health": { "sensor_ok": true, "wifi_rssi": -61, "free_heap": 182344 },
  "last_ack": { "request_id": "…", "attempt": 1 }
}
```
> `seq_last`/`boot_count` 让后端在为**下一条**指令生成基线快照时**天然带上设备当前进度**。
> `last_ack` 用于幂等对账（设备侧缓存最近 N 条回执，网络恢复后补发）。

**成功响应 `200`**
```json
{
  "ok": true,
  "server_time_utc": "2026-10-08T05:49:30.462Z",
  "data": {
    "commands": [
      {
        "request_id": "b7f1c2e0-9a44-4c1f-8f2a-0d5e6c7b8a91",
        "type": "collect_now",
        "nonce": "3f9a1c77b25e4d0aa6c8e1f40b7d2358",
        "sensor": "qma6100p",
        "timeout_ms": 15000,
        "issued_at_utc": "2026-10-08T05:49:30.300Z",
        "baseline": { "boot_count": 808, "seq_last": 3190, "uptime_ms": 318340 },
        "attempt": 1
      }
    ],
    "poll_after_ms": 1000
  }
}
```

**无指令时**：`data.commands = []`（**正常成功**，`ok:true`；不是 404，也不是错误）。

**设备处理规则**
1. 收到 `collect_now` → **立即**回执 `received`（§4.2），再执行采集；
   回执必须在 `min(1s, timeout_ms/3)` 内发出，否则后端按未回执计时。
2. 采集成功 → 立即 `POST /observations`（§4.3），并回执 `started`（可选，用于中间态）。
3. 采集失败（传感器读失败）→ 回执 `rejected` 且 `reason = SENSOR_ERROR`；
   **不允许**用任何构造值/上次值顶替（沿用第 1 周红线：读失败就如实报错）。
4. 若同一 `request_id` 收到第二次（重投）→ 幂等：**不重复采第二次**，
   直接重发上次的观测；回执 `attempt` 递增。
5. 若在队列里发现有更新的 `collect_now` 尚未处理 → 对旧指令回执 `superseded`
   （`reason = superseded_request_id`），只执行最新一条（防重复点击造成排队积压）。

**错误**：`401 BAD_TOKEN`；`400 MISSING_FIELD`（缺 `device_id`）。

### 4.2 `POST /api/v1/device/ack` —— 设备回执

**请求**
```json
{
  "request_id": "b7f1c2e0-9a44-4c1f-8f2a-0d5e6c7b8a91",
  "device_id": "esp32s3eye-1C701C",
  "ack_type": "received",
  "nonce": "3f9a1c77b25e4d0aa6c8e1f40b7d2358",
  "attempt": 1,
  "boot_count": 808,
  "up_ms": 318360,
  "reason": null,
  "detail": { "queue_len": 0, "battery_mv": 4200 }
}
```

| `ack_type` | 何时发 | 后端状态迁移 |
|---|---|---|
| `received` | 指令已解析并入队 | `submitted → acked` |
| `started` | 已开始读传感器 | `acked → collecting` |
| `rejected` | 明确拒绝（如 `SENSOR_ERROR`） | `→ failed`（**不是 timeout**） |
| `superseded` | 被更新的同类型指令取代 | 该请求 `→ cancelled`，`failure_reason=SUPERSEDED` |
| `help_ack` | 设备确认已收到「查看者回应」（第 3 周） | 写 `help_events.remote_acked_at_utc` |

**成功响应 `200`**
```json
{ "ok": true, "server_time_utc": "…",
  "data": { "request_id": "…", "status": "acked", "deduplicated": false } }
```

**规则**
- `nonce` 必须与下发一致，否则 `409 REQ_ID_MISMATCH`；
- 回执**只能前进不能倒退**（已 `completed` 的请求再来 `received` 视为幂等重复，`200` + `deduplicated:true`）；
- **回执 ≠ 完成**：`acked` 只证明设备收到了指令（这就是页面上「设备接收回执」这一状态的唯一来源），
  **不得**据此显示「采集完成」。

### 4.5 下行指令**只有一条通道**（重要边界）

**设备侧只暴露 4 个端点**，全部是设备主动发出的（`device` 前缀）：
`POST /device/commands/poll`、`POST /device/ack`、`POST /device/observations`、
`POST /device/reports`（§4.4）。**没有** `/device/help_ack` 这种"直接通知设备"的下行端点——
那些动作全部是**操作者侧端点**生成的**指令**，再由设备轮询取走
（注意 `POST /api/v1/device/pause` 虽然路径里带 `device`，但它是**操作者调用**的，
语义是"请该设备暂停"，不是设备上报）：

| 操作者动作 | 操作者侧端点 | 生成的指令 `command.type` | 设备取走方式 |
|---|---|---|---|
| 暂停/恢复周期上报 | `POST /api/v1/device/pause`（§6.5） | `pause_reports` / `resume_reports` | `commands/poll` |
| 查看者回应「我看到了」 | `POST /api/v1/help_events/<help_id>/response`（§7.2） | `help_ack` | `commands/poll` |
| 佩戴者取消求助 | `POST /api/v1/help_events/<help_id>/cancel`（§7.3） | `clear_alert` | `commands/poll` |
| 点击「采集最新数据」 | `POST /api/v1/collect_requests`（§6.1） | `collect_now` | `commands/poll` |

**关键推论**：任何「远端已收到」的结论都必须等设备把 `help_ack` 取走并回执
（`POST /device/ack`，`ack_type=help_ack`）之后才能写入 `remote_acked_at_utc`——
后台把指令"放进队列"**不算**送达（§7.4 红线的实现落点）。

### 4.6 板端落地要点（不改底层通信）

| 位置 | 改动 | 说明 |
|---|---|---|
| `firmware/src/app_config.h` | 新增 `APP_COMMAND_POLL_MS 1000`、`APP_HELP_DEBOUNCE_MS 1500`、`APP_BUZZER_GPIO`、`APP_LED_GPIO`、`APP_BUTTON_GPIO` | 部署参数，非测量数据 |

## 5. 请求状态机与「新采集」判定

### 5.1 状态机

```
                       ┌──────────────── 任意状态 ───────────────┐
                       │                                        │
  POST /collect_requests                                        │
        │                                                       │
        ▼                                                       │
   [submitted] ──ack:received──► [acked] ──ack:started──► [collecting]
        │                            │                          │
        │                            │        ┌─ 观测 L1∧L2∧L3 通过 ─► [completed]  (终态)
        │                            │        │
        │                            └────────┴─ ack:rejected ───► [failed]      (终态)
        │                                                              ▲
        │  deadline_utc 到期且未 completed/failed                      │
        └──────────────────────────► [timeout]  (终态)                 │
                                                                       │
   操作者撤销 ─────────────────────► [cancelled] (终态)                │
   观测被拒收(409) ────────────────► 状态不变（只写 rejected_observations）
   ack:superseded ─────────────────► [cancelled] failure_reason=SUPERSEDED
```

**终态集合**：`{completed, failed, timeout, rejected, cancelled}`。
终态后到达的观测一律 `409 REQUEST_ALREADY_FINAL`，**状态不改写**。

### 5.2 完成条件（三者同时为真）

| 检查 | 公式 | 失败码 |
|---|---|---|
| **L1 身份绑定** | `obs.request_id == req.request_id` **且** `obs.nonce == req.nonce` | `REQ_ID_MISMATCH` |
| **L2 新旧性** | `obs.boot_count > req.baseline_boot_count`（重启后采，`freshness=new_after_reboot`）<br>**或** `obs.boot_count == baseline_boot_count` **且** `obs.seq_first > baseline_seq_last`（`freshness=new_monotonic`） | `STALE_OBSERVATION` |
| **L3 时间性** | `obs.up_ms > req.baseline_uptime_ms`（同 boot）**或** `obs.boot_count > baseline_boot_count`（跨 boot）<br>且 `obs.received_at_utc >= req.dispatched_at_utc` | `STALE_OBSERVATION` |
| 附加 | `sample_count >= 1` 且每个 sample 含 `raw`（后端**绝不代为生成**，沿用第 1 周 400 规则） | `MISSING_FIELD` |

**通过后一次性写入（同一事务）**：
1. `raw_uploads` 存逐字节原文 + SHA256（沿用第 1 周）；
2. `sensor_records` 逐点落库（沿用第 1 周）；
3. `observations` 写绑定行（`record_id`/`upload_id` 指向前两者）；
4. `collect_requests` → `completed`，写 `completed_at_utc`。

### 5.3 超时判定（timeout ≠ 硬件故障）

| 量 | 定义 |
|---|---|
| `timeout_ms` | 后端决定：`collect_now` 默认 **15000**（可配 `COLLECT_TIMEOUT_MS`）；`help` 上传默认 **30000** |
| `deadline_utc` | `dispatched_at_utc + timeout_ms` |
| 扫描周期 | 后端定时任务每 **1s** 扫描 `deadline_utc < now` 且状态 ∈ `{submitted, acked, collecting}` → 置 `timeout` |
| 同时写 | `device_events(event_type='command_timeout', source='server')` |
| **不做** | 不把设备置为 `offline`，不写任何 `sensor_error`，不改 `devices.last_status` |

**页面文案映射（强制）**

| 后端事实 | 页面必须显示 | 页面**禁止**显示 |
|---|---|---|
| `requests.status=timeout` + 设备 15s 内有轮询（`online`） | 「**设备在线但未在 15s 内回报**（可能指令未执行/回报丢失）」 | ❌「设备故障」「传感器损坏」 |
| `requests.status=timeout` + 设备超 15s 无轮询（`offline`） | 「**设备当前离线**（可能关机/断网），本次请求超时」 | ❌「硬件故障」（离线含关机与断网两种，不得断言） |
| `ack_type=rejected` + `reason=SENSOR_ERROR` | 「**设备明确拒绝：传感器读取失败**」（这才是硬件问题） | ❌「超时」 |
| `requests.status=timeout` 且后续设备恢复并补传合法观测 | 「**已超时**」+ 另附「设备恢复后补传了一条观测（不作为本次完成）」 | ❌ 把它回写成「完成」 |

> 一句话总结给验收用：**超时是"没等到"，故障是"设备说了它坏了"**，
> 两者的证据来源不同（服务端计时 vs 设备回执），字段不同（`status=timeout` vs `failure_reason=SENSOR_ERROR`）。

| `rejected` | 请求被拒（未建立） | 灰红 | 创建时校验不过（如 `NO_BASELINE`） |
| `cancelled` | 已撤销 | 灰 | 操作者撤销 / `superseded` |

### 6.3 `GET /api/v1/collect_requests?device_id=&limit=&status=` —— 动作执行追踪

返回按 `submitted_at_utc DESC` 的请求列表（默认 `limit=50`，上限 `500`），
每项含 `request_id/status/提交/下发/回执/完成/超时时刻/被拒次数/observation 摘要`。
**用途**：当堂验证「重复点击追踪记录」——连点两次必须看到**两条**记录与各自终局。

### 6.4 `POST /api/v1/collect_requests/<request_id>/cancel`

操作者撤销未完成的请求 → `status=cancelled`，`failure_reason=CLIENT_CANCELLED`，
写 `device_events(source='operator')`，并（可选）下发 `clear_alert` 等同族指令。
终态请求调用 → `409 REQUEST_ALREADY_FINAL`。

### 6.5 `POST /api/v1/device/pause` —— 暂停/恢复周期上报（当堂验证用）

```json
{ "device_id": "esp32s3eye-1C701C", "enable": false, "reason": "当堂验证暂停周期上报" }
```
**响应 `200`**
```json
{ "ok": true, "server_time_utc": "…",
  "data": { "device_id": "…", "periodic_enabled": 0,
            "command_id": "pause_reports", "status": "pending_device",
            "note": "已排入设备指令队列，等待设备下一次组合轮询" } }
```
**核对**：轮询 `GET /api/v1/devices` 应看到 `periodic_enabled=0` 且周期包停止；
`collect_now` 仍能完成（证明"暂停的是周期上报，不是采集能力"）。

### 6.6 只读接口（沿用第 1 周 + 必要扩展）

| `GET /api/v1/records`（含 `after_id` 增量） | 不变 |

## 7. 第 3 周接口：按键求助与物理反馈闭环

### 7.1 `POST /api/v1/help_events` —— 设备上传求助（按键触发）

> **断外网也必须能本地识别按键**：设备先在本地完成反馈，再尝试上传；
> 上传失败时把事件留在本地队列（NVS/内存环形缓冲）**并标注 `local_feedback` 已发生**，
> 网络恢复后补传（补传时带 `trigger_up_ms` + `boot_count`，**不得伪造触发时间**）。

**请求**
```json
{
  "device_id": "esp32s3eye-1C701C",
  "help_id": "9c2d51ab-3f77-4b90-9f21-7c0a1b2c3d4e",
  "client_request_key": "btn-808-318440",
  "trigger_type": "button",
  "trigger_at_utc": "2026-10-08T13:49:31.437+0800",
  "trigger_up_ms": 318440,
  "boot_count": 808,
  "queued_at_utc": "2026-10-08T13:49:31.437+0800",   // 设备首次尝试上传的时刻；断网滞留时与 trigger_* 不同
  "local_feedback": "buzzer+led",
  "local_feedback_at_utc": "2026-10-08T13:49:31.437+0800",
  "message": null,
  "pending_local": false          // true = 断网期间产生、现在补传
}
```

**响应 `201`**
```json
{ "ok": true, "server_time_utc": "…",
  "data": { "help_id": "9c2d51ab-…", "status": "uploaded",
            "remote_ack_required": true,
            "notice": "本地反馈已发生；远端可见性待查看者回应" } }
```

**幂等**：同一 `client_request_key`（设备侧按键去抖键 = `boot_count + trigger_up_ms` 舍入到去抖窗口）
重复上传 → `200` + `deduplicated: true`，不产生第二条。

**⚠️ 时间字段口径表（唯一口径，实现与用例都必须照此判定）**

第 3 周有 5 个"看起来都在说时间"的字段，**来源不同、可比范围不同**，
混用会直接导致"滞留 5 分钟被显示成刚按下"或"拿单调时钟减墙上时钟"这类错误：

| 字段 | 来源 | 格式 | 可为 NULL | 单调/可比范围 | 唯一用途 |
|---|---|---|---|---|---|
| `trigger_at_utc` | **设备侧** SNTP 已对时 | 带时区本地串，如 `2026-10-08T13:49:31.437+0800` | 是（未对时） | 墙上时钟，与 `server_time_utc` 可比 | 佩戴者的**真实触发**时刻 |
| `trigger_up_ms` | **设备侧** `esp_timer_get_time()/1000` | 整数毫秒 | 否 | **单调时钟，只在同一 `boot_count` 内可比** | 断网时唯一可靠时间；算**本地反馈时延** |
| `queued_at_utc` | **设备侧**首次尝试上传的时刻 | 同上本地串 | 是 | 墙上时钟 | 算断网滞留的真实 `age_ms` |
| `local_feedback_at_utc` | **设备侧**本地反馈**实际发生**的时刻 | 同上本地串 | 是（未对时） | 墙上时钟 | **证明本地反馈已发生**及反馈时延 |
| `local_feedback_received_at_utc` | **服务端**收到该事件的时刻 | UTC ISO8601 `…Z` | **否**（永远非空） | 墙上时钟 | 服务端侧口径与未对时兜底 |

**硬性判定规则**：
1. **`local_feedback_at_utc` 是设备侧时间**（与请求示例一致），**不是**"服务端收到时刻"——
   服务端收到时刻一律看 `local_feedback_received_at_utc`。两者**不得互相替代**。
2. 本地反馈时延 = `local_feedback_at_utc - trigger_at_utc`（都来自设备侧，口径一致）；
   设备**未对时**时这两个字段均为 `null`，此时改用
   `local_feedback_at_utc` 无法求得 → 用串口 `up_ms` 差值核对（见 `docs/08` 实体反馈用例）。
3. **禁止**用 `trigger_up_ms` 与任何 `*_at_utc` 相减（单调时钟 ≠ 墙上时钟，跨重启更不可比）。

### 7.2 `POST /api/v1/help_events/<help_id>/response` —— 查看者回应「我看到了」

```json
{ "actor": "viewer-b", "message": "已通知值班同学" }
```
**响应 `200`**
```json
{ "ok": true, "server_time_utc": "…",
  "data": { "help_id": "…", "status": "responded",
            "responded_at_utc": "…", "remote_ack_command": "help_ack",
            "remote_acked_at_utc": null,
            "note": "已记录回应，并已向设备下发 help_ack；设备确认后 remote_acked_at_utc 才会写入" } }
```
**关键**：此响应**不代表**设备已知晓。`remote_acked_at_utc` 只在设备通过
`POST /api/v1/device/ack`（`ack_type=help_ack`）确认后写入。

### 7.3 `POST /api/v1/help_events/<help_id>/cancel` —— 取消

```json
{ "actor": "wearer-a", "reason": "误触" }
```
**响应 `200`**
```json
{ "ok": true, "server_time_utc": "…",
  "data": { "help_id": "…", "status": "cancelled", "cancelled_at_utc": "…",
            "device_command": "clear_alert",
            "note": "已下发 clear_alert；设备收到后停止蜂鸣并复位指示灯" } }
```

**取消逻辑定义（第 3 周理论部分要讲清的四条）**

| # | 规则 |
|---|---|
| C1 | 取消**只有佩戴者侧**可发起（`actor` 需匹配 `accepted_by` 之外的角色，教学环境以操作者声明为准） |
| C2 | 取消**可在任何非终态**发起：`created/uploaded/acked/viewed/responded` → `cancelled` |
| C3 | 取消**不删除**任何记录（`help_events` 与 `help_actions` 全留痕，`cancel_reason` 必填） |
| C4 | 已经完全结束的求助（`cancelled`/`expired`）再次取消 → `200` + `deduplicated: true`（幂等，不报错） |

### 7.4 `GET /api/v1/help_events?device_id=&status=&limit=` —— 查看者列表

每项含：`help_id/status/trigger_type/trigger_up_ms/trigger_at_utc/queued_at_utc/received_at_utc/
local_feedback/local_feedback_at_utc/local_feedback_received_at_utc/pending_local/
viewed_at_utc/responded_at_utc/remote_acked_at_utc/accepted_by/cancel_reason/age_ms`。
（时间字段口径以 §7.1 的口径表为唯一标准。）

**`age_ms` 的算法（不得用错，否则会把"滞留 5 分钟"显示成"刚按下"）**

| 事件类型 | `age_ms` = | 理由 |
|---|---|---|
| 正常在线事件（`pending_local=false`） | `now - received_at_utc` | 上传几乎即时，接收时刻≈触发时刻 |
| 断网滞留后补传（`pending_local=true` 且 `queued_at_utc` 非空） | `now - queued_at_utc` | 设备首次尝试上传的时刻，才反映佩戴者真实等待时长 |
| 滞留补传但设备时钟已对时（`trigger_at_utc` 非空且可信） | `now - trigger_at_utc` | 最精确；仅在设备 SNTP 已同步时采用 |

> **禁止**用 `trigger_up_ms` 直接减服务端时间（单调时钟与墙上时钟不可比，跨重启更不可比）。

**「已收到」显示规则（第 3 周红线）**

| 事实 | 查看者页面 | 佩戴者设备本地 |
|---|---|---|
| 仅 `local_feedback` 发生（无任何服务端回执） | 若列表能看到该事件 → 显示「**佩戴者已按键**（待回应）」，**禁止**显示「对方已收到」 | 蜂鸣 + LED 橙色「等待中」 |
| `status=responded` 但 `remote_acked_at_utc == null` | 显示「**我已回应，等待设备确认**」，仍**禁止**显示「对方已收到」 | 仍为橙色「等待中」 |
| `remote_acked_at_utc != null`（设备已 ack `help_ack`） | 可显示「**佩戴者设备已收到回应**」 | LED 转绿色「已送达」，蜂鸣停 |

> 实现约束：前端**只能**依据 `remote_acked_at_utc` 渲染「对方已收到」，
> 不允许依据 `status=responded` 或本地计时器推断（对应测试用例 `TC-W3-09/10`）。

### 7.5 本地反馈与远端显示差异（理论要点，写成对照表）

| 环节 | 发生位置 | 依赖外网 | 证据 |
|---|---|---|---|
| 按键识别 + 本地确认 | 佩戴者设备 | **否** | 串口 `[HELP] local feedback done`；蜂鸣/LED 物理现象 |
| 上传到 VPS | 设备 → 后端 | 是 | 后端 `help_events.received_at_utc` |
| 查看者看到 | 后端 → 查看者浏览器 | 是 | 页面列表出现该 `help_id` |
| 查看者回应 | 查看者 → 后端 | 是 | `help_actions(action='responded')` |
| 设备确认已收到回应 | 后端 → 设备（`help_ack`）→ 设备 ack | 是 | `help_events.remote_acked_at_utc` |
| 取消 | 佩戴者 → 后端 → 设备（`clear_alert`） | 是 | `help_actions(action='cancelled')` + 设备 ack |

## 8. 不复用第 1 周能力的地方（明确边界）

| 项 | 决定 | 原因 |
|---|---|---|
| 底层 Wi-Fi / TLS / SNTP / HTTP 客户端 | **完全复用**，一行不改 | 需求明确「不做底层通信」 |

| 真实数据红线 | 沿用（无随机数、读失败就报错、缺 `raw` 就 400） | 第 1 周已写进 README |
| 紧急电话 / 真实呼救 | **不接**，仅教学接收端 | 需求「不接真实紧急电话」 |

## 9. 兼容性与迁移

1. 后端启动时执行 `SCHEMA` + `MIGRATIONS`（沿用 `server.py` 既有机制），**幂等**，
   已有 1.7 万条历史记录不需要任何转换。
2. `POST /api/v1/ingest` **保持完全不变**（第 1 周固件不升级也能继续跑）。新链路走
   `/api/v1/device/reports`。这样"第 1 周工程"与"第 2/3 周工程"可以**同时在线**，
   便于对比演示「旧固件只能周期上报，新固件能远程按需采集」。
3. `sensor_records` 加列（幂等）：
   ```sql
   ALTER TABLE sensor_records ADD COLUMN request_id TEXT;      -- 可空：周期包为 NULL
   ALTER TABLE sensor_records ADD COLUMN report_mode TEXT;     -- periodic|manual
   ```
   便于直接按 `request_id` 在原始点表里追溯本次观测。
4. 回滚：停用新端点即可回到第 1 周行为；新表可保留（只增不减，不影响旧查询）。
