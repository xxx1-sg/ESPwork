# 04 · 三方核对验证

任务要求「开发板串口打印的硬件实测值、VPS 数据库原始存储记录、网页显示数值三者保持一致」。
本文给出**可复现的操作步骤 + 自动化脚本**，把这件事变成一条命令。

---

## 1. 三方分别是什么

| 方 | 来源 | 获取方式 |
|---|---|---|
| ① 板端实测 | QMA6100P 寄存器 → 固件换算 → 串口打印 | `tools/serial_watch.py` 抓串口日志里的 `[DATA]` 行 |
| ② 数据库原始记录 | 后端落库的 `sensor_records` / `raw_uploads` | 直接 `sqlite3` 查库（或 `tools/analyze_db_rate.py`） |
| ③ 网页数值 | 网页调用的 `GET /api/v1/latest`、`GET /api/v1/records`、`?after_id=` 增量 | 脚本查询同一批接口 |
| ④ 前端实测（补充） | 真实 `web/app.js` 跑在真接口上 | `node tools/live_web_probe.js` |

补充：串口里的 `[POST]` 行打印的是**后端存库后回读的响应体**，
也就是说 ① 和 ② 的对照在串口日志里就能看到。

---

## 2. 一条命令完成核对

```powershell
# 1) 抓一段串口日志（板子正在上传时；注意抓串口一定会复位板子一次）
python D:\ESP\tools\serial_watch.py --port COM5 --seconds 70 --out D:\ESP\evidence\serial_run.log

# 2) 自动比对三方（键 = boot_count + seq + 包内序号 sample_idx）
python D:\ESP\tools\verify_three_way.py ^
    --serial D:\ESP\evidence\serial_run.log ^
    --db     D:\ESP\backend\data\sensor.db ^
    --api    http://127.0.0.1:8000 ^
    --out    D:\ESP\evidence\verify_report.json

# 3) 网页侧自检（DOM 是否齐全 / 有无兜底假值 / 接口字段是否齐全 / 增量接口）
python D:\ESP\tools\check_web_contract.py --api http://127.0.0.1:8000

# 4) 前端行为自检 + 实时探针（不需要浏览器）
node D:\ESP\tools\test_web_stale.js
node D:\ESP\tools\live_web_probe.js --seconds 15

# 5) 数据密度（零干扰观察：只读数据库，不复位板子）
python D:\ESP\tools\analyze_db_rate.py --minutes 10
```

> 为什么用 `serial_watch.py` 而不是直接开串口：打开 ESP32-S3 的 USB-Serial-JTAG 会让芯片复位、
> USB 随之重新枚举，刚打开的句柄会立刻失效。普通工具在这时会报
> `ClearCommError failed (PermissionError(13, …))` 且抓不到任何数据；
> `serial_watch.py` 用「第一次打开触发复位、第二次打开稳定读取」的策略规避，并把
> 复位原因一并记进日志（排查"板子是不是在自己反复重启"时很关键）。
> **但要注意：它仍然会复位板子**（`rst:0x15 USB_UART_CHIP_RESET`），所以"长时间稳定性"
> 别用串口看 —— 用 `analyze_db_rate.py` 只读数据库，它是零干扰的。

> 核对键请用 **(boot_count, seq, sample_idx)**：
> 1) 开发板每次重启 `seq` 都从 1 开始，只按 `seq` 比对会把不同次开机的数据串到一起；
> 2) 现在一包里有 10 个采样点（网络慢时还会把几个包合并成一次请求），
>    所以同一个 `seq` 不再等于"一包"，必须再带上包内序号 `sample_idx`（串口里的 `idx=K/N`）
>    才能与数据库 `sample_idx` 一一对应。

输出示例（每行是一个**采样点**的比对结果）：

脚本判定规则（任一不满足即 FAIL，并指出是哪一方不一致）：

- `raw.x/y/z` 三方完全相同（原始码值是整数，必须精确相等）
- `accel_g.x/y/z`、`magnitude_g` 三方误差 ≤ 0.0006 g
- `accel_ms2.*` 三方误差 ≤ 0.0051 m/s²（**串口日志只打印 2 位小数**，这是显示精度差，不是数据差）
- `ts_local`（设备本地时间戳）三方完全一致；若相差 ≤ 5ms 只给"提示"而不判失败
  （新固件已做到每采样点只取一次时间，串口与报文里的时间戳完全相同）
- 旁证：串口 `[POST]` 行里的服务器回显必须为 `http=201`，且其 `stored` 数值等于 ①②
  （一次请求合并了多个包时，回显只带**本包最后一个采样点**，工具会按
  `(seq, sample_idx)` 或原始码值把它对回正确的那个点）
- ③ 还额外检查 `sample_idx` / `sample_count` / `sample_period_ms` 字段与数据库一致，
  以及 `?after_id=` 增量接口"只返回锚点之后、按 id 升序"—— 网页就是靠它保证不丢样本的

真实核对输出示例见 [docs/05](05_真实硬件采集记录样例.md) 第 5 节（8/8 全部一致）。

## 3. 手工核对（不相信脚本时）

```powershell
# ① 串口：看重放的最新一行 [DATA] 与 [POST]
python D:\ESP\tools\serial_watch.py --port COM5 --seconds 15 --only-data

# ② 数据库：直接查原始存储记录（10Hz 下多了 sample_idx/sample_count 两列）
sqlite3 D:\ESP\backend\data\sensor.db ^
  "SELECT id,boot_count,seq,sample_idx,sample_count,raw_x,raw_y,raw_z,gx,gy,gz,magnitude_g,ts_local,received_at_utc FROM sensor_records ORDER BY id DESC LIMIT 3;"

# ③ 接口：网页读的就是这个
curl http://127.0.0.1:8000/api/v1/latest
curl "http://127.0.0.1:8000/api/v1/records?limit=3"
```

三处的 `raw`、`g`、`ts_local` 应当逐位一致。

> 说明：网页上的「实时数值」就是 ③ 的 `record.accel_g` / `record.raw` 字段，
> 页面不会做任何二次计算（`magnitude_g` 也是后端直接返回的板端计算值）。
> 卡片数值取的是**最近一个批次里最新那个采样点**，详情栏还会显示
> 「包内第 K/N 点」，可以直接对上串口 `[DATA]` 行的 `idx=K/N`。

## 4. 断流验证（页面必须保留时间戳 + 提示「暂无新数据」）

1. 让板子正常上传 10 秒以上，确认网页数值在跳动，记下页面显示的「服务器接收时间」。
2. **拔掉开发板电源**（或关掉手机热点）。
3. 观察网页（默认 2 秒轮询、超过 6 秒无新数据判定断流）：
   - 顶部出现红色提示条：**⚠️ 暂无新数据**
   - 提示条里保留最后一次采集时间 + 设备本地时间戳 + 「已停止更新 xx 秒」
   - 数值区变灰（视觉上明确不是实时值），但**上一次的真实数值和时间戳不会被清空**
   - 状态胶囊从「数据实时」变为「暂无新数据」
4. 重新上电，数值自动恢复跳动，提示条消失。

对应实现位置：`web/app.js` 的 `updateFreshness()`；
采样阈值可用 URL 参数调整，例如 `/?stale=3000&poll=500`。

**不用真拔电也能立刻验证**（推荐先跑这个）：用打桩 DOM 直接执行真实的 `web/app.js`，

## 5. 常见"对不上"的原因

| 现象 | 原因 |
|---|---|
| 数据库有数据，串口没有 | 抓串口时板子已经在跑，串口日志没覆盖到那几条；重新抓即可 |
| `ts_local` 串口与数据库不同 | 板子中途重启/重新对时，`seq` 从头开始；核对时用同一 `boot_count` 的区间（脚本已按 boot+seq+idx 匹配） |
| 串口和数据库都有数据，但"共同 (boot,seq,sample_idx) 0 组" | 日志与数据库不是同一次上传（抓串口会复位板子，重启后 `seq` 从头开始，`boot_count` 也变了）；重新抓一次即可 |
| g 值差 0.001 左右 | 浮点显示位数差异（串口保留 3 位小数），脚本容差已放宽到 0.0006 |
| `accel_ms2` 差 0.005 左右 | 串口只打印 2 位小数，属显示精度差；脚本容差 0.0051 |
| 板子约 1 秒重启一次、串口断在 `wifi_init` 后 | USB 口供电不足导致 brownout；固件已把 Wi-Fi 发射功率降到 8dBm 缓解（见 docs/05 第 8.4 节） |
| 板子反复重启且串口出现 `Guru Meditation … LoadProhibited` | 固件跑飞（内存越界等），用 `riscv32-esp-elf-addr2line` 解调用栈定位；本轮真踩过一次（见 docs/05 第 8.10 节） |
| 数据密度只有 2~3Hz 且偶尔有几十秒空洞 | 上传把采样卡住了（单循环固件）；现已拆成采集/上传两个任务，并用 `analyze_db_rate.py` 观察真实密度 |
| 接口返回 404 | 数据库里确实没有记录（设备没上传成功），不是页面问题 |
| `verify_ok=0` | 后端用 `raw/lsb_per_g` 重算与板端上报不一致，说明量程/灵敏度配置有出入 |
| 上传一直失败 | 看 `[POST]` 行的 http 状态：401 = 令牌不一致；其它 = 网络/地址问题 |
| HTTPS 握手失败 `-0x3000` | 服务器 CA 不在 IDF 内置根证书包；用 `tools/gen_ca_header.py` 内嵌真实 CA（见 docs/05 第 8.2 节） |
| 隧道域名解析到奇怪的 IP、cloudflared 报 `context deadline exceeded` | 本机 DNS 被投毒；用 `Resolve-DnsName api.trycloudflare.com -Server 223.5.5.5` 比对确认。此时改用同网段直连更省事 |
