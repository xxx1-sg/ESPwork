# 第 6 周：让语音任务可以澄清与停止

> **这是第六周的任务交付。**
> 分支：`feature/week6-voice-clarify-stop`
> 技术细节见 [docs/14_第6周_让语音任务可以澄清与停止.md](docs/14_第6周_让语音任务可以澄清与停止.md)

---

## 一句话说明

第 5 周已经做到"说一句话 → 听到回答"。本周解决的是**跑通之后立刻会遇到的三个问题**：

```
听不准怎么办？   →  先问一句，最多问两轮，问到上限给退路（不硬猜）
想中途停下怎么办？ →  三种"停"分开处理，任务与播报各管各的
停下之后那个还在路上的结果怎么办？ → 服务端硬拦截，绝不让它播出来
```

---

## 本周要回答的问题

> **系统听错了、用户改变主意或回答迟到时，如何保持交互连续？**

拆成三件可验证的事：

| 场景 | 本周的处理 | 怎么证明做到了 |
|---|---|---|
| 用户说"停" | 取消本轮，后续步骤一行都不执行 | 任务段状态是 `skipped`，且数据库里没有新增指令 |
| 用户改变主意后又说了新的一句 | 旧结果被顶掉，不许覆盖新结果 | 旧轮次 `superseded`，它的播报拿不到 |
| 旧结果姗姗来迟 | 服务端拦下，前端也丢弃 | 返回 `410 Gone`，音频存在但不给 |
| 一句话有歧义 | 反问一句，用规则消解，不猜 | 反问轮不调用任何业务工具 |
| 用户想听重点 | 停止播报，但任务结果保留 | 终局仍是 `done`，只记"停在第几毫秒" |

---

## 交付了什么

### 1. 三种"停"是三个不同的动作

这是本周最容易做错的地方：**"停"不是一个按钮，是四个**。区别不在界面，而在"任务有没有跑过、音频有没有合成过、还允不允许播"。

| 动作 | 什么时候 | 对任务的影响 | 对播报的影响 | 最终状态 |
|---|---|---|---|---|
| **放弃录音** | 还在录，没上传 | 任务不存在 | 无 | 不留记录 |
| **取消本轮** | 已上传，在识别/任务/合成中 | 没跑到 → 一行都不执行 | 一律不许播 | `cancelled` |
| **停止播报** | 音频正在播 | **完全不影响** | 立刻停 | 仍是 `done` |
| **被新的一句顶掉** | 旧的还没回来，用户又说了 | 旧的不再继续 | 旧的不许播 | `superseded` |

> **为什么取消和停止播报必须分开**：取消是"这件事我不想要了"，停止播报是"这件事做完了，只是不想听"。
> 如果混成一个按钮，就会出现"点了停止，已经把成功的任务标成取消"这种事故。

### 2. 澄清：听不准时先问一句，不硬猜

- 最多问 **2 轮**（`MAX_CLARIFY_ROUNDS=2`）
- 消解**用规则不用模型**（序号 / 关键词 / 设备名 / 整句重放）——因为选错会真的下发采集指令，代价是物理世界的
- 反问轮**不调用任何业务工具**，只负责问
- 到上限给退路，而不是继续问第三遍
- 反问也**念出来**（语音助手不能在屏幕上问问题）
- 澄清时可以直接**打字**补充，走同一条链路，但如实标注 `audio_source=text_input`（不伪装成麦克风）

### 3. 迟到结果隔离：服务端硬拦

前端是可能被绕过的一层（用户可以直接打开音频地址），所以**隔离写在服务端**：

| 情况 | 返回 | 为什么 |
|---|---|---|
| 正常完成 | `200`，给音频 | — |
| 取消了，但从未合成 | `404 NO_REPLY_AUDIO` | 本来就没音频，说 410 会让人以为被藏起来了 |
| 取消了，音频已合成 | **`410 Gone`** | 音频真的存在，但这一轮不许播 |

> 用 `403` 会让人以为是权限问题，用 `404` 会掩盖"它其实生成过"这个事实。

### 4. 前端可以看得见、控得住

| 界面元素 | 作用 |
|---|---|
| 状态条 | 空闲 / 在听 / 在算 / 播报中 / 等待澄清（状态由服务端给，前端不自己发明） |
| 停止按钮 | 按当前阶段自动分发到"放弃录音 / 取消 / 停止播报" |
| 会话条 | 显示 `session_id`、有没有在途任务、第几轮 |
| 澄清卡片 | 能点候选，也能直接打字 |
| 时序表 | 四个耗时数字全来自接口，前端不算 |
| 事件流 | 按 `request_id` 串起来，取消/被顶掉的事件标红 |

**按钮文案的纪律**：点了取消之后，页面只说"**已登记取消**"，不说"已取消"。
因为在收到服务端的确认之前就宣称取消成功，等于替服务端说谎。

## 一个必须说明的环境情况

本次复跑时，这台机器一度**没有可用的音频输出设备**（`SpVoice.GetAudioOutputs()` 返回 0），
导致 SAPI 合成真人语音失败。这是**设备层的问题，不是代码问题**
（第 5 周的记录里 TTS 是好的：`engine=sapi` / `ms=407`）。

处置方式是三层，**每一层都不许"假装成功"**：

1. 合成前先探测设备，取不到就直接给出人能读懂的错（而不是一个看不懂的错误码）
2. 自动降级到 `tone` 合成音保住链路可测性，但**如实标注**：`tts.engine="tone"`、`voice=null`、`speaks=false`
3. 自检自己识别环境，切换到注入模式，并在结尾**如实报告**有多少轮是注入的

> 关键原则：**降级可以，冒充不行。** 如果合成音长得和真语音一样、记录里也不标，
> 那"本周实测 TTS 正常"这句话就变成假的了。

**该状态随后自行恢复**，恢复后立刻用真实语音完整验证了一遍（见上面的 `voice6_real_voice.log`）。
所以本周的结论**不依赖 TTS 是否可用**：取消、迟到隔离、澄清、时序在两种环境下都成立。

## 已知限制（如实说明）

1. **没有使用开发板的麦克风**。音频来自浏览器麦克风或上传的录音文件；板载麦克风属于端侧硬件课，本周不作为前提。
2. **半双工是"服务端记账 + 前端自觉"，不是音频层抢占**。没有做回声消除，用户边说边播时音频会重叠。真正的可打断（barge-in）需要 AEC，本周不做。
3. **澄清消解是确定性规则，不是"模型听懂了"**。只认序号、意图关键词、设备名三类回答；说得太绕就是 `unresolved`。这是**故意的**——选错会真的下发采集指令。
4. **时序是服务端视角**。`t0` 是服务端收到完整音频的时刻，不含"用户说完 → 浏览器上传"这一段（那一段由 `client_ack_ms` 单列为本地事实）。
5. **数据库仍是单机 SQLite**。周内的三表并发写已经能撞出 `readonly database`，生产环境应换 PostgreSQL/MySQL。
6. **打字补充不算语音**。记录里如实标 `audio_source=text_input`、`asr.engine=keyboard`，统计"语音使用率"时不能算进去。

## 本周的中心句

> **"能停下来"不是一个按钮，而是三件可核对的事实** ——
> 任务到底跑没跑（`action_taken`）、音频到底给不给（404 / 410）、
> 结果到底属于哪一轮（`request_id`）。
> 三件事都落到库里，界面才敢说话。
